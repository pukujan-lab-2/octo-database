## Summary

Octo is a reusable self-hosted control plane for personal, family, work, research, and project-specific applications. It provides one identity/workspace boundary, one logical file/data API, one operational control surface, and optional capabilities that can be enabled without forcing every workspace to run every subsystem.

The program must be delivered in vertical slices. Each slice is independently useful, preserves stable boundaries for later replacement, and cannot silently expand the platform into a general cloud, enterprise SaaS, or distributed-systems project before the preceding user path works.

## PDD / product goal

A signed-in owner can manage multiple workspaces, upload and view private files, use a dedicated family/gallery UI, share a scoped album without exposing the admin console, archive inactive bytes from R2 to Drive without changing logical file IDs, inspect jobs/activity, and later grant narrowly scoped agent access. Advanced retrieval, graph, analytics, and distributed operation are optional layers built only after the core path is usable.

## Program success condition

The program's first major success milestone is an end-to-end path that works from a fresh browser session:

Google login → authorized workspace → upload image → thumbnail/gallery → full image view → read-only share link in a logged-out browser → revoke share → archive file R2→Drive → restore Drive→R2 → view again → see job/activity evidence.

Success also requires:
- no cross-workspace data leak in negative tests;
- no master storage/database credential in browser or agent surfaces;
- canonical state recoverable from PostgreSQL + durable object storage;
- every later subsystem remains removable/rebuildable unless an accepted issue explicitly changes ownership.

## Architectural invariants / SDD program contract

- PostgreSQL/Supabase owns canonical operational/control state.
- R2 owns active object bytes; Google Drive owns cold/archive bytes.
- The platform API owns routing and policy; clients request logical resources, not providers.
- Every durable user-owned resource carries a workspace boundary.
- Human, agent, and service principals are distinct but use the same authorization model.
- pgvector/Neo4j/DuckDB outputs are derived/capability-specific unless a later issue says otherwise.
- Dashboard/UI code never becomes the source of authorization truth.
- Secrets stay server-side and outside GitHub planning artifacts.
- Operators may inspect operations without automatically gaining private-content access.
