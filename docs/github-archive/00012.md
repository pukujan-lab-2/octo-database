## FalkorDB provisioning plan (owner-directed 2026-10-06)

Owner chose FalkorDB over Neo4j Community and Apache AGE for the per-project graph: its native "one graph per workspace" matches the isolation model, vs Neo4j Community's single-database limit and AGE's lack of RLS on PG16. This comment records the provisioning plan. Engine choice is settled; not relitigated.

**Shape:** FalkorDB as a fourth container on `octo_internal`, one graph per workspace, reachable by agents only through Octo's mediated API/MCP, as a rebuildable projection of canonical PostgreSQL. Sliced smallest-first.

### Isolation story (honest — this is the important part)

FalkorDB inherits **none** of the `octo.*` RLS fence. It is outside the octo schema, outside `octo_app`, and outside the request pipeline that binds `request.workspace_id`. Three layers enforce per-workspace isolation, all of them *outside* the engine:

1. **One graph per workspace, named server-side.** The graph name is derived from the authenticated workspace UUID inside the mediation path and never accepted from client input. No route takes a graph-name parameter.
2. **Network confinement.** No published port; only containers on `octo_internal` can dial 6379.
3. **Octo mediation.** Every graph read crosses the same four checks as every other capability. Agents hold Octo keys, never the Redis password.

**Correction to an earlier claim:** FalkorDB core documents **no per-graph Redis ACLs** — the docs have no ACL page. The single global `requirepass` is an access gate, **not a tenant boundary**: anyone holding it can query every graph. So the engine offers zero tenancy backstop. The mediation path is the *only* thing preventing cross-workspace graph access — in Postgres a scoping bug is backstopped by RLS; here it is not. Residual risk stated plainly: one scoping bug in the graph route = silent cross-workspace read.

### Open questions for the owner

1. **Image tag:** `falkordb/falkordb-server` at `v4.22.0` or `6.0.1`?
2. **`/health` reporting the graph?** Recommend: informational at most, never part of the deploy gate. Doing nothing is also fine.
3. **What fills the graph?** The slice-9 epistemic tables (`claims`/`beliefs`/`claim_relations`) have **zero references in `src/`** — an empty schema with no write path, so a projection from them projects nothing. Does GraphRAG source from epistemic rows (needing an epistemic write path first) or from documents/chunks (needing a defined node/edge mapping)? This decides Slice E's content.
4. **Enqueue path for `graph_rebuild`:** generic `POST /api/jobs` (operator role) or server-internal only?
5. **AOF on/off?** If the graph is purely rebuildable, AOF is restart-convenience, not backup. Recommend: rebuild-from-Postgres is the entire durability story.

8. **Local parity in Slice A**, or gravebuster-first with the local mirror to follow?

## Slice decisions (A–D built; recorded 2026-10-06)

Owner directive was to resume and finish the authorized work without pausing. The eight open questions are decided below with the minimal default that keeps the requested workflow working; questions whose answer belongs to slice E are deferred with the reason recorded.

**Delivered**
- **A** — `octo-graph` on gravebuster + local compose, internal-only, pinned tag. PR #167 (merged).
- **B** — `src/graph/falkordb-client.ts`: the single grep-able boundary; derives the graph name from the workspace UUID, exposes only `GRAPH.RO_QUERY`. PR #168.

### Decisions

1. **Image tag** → `falkordb/falkordb-server:6.0.1`. The newer of the two, pinned to an explicit upstream tag (never `${IMAGE_TAG}`) so `rollback.sh` keeps addressing the same engine build.
2. **`/health` reporting the graph?** → **No change.** The graph is optional and must never gate API startup or the deploy gate (which greps `"connected":true`); a graph hiccup must not auto-rollback a healthy deploy. The route reports its own state (`503 GRAPH_NOT_CONFIGURED`) and capabilities advertise `graph.query` as `unavailable`.
3. **What fills the graph?** → **Deferred to slice E.** Confirmed the slice-9 epistemic tables (`claims`/`beliefs`/`claim_relations`) have zero references in `src/` — no write path — so projecting from them would project nothing. This is E's content decision, and E is not authorized here.
4. **Enqueue path for `graph_rebuild`** → **Deferred to slice E** (it is the job E introduces).
5. **AOF** → **Off.** A graph is a rebuildable projection of canonical Postgres, so rebuild-from-Postgres is the entire durability story; no data volume, no AOF.
6. **Workspace deletion** → **Deferred to slice E.** Today a deleted workspace can leave a rebuildable orphan; `GRAPH.DELETE` belongs with the projection lifecycle, not this slice.
7. **Memory bounds** → `mem_limit 1g` with `--maxmemory 768mb`. FalkorDB is in-memory; the engine cap sits below the container cap so it refuses writes and degrades instead of growing into an OOM kill that would take the host.
8. **Local parity in slice A** → **Included.** `deploy/local` mirrors the service so the local workflow matches gravebuster.

### Eval note

The graph read is exercised two ways: the fail-closed path (401/403/400/503) runs everywhere, and a `falkordb` service is wired into `gates.yml` so the configured path (a read against an unprojected workspace returns empty rows, not an error) runs in CI rather than skipping.
