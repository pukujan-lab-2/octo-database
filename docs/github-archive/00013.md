## Summary

Add an analytical data path using Parquet in R2 plus DuckDB query jobs, without turning the operational PostgreSQL database into the bulk OLAP store.

## Identity and lineage

- Parent: #1.
- Task ID: OCTO-1100.
- Depends on: #4, #8, #9.
- Optional capability: analytics-enabled workspaces only.

## Goal

Register a large/tabular dataset as Parquet objects in R2, query it with DuckDB through an Octo-controlled job, and register result artifacts without exposing R2 master credentials or loading bulk analytical rows into canonical operational tables.

## Success condition

- dataset catalog row identifies workspace, logical dataset/version, schema/format, R2 locations, provenance;
- DuckDB reads multiple Parquet files directly;
- analytical query completes through job API;
- result Parquet is written to R2 and registered;
- another workspace cannot query it;
- operational Postgres stores metadata, not every analytical row;
- agent receives only scoped analytics capability.

## SDD / ownership

Postgres: dataset metadata, versions, ownership, jobs, result metadata.
R2: Parquet data/result artifacts.
DuckDB: ephemeral/on-demand compute engine.
Later Iceberg/ClickHouse: not present until accepted need.

Partition/path layout is an optimization, not the authorization mechanism.

- Another workspace cannot query it: 404 for foreign versions/jobs/results; RLS tenant fence on all three tables.
- Postgres stores metadata only; bytes live in R2.
- Scoped capability: `datasets.register` (write), `analytics.query` / `analytics.query_status` / `analytics.result` (read), plus the four MCP tools.
