## Summary

Use the working platform as a deliberate distributed-systems learning lab. Scale only after the single-node path is useful and measured; introduce one concurrency/failure dimension at a time and preserve the earlier logical contracts.

## Goal

Demonstrate that Octo's logical behavior survives controlled horizontal scaling and partial failure, while adding observability/queue infrastructure only when measured pain justifies it.

## Success condition

At minimum:
- two workers process the same job source without duplicate logical completion;
- worker loss is recovered;
- network/provider interruption produces bounded retry/reconciliation;
- API can run statelessly enough for a second node;
- DB connection pressure is measured before adding pooling/replicas;
- logs/traces added only where they answer a real debugging question;
- earlier authorization/storage invariants remain unchanged.

## SDD / staged scale path

1. one server / one worker baseline;
2. two workers;
3. explicit lease/ack/retry/DLQ if Postgres job model needs it;
4. structured telemetry;
5. second stateless API node + load balancer;
6. DB pooling/replica only after measurement;
7. partitioning/sharding only after demonstrated database limit.

No technology may jump ahead without evidence from the previous stage.

## Scope control

In scope:
- concurrency;
- fault injection;
- queue semantics if needed;
- OpenTelemetry/OpenObserve when debugging need is demonstrated;
- multiple API nodes;
- DB connection/pool measurement.

Out of scope:
- Kubernetes for branding;
- distributed DB by default;
- Kafka without workload need;
- synthetic scale targets disconnected from actual project;
- “exactly once” claims without proof.

## TDD / failure-drill plan

- two workers claim same eligible job;
- worker dies before/after side effect;
- database unavailable briefly;
- R2/Drive/provider timeout;
- API node dies mid-request;
- retry storm/rate limit;
- DB connection saturation experiment;
- trace correlation by RUN_ID/job ID across components.

## Evidence to close

- baseline and scaled metrics;
- exact failure-drill logs/traces;
- duplicate-side-effect check;
- recovery state;
- authorization equivalence;
- reason for each newly introduced infrastructure component;
- green gates.

## Rollback / recovery

Every scaling component must be removable back to the last stable single-node mode. If concurrency breaks correctness, reduce worker/API count first, preserve evidence, and fix invariants before adding more infrastructure.
