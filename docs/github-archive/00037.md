## Decision record — FOSSIL as the durable epistemic store for hosted agent workspaces

**Verdict: do not adopt FOSSIL as Octo's canonical database.** FOSSIL is a well-built durable substrate, but it is not a database and cannot serve a hosted, multi-tenant agent workspace. This record answers the three readings, compares the two models entity by entity, and names the one integration surface that would actually be reuse rather than added scope.

**Evidence base.** `fossil-core` @ `2b20dc8` (canonical checkout `D:\claude\projects\fossil\fossil-core`); Octo `origin/main` @ `a5db270`. Three parallel deep-dives were run: (a) FOSSIL capability inventory, (b) storage-substrate feasibility, (c) Octo-side fit. All three reported and converged.

---

### 1. What FOSSIL actually is

- **There is no relational database anywhere in `src/`.** A grep for `postgres|psycopg|sqlalchemy|sqlite3|DATABASE_URL` over the canonical checkout returns zero hits. Adapters present: `filesystem`, `s3`, `litellm`, `mcp`, `vector`. Projections: `graphiti` (Neo4j), `ledger`, `migration`, `null`.
- **Canonical truth is exactly two things:** immutable content-addressed artifacts (`blobs/sha256/<xx>/<digest>`, id `art_<digest[:32]>`) and an append-only knowledge-event log (one immutable JSON file per event). Durability comes from create-no-overwrite — `_S3ObjectBackend.put_immutable` uses `IfNoneMatch="*"`, and the filesystem path `fsync`s a temp file before `os.link`ing it into place.
- **The two durable ports are narrow.** `ArtifactStorePort` (`put_bytes`, `put_file`, `get_manifest`, `read_bytes`, `verify`, `is_redacted`, `get_redaction`, `redact`) and `EventStorePort` (`prepare`, `validate`, `commit`, `get`, `iter_events`, `is_redacted`, `get_redaction`, `redact`). Both are KV + append + scan. Neither is relational.
- **No users, tenants, workspaces, principals, roles, or authentication.** Isolation is logical only: `PackAccess` read/write manifests plus a capability registry, with a node mounting a single pack (`src/fossil_core/domain/pack.py`). The declared non-goals (`ARCHITECTURE.md` §17) explicitly exclude custom auth/OAuth.
- **The governing rule is enforced, not aspirational:** "a projection may help find or inspect knowledge; it may not become the authority that defines the knowledge" (`README.md`).

### 2. Entity-by-entity: FOSSIL's durable model vs Octo's `octo` schema

| Concern | FOSSIL | Octo (`octo` schema) |
|---|---|---|
| Durable unit | content-addressed artifact blob + append-only event | mutable row in `octo.files` |
| Identity | `art_<sha256[:32]>` — content-derived | UUID primary key, stable across content change |
| Mutation | never; supersede via a new event | `UPDATE`, with `status`/`archive_state` transitions |
| Query | iterate events / scan by prefix; retrieval via reranker projection | SQL joins, filters, indexes, `ORDER BY` |
| Multi-tenancy | none (single mounted pack) | `workspaces`, `memberships`, RLS on every table |
| Authorization | `PackAccess` manifest (logical) | Postgres RLS + scoped agent tokens (`/api/capabilities`) |
| Transactions | none | ACID, incl. `FOR UPDATE SKIP LOCKED` job leases |
| Bitemporal claims | claim lifecycle via events + supersession/retraction | `20261001040000_slice9_epistemic_schema.sql` — claims/beliefs/evidence/provenance, bitemporal, RLS |
| Redaction | first-class, with non-resurrection guarantee | not modeled |
| Research/conversation lineage | first-class (the core competency) | not modeled |

Octo's Slice 9 epistemic schema is currently **schema-only**: no file under `src/` references the epistemic tables and there is no epistemic API route. The overlap with FOSSIL is therefore on paper today — but #11 already fixes PostgreSQL as the canonical substrate for it.

### 3. The three readings

**(a) Back FOSSIL's durable substrate with a relational DB via a new adapter — *sound in principle, buys nothing in practice*.**
The ports are KV + append + scan, which a Postgres table can trivially serve, so the adapter is writable. But it adds no capability FOSSIL lacks (filesystem/S3 already provide it), it requires a *third* `SourceSnapshot`-style port because the pack directory layout is load-bearing (`pack_fixture.py` asserts it), and a mutable store reopens the redaction-resurrection hole that create-no-overwrite exists to close. It is sound only as a dumb immutable KV — at which point it is strictly worse than the S3 adapter that already ships.

**(b) Replace PostgreSQL as Octo's canonical operational store — *unsound*.**
FOSSIL has no mutable current-state rows (no `files.status`, no `archive_state`), no transactions (no lease-based job queue), no joins, no RLS, and no principal/workspace/membership model at all. Octo's entire operational surface — auth, workspace scoping, gallery, shares, jobs, archive lifecycle — is relational and tenant-scoped. Adopting FOSSIL here means re-implementing the database Octo already has, on a substrate whose central invariant forbids mutation. This fails on capability, not on taste.

**(c) Run self-contained with no external service — *sound; this is the designed mode*.**
Filesystem-only is FOSSIL's native, tested configuration. The useful finding is that this needs **no new service in Octo**: Octo's R2 client is `@aws-sdk/client-s3` with an endpoint override and `forcePathStyle: true` (`src/storage/r2-client.ts:76-83`), i.e. R2 is S3-compatible — and FOSSIL already ships `S3ArtifactStore` and `S3DurableEventStore` (`adapters/s3/storage.py`, `IfNoneMatch="*"`). FOSSIL's durable corpus could therefore live in Octo's *existing* bucket, off-machine, with zero new infrastructure.

### 4. What a hosted agent workspace needs, and whether FOSSIL satisfies it

A hosted workspace that records agent data and research needs: (i) tenant isolation with per-workspace authorization; (ii) a mutable operational record (what exists now, in what state); (iii) durable, attributable research lineage. FOSSIL satisfies **(iii) exceptionally well** and **(i) and (ii) not at all** — no tenant concept, and no mutation by design. Judged on its tested capabilities rather than its aspirations, FOSSIL is a lineage store, not a workspace store.

### 5. Recommendation (AGENTS.md-compliant)

**No integration is warranted now.** Adopting FOSSIL as Octo's database would be an added external dependency and a second source of truth — it fails "minimum sufficient change" and "no speculative future-proofing." Octo's Slice 9 schema (#11) already owns the epistemic model on the substrate #11/#12 fixed as canonical; the real gap is that #11 is unimplemented, which argues for building #11, not for swapping the store.

**The one surface that would pass the rules, if the owner later wants durable research lineage:** run a FOSSIL node against Octo's existing R2 bucket using its already-built `S3ArtifactStore`/`S3DurableEventStore`, exposed through its existing `mcp` adapter — reusing two shipped adapters, adding no service, no schema change, and no credential system. That is a *future* owner decision; it is recorded here so the option need not be re-litigated from scratch.

**Integration surfaces evaluated:**
- MCP node against existing R2 — viable; reuses two shipped FOSSIL adapters and Octo's existing S3-compatible bucket; no new service. *Recommended if lineage is ever wanted.*
- Python CLI/library call from Octo — viable but adds a cross-language runtime dependency to a Node service. Not warranted.
- PostgreSQL re-implementation of FOSSIL's ports — unsound (§3a).
- FOSSIL-as-store replacing Postgres — unsound (§3b).
