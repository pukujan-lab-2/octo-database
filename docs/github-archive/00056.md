## Root cause confirmed and fixed — PR #57

Investigated with Playwright against the live site and a local route-stubbed harness. The two reported symptoms share one cause, and it is **not** the deployment or the server.

**The server and deploy are correct.** `GET /api/me` returns `isPlatformOwner: true` for `pujan3645@gmail.com`; `GET /api/workspaces` returns both workspaces; a fresh session renders the full dashboard with the 👑 badge and ⚡ Admin button. Gravebuster is running the current build (`octo-web:81a17ed54aa8`, `production == main`). So proposals 1 and 2 in the issue are ruled out.

**Root cause — the client never re-validated a persisted session.** The restore effect only ran when a token existed **and** the principal was *missing*:

```js
if (sessionToken && !principal) { ... }
```

So when a principal was already in `localStorage`, it was trusted as-is:

- **Stale persisted principal** (saved before `isPlatformOwner` was set) → badge and Admin button never render, and the workspace fetch leaves the body on "Loading workspace details…" — symptom 1.
- **Token the server no longer honours** → the workspace list comes back empty and the app keeps the stale principal, showing "No Authorized Workspaces" with the selector gone — symptom 2.

Playwright reproduced both exactly, and neither appears with a fresh session.

**Fix (PR #57):** restore always calls `GET /api/me` for a persisted token and replaces the persisted principal with the server's answer, so a restored session and a fresh OAuth login cannot diverge. A `401` now clears the dead credential *and* all derived state (workspaces, active context, files, gallery, shares, jobs, activity, keys) via a shared `clearSession` helper, returning the caller to the login screen instead of an empty signed-in shell. A Playwright regression covers the dead-token path.
