## Summary

Fixes the two symptoms in #56 (platform owner sees a stuck "Loading workspace details..." after OAuth login, and "No Authorized Workspaces" after refresh, with no Platform Owner badge or Admin button in either state).

Root cause: the client trusted the `octo_principal` / `octo_token` values persisted in `localStorage` without checking them against the server. The previous restore effect only ran when a token existed **and** the principal was missing, so a stale persisted principal was never refreshed and a token the server no longer honours was never rejected.

- Restore now always calls `GET /api/me` when a persisted token exists. The server's principal replaces the persisted copy, so a restored session and a fresh OAuth login cannot diverge.
- A `401` clears the dead credential **and** all derived state (workspaces, active context, files, gallery, shares, jobs, activity, keys) through a shared `clearSession` helper, returning the caller to the login screen instead of an empty signed-in shell.
- `handleSignOut` now reuses `clearSession` (also fixes the stale `activeContext` it previously left behind).

2. **Stale persisted principal** (missing `isPlatformOwner`, `/api/me` → owner): the 👑 Platform Owner badge and ⚡ Platform Admin button render, the body resolves past the loading state into "Workspace Capabilities", and no empty-workspace card appears. Screenshot audited.
