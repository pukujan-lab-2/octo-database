# Issue #61: Research + plan: workspace/database model, API key semantics, storage routing, archive lifecycle, and dangerous-command protection

- State: closed (2026-10-06)
- Opened by Pukujan on 2026-10-02
- Original: https://github.com/Pukujan-lab/octo-database/issues/61
- Labels: enhancement

## Why this issue exists

The owner asked a set of product questions about how Octo actually behaves:

- Where is the account-wide API key and the workspace key?
- How does a workspace work, and how do I view individual databases in a workspace?
- If I create a workspace for one app that uses various types of DB, how does the app route to server hot data vs R2 vs Google Drive?
- When does data go to Drive archive, when is it called back on demand, can agents do it, and was it tested end to end?
- Will a blind agent holding a key be able to create a workspace, and does deleting a workspace require a human password?
- What protects a workspace / a database from dangerous commands?
- If I build a CRUD app that needs a workspace via a workspace key or an account-wide key, how do the app and agent actually use the keys, and are they defined?

This issue records the research findings (what exists, what does not) and the plan. **No implementation starts until the owner confirms the decisions in the "Decisions needed" section.** All claims below are grounded in the current `main` tree.

---

## Research findings

### 1. Account-wide vs workspace-scoped API keys — they exist, but the UI is incomplete

**Both key types are implemented and creatable from the dashboard.**

- UI: the `🔑 API Keys (Account-Wide & Workspace-Scoped)` card (`src/ui/Dashboard.tsx:791-887`) has a scope `Select` (`Workspace-Scoped` default / `Account-Wide`), a name field, and `Generate API Key`. The raw secret is displayed once (`createdSecret`).
- Server: `POST /api/keys` (`src/server/index.ts:1186`). Account-wide = no `workspaceId` → prefix `octo_live_acc_`; workspace-scoped = `workspaceId` → prefix `octo_live_ws_`. Default scopes `['read','write','files']`. Allowed scopes `read, write, files, delete, admin`.
- Table: `octo.api_keys` (`supabase/migrations/20261001010000_slice2_files_and_api_keys.sql:29`), where `workspace_id IS NULL` means account-wide and `role IS NULL` means "derive authority from the principal's live memberships".

**Gaps in the key surface:**
- The keys table shows Name / Prefix / Scope / Scopes / Last Used but has **no Revoke button**. The `DELETE /api/keys/:id` route exists (`index.ts:1272`) but nothing in the UI calls it.
- No expiry picker and no per-key scope picker in the UI — every key gets the server default scopes.
- The `admin` scope is accepted at creation (`ALLOWED_SCOPES`, `index.ts:1204`) but is **never enforced anywhere** in the server.

### 2. Workspaces and "individual databases" — there is no database entity

- A workspace (`octo.workspaces`) is the **only** tenancy boundary. Files (`octo.files`) belong to a workspace.
- There is **no `databases` table, no database route, and no database UI**. Grep across `src/` finds "database" only in the sense of the Postgres client, never as a user-facing entity.
- The dashboard exposes exactly two views of workspace contents: the `File Catalog (Cloudflare R2)` table and the workspace Gallery.
- The closest thing to "various types of DB" is the set of *optional per-workspace capabilities* named in `PROJECT.md` (pgvector/RAG, epistemic schema, Neo4j projection, DuckDB/Parquet) — but none of these is browsable as a "database" in the UI today.
- The canonical contract in issue #1 already says: *"Every durable user-owned resource carries a workspace boundary"* and *"The platform API owns routing and policy; clients request logical resources, not providers."* Under that contract the workspace **is** the data boundary.

**So: "individual databases in a workspace" does not exist as a concept.** Whether it should is the central decision below.

### 3. Storage routing (hot vs R2 vs Drive) — no routing or tiering exists

- Uploads go to **R2 unconditionally** (or local FS in dev). `provider: 'r2'`, key `workspaces/{workspaceId}/{fileId}/{name}` (`src/storage/file-service.ts`).
- There is **no automatic tiering**: no size threshold, no MIME rule, no age rule, no policy that sends a file anywhere.
- "Hot data" is R2 only. There is no Postgres-stored small-file tier and no in-memory file cache.
- The only R2→Drive movement is `archiveFile()`, invoked **only** by the manual archive button.
- Reading an archived file **does** restore on demand: `GET /api/files/content` calls `ensureActiveBytes()`, which on an R2 miss restores Drive→R2 and then streams from R2 (`index.ts:156-177`).

**So: an app cannot choose a tier. Everything is R2 until a human presses Archive.**

### 4. Archive lifecycle — manual only, no retention, not E2E-verified by me

- There is **no retention/expiry/age policy**. Nothing auto-archives. There is no cron, no `setInterval`, no pg_cron, no worker script in `package.json`.
- The only trigger is a human clicking Archive → `POST /api/files/:id/archive` → enqueues an `archive_file` job. The queue is drained **manually** via `POST /api/jobs/run` (or the worker process, which nothing schedules).
- "Called on demand" works: archived files still list in the gallery (`status='active'`), and bytes are transparently restored from Drive on read.
- Agents: the archive/restore route (`index.ts:1036`) requires operator+ workspace **role** but calls **no `requireScope`** — so any key whose principal holds operator+ can archive/restore, regardless of the key's scopes.
- **End-to-end: not verified by me in this session.** There are unit/route tests for the lifecycle, but I have not run a live R2→Drive→R2 round trip. I will not claim this works until I do.

### 5. Blind agent: create workspace / password-protected delete — neither exists

- **Create workspace: no route.** `POST /api/workspaces` does not exist. Even the UI cannot create a workspace — workspaces are auto-provisioned only on login (`personal-<id8>`) and guest (`guest-<id8>`). `createWorkspace()` in `workspace-service.ts` is dead code.
- **Delete workspace: no route.** `DELETE /api/workspaces/:id` does not exist.
- **No password/confirmation gate exists anywhere** in the codebase.

**So today a blind agent can neither create nor delete a workspace.**

### 6. Workspace / database protection for dangerous commands — none

- No password, no retype-the-name confirmation, no soft-delete, no "protected workspace" flag.
- The only gates are role (owner/admin/operator/member) and, where wired, scope. File delete requires owner/admin **and** the `delete` scope. Archive/restore requires operator+ but no scope.
- Routes that skip scope checks entirely: `GET /api/me`, `GET /api/activity`, `POST /api/jobs/run`, `POST /api/jobs/:id/retry`, archive/restore, and key revoke.

### 7. How an app/agent uses a key — defined, but partly aspirational

- Keys **are** documented at `GET /api/capabilities` (`src/api/capabilities.ts`): 8 advertised actions with their required scope, plus `AUTH_GUIDANCE` (Bearer `octo_live_...`).
- **But `src/api/gateway.ts` — the module meant to route agent API requests — is dead code.** It is never imported by the live server; only tests exercise it. Agent calls hit the same server routes humans use, authorized by `authenticateRequest` (key → principal) + `requireScope` where present.
- The advertised capabilities do not all match enforcement: `admin` is never enforced, and several routes are unscoped.

## Decisions needed (owner)

1. **Database model.** Keep the workspace as the single data boundary (one workspace per logical DB), or introduce an explicit `databases` sub-entity inside a workspace?
2. **Destructive-op protection.** Add a human-confirmation gate (password or retype-name) for workspace delete and other dangerous commands, or keep role/scope-only?
3. **Archive lifecycle.** Keep archive manual, or add a retention/tiering policy plus a scheduler to run it automatically?
4. **Agent surface.** Formalize the agent API (wire real scope enforcement, remove dead `gateway.ts`, document usage) — and at what scope?

**Pukujan commented, 2026-10-02**

## Owner decisions (recorded)

The owner reviewed the research above and confirmed:

1. **Data model — "Workspace = database."** One workspace per logical database. No new `databases` sub-entity. This matches issue #1's contract ("every durable user-owned resource carries a workspace boundary"). The missing workspace create/delete API + UI will be added so a workspace can actually be created for an app.
2. **Protection — add a human confirmation gate.** Destructive commands (delete workspace, and other dangerous ops) require re-authentication beyond role/scope.
3. **Archive — add automatic retention/tiering.** Plus a scheduler so the job queue drains without a human pressing "Run worker pass."
4. **Agent API — wire + document it properly.** Enforce real scopes on every route, remove dead `gateway.ts`, add in-dashboard usage docs.
5. **Key model.** Exactly **one account-wide key total**, plus **one workspace key per workspace**, auto-provisioned when the workspace is created (secret shown once).
6. **Agent permissions.** Named presets (Read-only / Read-write / Ingest / Full) plus a custom scope picker, mapped onto the existing `read/write/delete/files/admin` scopes.

## Bonus defect found and fixed during verification

While bringing the app up locally to check the frontend, two unrelated defects were found and fixed:

- **Server never started on Windows.** `src/server/index.ts` gated `server.listen()` on `process.argv[1]?.endsWith('server/index.ts')`. On Windows `argv[1]` is a backslash path (`...\server\index.ts`), so the guard was always false and the process exited silently with no listener. Fixed by comparing on `path.basename`.
- **Frontend padding inconsistency.** The Active Workspace metadata card applied `p: 2` *and* rendered a `CardContent` (default 16px), double-padding it to 33px while every sibling card sat at 17px; the Gallery header had the same problem (`py: 2` inside an already-padded `CardContent`). Both removed; all cards now align at 17px, confirmed by DOM measurement and screenshot.

## Plan (final) and delivery status

Design approved and merged in #64 (`docs/superpowers/specs/2026-10-01-octo-workspace-data-plane-design.md`). Implementation now on `feat/workspace-data-plane`.

### What shipped

1. **Workspace = database (decision 1).** Added `POST /api/workspaces` (atomic create, slug collision → `409 SLUG_TAKEN`, workspace-key callers refused `403`) and `DELETE /api/workspaces/:id`. Creating a workspace auto-provisions exactly one workspace key and shows the secret once. `GET /api/workspaces` now returns `retentionDays`.
2. **One account-wide key total (decision 5).** Partial unique index `uq_api_keys_account_wide ON octo.api_keys (principal_id) WHERE workspace_id IS NULL`; a second account-wide key → `409`.
3. **Protection gate (decision 2).** `principals.confirm_secret_hash`. Destructive routes fail closed: unset secret → `412`, key caller → `403` (API keys can never delete), wrong secret or slug mismatch → `403`/`CONFIRM_SLUG_MISMATCH`. Dashboard has a Set-Secret then type-the-slug + secret flow.
4. **Retention/tiering (decision 3).** `workspaces.retention_days` (NULL = never auto-archive) drives `runRetentionSweep`, run by `startSchedulers` so the job queue drains without a human pressing "Run worker pass". Uploads still land in R2; Drive is cold only, restored on demand.
5. **Agent API (decision 4).** Real `requireScope` enforcement added to activity, jobs-run, archive, restore, and keys-revoke. Dead `src/api/gateway.ts` removed. In-dashboard "Using your key" panel documents the Bearer format and the full action/scope table.
6. **Agent permissions (decision 6).** Named presets Read-only / Read-write / Ingest / Full plus a custom scope picker, mapped onto `read/write/files/delete`; `admin` is platform-owner-only and separated into `ADMIN_CAPABILITIES`.

### Bonus defect fixed

Re-archive was permanently blocked: the archive job's idempotency key was `archive:<fileId>` and the `(workspace_id, job_type, idempotency_key)` uniqueness meant a second archive cycle never enqueued. Key is now transition-cycle-scoped (`archive:<fileId>:<cycle>`), verified live (`:0` → `:1`).

### Verification

- **End-to-end (live server + real PostgreSQL + real Google Drive):** create workspace → key → upload → archive → restore → re-archive → delete all exercised via the API; slug collision, account-wide uniqueness, agent pinning/refusal, and the confirm-secret gate (412/403/mismatch) each asserted.
- **Unit:** 23 files / 134 tests pass, including new `tests/unit/metamorphic.test.ts` (MR-A round-trip fidelity, MR-B last-copy survival, MR-C scope monotonicity, MR-D key containment) over seeded random inputs.
- **Playwright:** 13/13 pass, including new `tests/e2e/workspace-lifecycle.spec.ts` (golden path + MR-1 idempotent create + MR-3/MR-7 pinning and no-key-delete).
- **Visual:** dashboard, key manager, new-workspace dialog, and custom-scope picker captured and inspected; card padding aligns at 17px.

### What this answers from the original questions

- **Where are the keys?** One account-wide key (`octo_live_acc_`) and one per-workspace key (`octo_live_ws_`) per workspace, both managed in the dashboard's API Keys card with preset/custom scopes, expiry, and revoke.

- **Dangerous-command protection.** The confirmation-secret gate fails closed (unset `412`, key caller `403`, wrong secret `403`).
- **How an app/agent uses a key.** The dashboard's "Using your key" panel documents the Bearer format and the full action→scope table, and every advertised action now has real `requireScope` enforcement.
