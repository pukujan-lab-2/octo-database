# Issue #66: Workspace delete returns 500 on a malformed/empty body instead of a clean refusal

- State: closed (2026-10-04)
- Opened by Pukujan on 2026-10-02
- Original: https://github.com/Pukujan-lab/octo-database/issues/66
- Labels: bug

## Observed

`DELETE /api/workspaces/:id` parses its body with a bare `JSON.parse(await readBody(req))`. An empty or non-JSON body throws before `confirmGate` runs, so the top-level handler returns **500 INTERNAL_SERVER_ERROR** instead of the intended refusal.

Reproduced live against production (`octodb.design-bakery.com`, `313db5a`) with a workspace-scoped API key and no request body:

```
DELETE /api/workspaces/<id>   (no body, Bearer octo_live_ws_…)
→ 500
```

With a body it correctly returns `403 FORBIDDEN: Destructive commands require a human session; API keys can never confirm.`

## Impact

Security outcome is preserved — the delete never happens, because the gate is fail-closed and the throw precedes any mutation. The defect is the wrong status code and an unhandled-error log line for a malformed request. A client or agent that omits the body sees an opaque 500 rather than a contract-shaped 4xx.

## Root cause

`src/server/index.ts` — three routes parse the body unguarded. The workspace-delete route is in the workspace data plane shipped by #61/#65; the same pattern also exists on `POST /api/keys`, `POST /api/files`, `POST /api/workspaces/shares`, `POST /api/jobs`, `POST /api/rag/ingest`, and `POST /api/rag/query` (pre-existing, separate features).

## Fix

Introduce `readJsonObject(req)` — reads the body, tolerates empty/malformed input as `{}` — and use it in the three workspace-data-plane routes so each route's own validation produces its intended 400/403/412. Regression assertion added to `tests/e2e/workspace-lifecycle.spec.ts` (MR-3 & MR-7): a bodyless delete must return 403, never 500.

## Out of scope

Converting the six pre-existing routes is a separate change to features this issue does not own; recorded here so it is not lost.

Part of #61.

**Pukujan commented, 2026-10-04**

Fixed and verified on `production` (promoted via #97). The workspace-delete handler now reads the body with the tolerant `readJsonObject` (`src/server/index.ts:1075`), which returns `{}` for an empty/malformed body instead of throwing. The request then reaches `confirmGate` with `confirmSecret: undefined` and is refused cleanly — 403 `CONFIRM_SECRET_INVALID` (or 412 `CONFIRM_SECRET_NOT_SET`) — rather than a 500. Covered by the `request-body-hardening` E2E spec.
