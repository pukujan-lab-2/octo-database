## Observed facts

- **Octo does not run Supabase.** Production is three containers: Caddy, a
  hand-written Node server (`src/server/index.ts`, ~2350 lines), and bare
  `pgvector/pgvector:pg16`. No GoTrue, PostgREST, Storage service, Studio, Kong,
  or postgres-meta.
- **The schema was written for Supabase Auth.** `octo.principals.auth_user_id`
  maps to `auth.users.id`; every RLS policy calls `auth.uid()` via
  `octo.current_principal_id()`.
- **RLS is declared but not enforced.** All 70 policy statements use
  `ENABLE ROW LEVEL SECURITY`, never `FORCE`. The app connects as the `postgres`
  superuser, which bypasses RLS. There is no `SET ROLE`, no `auth.uid()` binding,
  and no service-role split anywhere in `src/`. Authorization is done in
  application code (`dbGetAuthorizedWorkspaces`, `dbGetWorkspaceMembership`).
- **The custom dashboard duplicates mature OSS admin surfaces.** `Dashboard.tsx`
  (~1313 lines) contains a "Platform Admin" modal with infra-status cards and a
  tenant workspace registry; #52 proposes expanding it. Supabase Studio already
  provides table/SQL/RLS/auth administration.

## Proposal

Research, in three parts:

1. **Multi-project control plane.** Self-hosted Supabase's official compose runs
   exactly one project (~8 containers). `supabase/platform` is the multi-tenant
   control plane Supabase Cloud uses, but is undocumented for self-hosting.
   Enumerate the real alternatives and their isolation/cost/maintenance
   tradeoffs, including but not limited to: one stack per workspace; Supabase
   Cloud (not self-hosted); `supabase/platform`; Appwrite; Directus; Nhost;
   CloudNativePG; Dokploy/Coolify/Porter-style PaaS.
2. **Multi-DB projections.** How a future host serves Neo4j graph projections,
   pgvector, and DuckDB/Parquet analytics **without** hand-building a console for
   each. Which of these have a native console worth linking, and which are
   naturally covered by a Postgres console.
3. **Agent behaviour.** Why coding agents rebuild instead of adopting mature OSS,
   and what concrete repository rule prevents it. This is the root cause, not an
   aside — a fix that only changes the stack will drift back.

## Acceptance criteria

- [ ] Each candidate scored on: multi-project support, self-hostable, per-project
      console, isolation model, container/host cost, maintenance burden.
- [ ] A recommendation for the workspace ↔ project mapping, reconciled with the
      existing "workspace = database" model.
- [ ] A recommendation for non-Postgres projections, with the native-console vs
      custom-console split stated explicitly.
- [ ] A concrete, durable repository rule addressing agent over-build.
- [ ] Explicit list of what must survive any migration: R2/Drive archive
      lifecycle, scoped agent keys, job scheduler, gallery, share links.

## Boundaries / non-goals

- Not a mandate to migrate; a decision aid for the owner.
- No new governance, approval, or evidence gates.
