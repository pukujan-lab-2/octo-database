## Observed facts (verified against the working tree, 2026-10-02)

- Production does **not** run Supabase. `deploy/gravebuster/docker-compose.yml`
  defines three services: `octo-web` (Caddy), `octo-api` (Node), and `octo-db`
  (`pgvector/pgvector:pg16`). There is no GoTrue, PostgREST, Storage service,
  Studio, or postgres-meta.
- `@supabase/supabase-js` is present in `package.json` and used in
  `src/lib/supabase.ts` as a client, but no Supabase server stack is deployed.
- The schema was written for Supabase Auth: `octo.principals.auth_user_id` maps
  to `auth.users.id`, and every RLS policy resolves identity through
  `octo.current_principal_id()` → `WHERE auth_user_id = auth.uid()`.
- **RLS is declared but not enforced.** All 70 policy statements use `ENABLE ROW
  LEVEL SECURITY`, never `FORCE`. The server connects as `postgres` (superuser,
  via `DATABASE_URL`), which bypasses RLS. There is no `SET ROLE`, no
  `auth.uid()` binding, and no service-role split anywhere in `src/`.
- Authorization is implemented in application code (`dbGetAuthorizedWorkspaces`,
  `dbGetWorkspaceMembership`, per-route scope checks in `src/server/`).
- `src/ui/Dashboard.tsx` is ~1313 lines and re-implements admin surfaces a
  mature console provides (workspace registry, infrastructure status). Issue #52
  proposes extending exactly that surface.

## Research scope

1. **Mature self-hosted control-plane alternatives.** For each: does it provide
   a usable admin console, multi-tenant / multi-project support, and a Postgres
   data model. Candidates include, at minimum: self-hosted Supabase (single
   stack vs multi-project), Supabase Studio + postgres-meta alone, Appwrite,
   Nhost, Directus, NocoDB, Baserow, and a plain pgAdmin/DBeaver console.
   Determine what each gives for free versus what Octo would still build.
2. **Multi-project topology.** Whether one workspace maps to one Supabase
   project, one project with RLS tenancy, or a hybrid — and the cost of each in
   containers, migrations, and isolation.
3. **Non-Postgres projections.** How a future cloud host should serve Neo4j
   graph projections, pgvector, and DuckDB/Parquet analytics — whether each
   keeps its own native console navigated from a hub, rather than being unified
   into one custom UI.
4. **Agent behaviour.** Why coding agents rebuild working systems from scratch
   instead of adopting mature OSS with glue code, and what durable repository
   rule (not prose) prevents it. This is the root-cause question; the
   stack-choice questions are symptoms.
