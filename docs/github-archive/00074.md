# Issue #74: Productize Octo through capability contracts and end-to-end vertical slices

- State: open
- Opened by Pukujan on 2026-10-02
- Original: https://github.com/Pukujan-lab/octo-database/issues/74

## Goal

Turn the working Octo backend pieces into a coherent, reusable workspace data platform without preserving weak implementation code for its own sake.

Parent architecture discussion: #72.

## Product contract

`PROJECT.md` is the current authority. The immediate target is:

system requirement → user job → durable backend capability → API contract → usable frontend → automated user-flow verification

Existing R2, Google OAuth/login, Google Drive integration, storage lifecycle behavior, migrations, CI, and production deployment are assets to reuse behind the new contract.

## Delivery model

Do not build one giant oracle for the final product before implementation.

For each vertical slice, write a small productization packet:

### PDD — product/problem definition
- user/job
- why it matters
- in/out of scope
- mature systems to reuse
- observable success

### SDD — system/API design
- authority/canonical data
- server capability
- API contract
- provider integration
- frontend flow boundary
- migration/reuse of existing code

### TDD — verification design
- public deterministic acceptance tests
- integration tests
- targeted metamorphic/property tests
- small hidden holdout only where false completion/overfitting is plausible
- production smoke verification

The issue acceptance criteria are the slice oracle. PCM projects them into task/checkpoint state; PCM does not own the product oracle.

## Program slices

### 1. Workspace capability contract
Stabilize the HTTP workspace API and capability discovery around existing/proven backend behavior.

Done when apps/frontends/agents can discover and invoke the same workspace-scoped capabilities without provider credentials.

### 2. Thin client surfaces
Add a typed TypeScript SDK, CLI, and MCP adapter over the same API.

Done when all three are thin clients and no policy is duplicated outside the server.

### 3. Durable/reconstructible state
Classify valuable agent/user state as durable, synchronized, rebuildable, or ephemeral and expose the required sync/restore capabilities.

Done when a fresh machine can rehydrate one accepted workspace scenario without depending on the old machine.

### 4. Analytics path
Keep live operational state in PostgreSQL; export/compact historical data to Parquet; query through DuckDB; keep BI tools optional downstream consumers.

Done when one workspace can answer accepted long-range operational questions without turning Postgres into the analytical warehouse.

### 5. Frontend bakeoff
Freeze the current dashboard as a prototype. Give competing frontend approaches the same API contract, design system, and user jobs.

Baseline direction to test:
- React/Next.js
- shadcn/ui
- OpenPencil design workspace
- Onlook or equivalent real-code visual editing

Use mature native consoles for deep DB/BI/graph/provider administration.

Done when the chosen approach completes the defined user jobs with substantially less owner rescue than the current dashboard.

### 6. Product shell migration
Build the selected workspace shell and migrate only useful existing behaviors.

Custom surface: workspace overview, files/gallery, agent proposal/review, cross-system summaries, recovery/sync workflows.

## Verification rules

- Code compiling is not product completion.
- Required CI remains mandatory.
- Hidden holdouts/metamorphic tests are slice-scoped, not universal.
- Do not add unrelated security/privacy/compliance machinery.
- Do not preserve old code merely because it exists.
- Reuse mature systems before custom implementation.
- Production promotion continues through the existing `production` branch/runtime path.

## Success

A fresh user, app, or agent can authenticate, choose a workspace, discover capabilities, operate on durable state/files, query permitted analytics, and complete the accepted product flows without owner rescue.

## Owner correction — frontend direction (2026-10-03)

The existing dashboard is not a design reference to preserve. Rebuild its frontend presentation from a clean slate; keep existing Octo API behavior and useful workspace/file/job actions behind the new UI.
