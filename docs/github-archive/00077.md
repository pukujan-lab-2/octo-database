## Role

Strong frontier planning/reasoning model on high effort. **Do not implement product code in this task.**

Parent: #74.

## Goal

Inspect the actual Octo repository and turn the product contract into the smallest coherent sequence of locked PDD/SDD/EVAL slices that can be executed by lower-cost agents without product drift.

## Required inputs

Read:
- `PROJECT.md`
- `AGENTS.md`
- `docs/productization/SLICE_CONTRACT.md`
- issue #74
- issue #72 + working notes only where needed
- current server/API/storage/auth/deploy/frontend code
- current train/helper state after the bootstrap task is available

## Planning requirements

For each proposed slice:

### PDD
- one concrete user/agent job;
- why it matters now;
- in/out of scope;
- mature systems/code to reuse;
- observable success.

### SDD
- canonical state/data authority;
- API/capability contract;
- provider/data flow;
- client surfaces;
- existing code to reuse vs replace;
- bounded failure/robustness level.

### EVAL/TDD
- public deterministic tests;
- real end-to-end job;
- targeted metamorphic/property checks;
- hidden holdout only when overfitting/false completion is plausible;
- production smoke where relevant.

## Balance controls

The plan must explicitly prevent both:
- **overbuilding:** speculative security/privacy, generic abstractions, exhaustive edge-case matrices, premature scale work;
- **underbuilding:** compile-only completion, backend-only completion, missing recovery for durable writes, weak end-to-end verification, half-finished UI.

Use the repository's progressive robustness levels. State why each slice is Level 1, Level 2, or Level 3.

## Frontend bakeoff

Design a bounded bakeoff only after the API/user jobs are stable enough to compare candidates fairly.

Use the same:
- user jobs;
- API contract;
- data fixtures;
- design/content direction;
- evaluation tasks.

Evaluate a small set of approaches, not endless tools.

Candidate tool classes to inspect include:
- **OpenPencil** for agent-addressable/Figma-like design work;
- **Onlook** for visual editing of real Next.js/Tailwind code;
- **Dyad** or a comparable Lovable/v0/Bolt-style local app-builder as a rapid prototype challenger;
- the direct **Next.js + shadcn/ui** implementation path as the production baseline.

The bakeoff decides the delivery workflow/UX approach, not the backend architecture.

## Output

Produce:
1. ordered slice map with dependencies;
2. one locked-ready PDD/SDD/EVAL packet for the **first** implementation slice;
3. draft packets for later slices;
4. explicit Luna work-order format;
5. frontend bakeoff spec and when it should run;
6. risks/unknowns that actually block product success.

Do not broaden the product beyond `PROJECT.md`.

## Done

The owner can review/correct the first packet with a small number of product decisions, and a Luna-class implementer can execute it without inventing architecture, product scope, or its own definition of done.
