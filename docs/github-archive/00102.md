## Summary
The multimodal vision gate could fail a run that its own assertions consider acceptable, and it did: PR #100's `gates` failed on "Workspace Data Plane" with `score=78, passed=false`, then passed on a re-run with `score=98` — **on identical UI**, since #100 only changes server-side authorization. The specs assert `passed === true` *and* `score >= 75`, but the verifier returned the model's own `passed` boolean while the prompt told the model to pass only at `>= 80`. Any score in [75, 80) was unwinnable.

Fix: one exported `VISION_PASS_THRESHOLD = 75` (the bar the specs assert) is embedded in the prompt and `passed` is computed in code as `score >= VISION_PASS_THRESHOLD`. The model still judges the screen; the pass/fail policy now lives in code.

### Explicit decisions (please confirm)
- **Bar is 75, not 80.** The specs already assert `>= 75`, so 75 is the repository's stated bar; the prompt's 80 was the outlier. If the intent is actually 80, say so and I'll raise the specs instead.
- **The model's "no critical UI defects" veto is dropped.** The prompt asked for `passed = score >= 80 AND no critical defects`; the response has no structured critical-defect field, so that veto was never reliable. A genuinely broken layout scores low, and the score now decides. `issues[]` is still surfaced.
- **This does not remove LLM nondeterminism.** A screen scoring near 75 can still flip between runs. Durable options (owner's call, not implemented here): treat the vision gate as advisory (log, don't fail) on non-UI diffs, or run the audit only when rendered files change.
