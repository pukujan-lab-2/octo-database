# Issue #111: [OBSERVATION] Workspace isolation has no engine-level backstop: RLS is bypassed on the server's superuser connection

- State: open
- Opened by Pukujan on 2026-10-04
- Original: https://github.com/Pukujan-lab/octo-database/issues/111
- Labels: plane:lead-owner, observational-issue, proposal, priority:p3

### Priority Rating
P3 (Critical systemic risk — workspace isolation currently rests on application code alone)

### Risk & Blocker Classification
Critical Blocker / High Systemic Risk

### Human-Understandable Summary
Octo's core promise is "host once, serve many": one keyhole in front of shared infrastructure, many workspaces and people, isolated by auth. The intended engine-level backstop for that isolation is PostgreSQL Row-Level Security (RLS), and the RLS policies are present and well-formed in the schema. But on the server's own database path they do not actually fire, because the server connects as the `postgres` **superuser** and never sets the identity claim (`request.jwt.claim.sub`) that the policies read. In PostgreSQL, superusers bypass RLS unconditionally.

Consequence: today, cross-workspace isolation depends entirely on every application query remembering to filter by `workspace_id` / principal. One missed filter is a cross-tenant leak, and a workspace-scoped agent token that escapes its intended path has no engine-level wall behind it. This is exactly the "someone's agent ruins another project's database" risk flagged as the scary part. It is also the foundation for the desired multitenancy model (a provisioned database + a scoped credential per workspace), so it should be resolved at the engine level, not only in application code.

Explicitly **not** a confirmed live leak: the hand-written filters may be complete. This records the *absence of an engine-level backstop*, not a proven cross-tenant read. A full endpoint-by-endpoint audit has not been performed.

### Reproducibility Steps / Evidence
1. `src/server/db.ts:15-26` — the server's pool uses `DATABASE_URL`. Production default (`deploy/gravebuster/.env.example:11`) is `postgresql://postgres:<pw>@​octo-db:5432/postgres`, i.e. the `postgres` superuser role.
2. `supabase/migrations/20261001000000_slice1_principals_workspaces_memberships.sql:52-76` — every policy resolves identity through `octo.current_principal_id()` → `auth.uid()` → `current_setting('request.jwt.claim.sub')`.
3. Grep of `src/` for `set_config` / `request.jwt` / `SET LOCAL ROLE` → **no matches**. The server never sets that claim, so the policies would evaluate against a NULL identity even if RLS applied.
4. Grep of `supabase/` for `FORCE ROW LEVEL SECURITY` → **no matches**.
5. `deploy/gravebuster/initdb/00-supabase-auth-scaffold.sql:16,19` — `anon` and `authenticated` are created `NOLOGIN`; nothing logs in as them, so RLS never applies on the server's connection.
6. Net effect on the server path: RLS does not filter. Real isolation is enforced by hand-written predicates, e.g. `dbGetAuthorizedWorkspaces` (`src/server/db.ts:184-229`), and the server entry imports its DB access from `./db` (the pg pool).
7. Secondary observation: several modules call a Supabase client via `.from(...)` (`src/api/keys.ts`, `src/auth/authorization.ts`, `src/jobs/job-service.ts`, `src/auth/workspace-service.ts`, `src/auth/session.ts`). The live worker path appears to use injected pg-pool deps instead (`src/jobs/worker.ts` + `src/server/index.ts:442`), suggesting this `.from(...)` layer is largely dead/legacy — **needs confirmation** before concluding either way.

### Non-Binding Proposed Next Actions
- *(proposal)* Audit every server database path and record, per path, the connection role and whether an identity claim is set — so the true enforcement boundary is known rather than assumed.
- *(proposal)* Decide the isolation model for the keyhole:
  - **A. Per-workspace provisioned database + per-workspace role** — engine-enforced; a credential physically cannot reach another workspace. Strongest, and matches the "safer keys in the first place" goal.
  - **B. One shared schema, RLS made real** — non-superuser application role, `SET LOCAL` the identity claim per request, and `FORCE ROW LEVEL SECURITY`. Cheaper, keeps one database.
- *(proposal)* Make cross-tenant isolation the slice's explicit success condition: metamorphic/negative tests ("for any principal P and workspace W where P ∉ members(W), every endpoint denies and returns zero rows") plus a small hidden holdout the implementer never sees.
- *(proposal)* Keep destructive and cross-tenant actions behind human-session confirmation (partly exists: `workspaces.delete.any` requires a human session and confirmation secret).
- *(proposal)* Do **not** add formal-methods tooling (Lean/Coq/Dafny) for this: the failure mode is wiring (a missing filter, a connection that bypasses RLS), not a subtly-wrong algorithm, so the leverage is engine-enforced isolation plus targeted tests, not proofs.

### Boundary audit — result (read-only, no code changed)

Read-only pass over every server database path. Question: which role connects, is an identity claim set, where does tenant filtering actually live, and are the `.from()` modules live or dead.

**Method:** read `src/server/index.ts` (all DB-touching routes), `src/server/db.ts` (all exported `db*` helpers), `src/jobs/worker.ts`, `src/mcp/server.ts`; greps for `set_config` / `request.jwt` / `SET ROLE` / `FORCE ROW LEVEL SECURITY` / `current_setting`.

#### Per-path result

| Path | Connection role | Identity claim | Tenant filter | Live? |
|---|---|---|---|---|
| All HTTP routes (files, jobs, gallery, activity, keys, RAG) | `dbPool` → `DATABASE_URL` (prod: `postgres` superuser) | **none** | hand-written: `dbGetWorkspaceMembership` + `keyWorkspaceMatches` + `requireScope`, then `db.ts` predicates `WHERE workspace_id = $1` | live |
| Worker (`drainQueueOnce`, `index.ts:435-465`) | same pool | **none** | deps scoped by `job.workspaceId` | live |
| MCP adapter (`src/mcp/server.ts`) | no DB | n/a | forwards to the HTTP API via `OctoApi` client; inherits the route gates | live |
| `.from(...)` / `createOctoClient` modules | supabase-js (would carry JWT → RLS) | n/a | — | **dead** — `createOctoClient` is never imported; `src/main.ts` imports the services as `import type` only |

#### Findings

1. **No identity claim is ever set.** Grep for `set_config` / `request.jwt` / `SET LOCAL ROLE` / `SET ROLE` / `current_setting` across `src/server/db.ts` → **no matches**. The RLS policies (which read `request.jwt.claim.sub` via `octo.current_principal_id()` → `auth.uid()`) therefore evaluate against NULL identity even if they applied.
2. **The connection role is the superuser in production** (`src/server/db.ts:15-26`; default `deploy/gravebuster/.env.example:11` → `postgresql://postgres:<pw>@​octo-db:5432/postgres`). Superusers bypass RLS unconditionally, so the policies do not fire on this path regardless.
3. **The real boundary is application code, and it appears complete and consistent** on every path read:
   - RAG query (`index.ts:2528`): `authenticateRequest` → `requireScope('read')` → `keyWorkspaceMatches` → `dbGetWorkspaceMembership` → `dbMatchChunks(workspaceId, …)`. Verified `dbMatchChunks` passes `workspaceId` as `$1` into `octo.match_chunks(...)` (`db.ts:1105-1129`).
   - RAG ingest (`index.ts:2412`): same, plus `roleAllows(..., 'operator')`; all three write helpers (`dbEnsureEmbeddingConfig`, `dbUpsertDocumentVersion`, `dbReplaceChunksAndEmbeddings`) scope by `workspace_id`.
   - Worker path is scoped by the claimed job's `workspaceId`.
4. **Platform-owner bypass is intentional, not a leak.** `dbGetAuthorizedWorkspaces` (`db.ts:184-229`) returns *every* workspace to a platform owner; `dbGetWorkspaceMembership` (`db.ts:231-250`) returns `{role:'owner'}` for them. That is the owner account, by design.
5. **The `.from()` Supabase layer is dead code** on the server path — nothing in `src/server/index.ts` imports it. This removes the "inconsistent enforcement across endpoints" worry raised in the original report: there is one data path, not two.

#### Conclusion

The absence of an engine-level backstop is **confirmed**; a proven cross-tenant read is **not**. Hand-written filters are present on every path read. The risk is that this is the *only* thing standing between workspaces, so a single future missed predicate is a cross-tenant leak with no wall behind it.

No code changed by this audit. Isolation-model decision (shared-schema RLS made real vs. provisioned DB + per-workspace role) still open.
