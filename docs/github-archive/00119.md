## Summary

Follow-up to #118. A `push --force` on a `both-changed` or `untracked-both` path uploaded the local file but deleted only the baseline record — which on a `both-changed` path is already gone, because a remote change *is* a new record id. The workspace was left with two records at the same name, and the next run reported the path `ambiguous`, so `--force` never actually converged.

## Fix

The force path now also removes the single current remote record observed at the path, so the upload genuinely overwrites remote as the conflict note ("re-run with --force to overwrite remote") promises.

The id selection moves into a pure `recordIdsToSupersede(path, uploadedId, force)` in `src/sync/reconcile.ts`, so the behavior is unit-testable. The same-name-sweep refusal is unchanged:

- a normal push supersedes only ids this client already exchanged (`baseline.remoteId` + `pendingDelete`);
- a path with more than one remote id (`ambiguous`) is never forced;
- the id just uploaded is never in the delete set.
