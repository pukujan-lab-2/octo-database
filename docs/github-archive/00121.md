## Summary

An independent adversarial review of the shipped `octo-sync` client (the four-lens workflow started last session, completed here) surfaced five real defects. Each was reproduced against the actual code and fixed minimally in `scripts/octo-sync.ts`.

- **Wedge after a failed supersede-delete (high).** A transient `deleteFile` failure during a replace left two records at one name. That path classified `ambiguous`, which no push — even `--force` — acted on, so the persisted `pendingDelete` obligation was never retried and the path stayed stuck with a duplicate forever. Push now retries outstanding supersede-deletes independently of candidacy; a 404 counts as already done.
- **Same-size, mtime-preserved edits missed (data loss).** `scanLocal` reused the recorded sha256 whenever size+mtime matched, so a same-size edit with a preserved mtime was reported `in-sync` and could then be silently overwritten by a pull. It now always hashes, matching the documented "local change = sha256 differs" invariant.
- **Non-atomic state write.** `state.json` was rewritten in place; a torn write parsed as `undefined`, which skipped the `baseUrl`/`workspaceId` binding check and silently re-baselined against a different target. State is now written temp+rename.
- **Staging file could be pushed.** A pull staged into `<target>.octo-tmp`, which the ignore rules did not match, so a leftover from a failed/killed rename could be scanned and pushed as a real record. The suffix is now `.tmp`, which `classifyLocalFile` ignores.
- **`untracked-both` not surfaced as a conflict.** A class only `--force` can resolve was omitted from the reported `conflicts` list and the `--force` note. It is now included.
