# Issue #122: Robustness roadmap: human-stamped creation, rate limits, MFA step-up, and typed keys (research + slice plan)

- State: closed (2026-10-06)
- Opened by Pukujan on 2026-10-05
- Original: https://github.com/Pukujan-lab/octo-database/issues/122
- Labels: enhancement

## Why this issue exists

The owner wants Octo to be usable by agents and programs today, but safe from a blind agent doing mass damage. The owner named these requirements:

- An **account-wide key** (manages everything + mints keys), usable by a person OR an agent.
- **Workspace creation and API-key minting stamped by a human** so an agent cannot create or delete thousands of workspaces.
- A **workspace-scoped key** a human/agent/program uses to manage the workspace.
- Future robustness, **in slices**: MFA required for deletion; MFA for workspace creation and API minting; a workspace-creation **limit** a human must remove manually via the dashboard; a workspace-creation **rate limit** of 1/day, platform owner exempt.
- Future: **multi-tenant typed keys** (e.g. analytics keys that never reach Postgres, agent read-only keys, program-only write keys).

This issue records the research (what exists, what does not) and the accepted decisions. Slice issues are filed separately and link back here.

---

## Research findings (grounded in the current `main` tree)

### 1. The confirmation gate already exists — and is exactly the "stamp" pattern the owner wants

- `confirmGate(res, auth, suppliedSecret)` — `src/server/index.ts:598`.
  - **Refuses API-key callers outright** ("API keys can never confirm"), whatever their scopes. This is the structural answer to "can a blind agent delete a workspace".
  - Fails **closed** when no secret is set: `CONFIRM_SECRET_NOT_SET` (412).
  - Checks `hashApiKeySecret(suppliedSecret) === stored`.
- It is used today by **one** route: `DELETE /api/workspaces/:id` (`src/server/index.ts:1107`), which additionally requires `mem?.role === 'owner' || principal.isPlatformOwner` and a typed slug (`confirmSlug`).
- The secret is set/rotated via `POST /api/me/confirm-secret` (`src/server/index.ts:921`); `GET /api/me` returns `confirmSecretSet`. Storage: `dbGetConfirmSecretHash` / `dbSetConfirmSecret` (`src/server/db.ts`), value = `hashApiKeySecret(secret)`.
- Frontend already has a working set-secret + confirm flow in the delete-workspace modal (`src/main.ts:161-163`, `315-319`).

**So deletion is already stamped. The live gap is creation and minting.**

### 2. The gap: create and mint are ungated

- `POST /api/workspaces` (`src/server/index.ts:~1000-1100`) requires only an account-wide key; creates the workspace + its first workspace-scoped key atomically (`dbCreateWorkspaceAtomic`). **No human stamp.** An agent holding the account key can create unlimited workspaces today.
- `POST /api/keys` (`src/server/index.ts:1693`) mints keys; `authorizeKeyMint` ensures a token may only *narrow* its own authority; `admin` scope is reserved to platform owners. **No human stamp.**

### 3. No MFA and no rate limiting exist anywhere

- Grep for `mfa|totp|2fa|rate.?limit|throttle|cooldown` across `src/` finds nothing but docs. Both are greenfield.
- 2026 baseline: TOTP (authenticator apps, e.g. `otplib`) is the standard step-up; WebAuthn/passkeys are the phishing-resistant upgrade.

### 4. Related existing issues

- **#61** (open) — dangerous-command protection research; already posed the delete-gate decision and flagged that the `admin` scope is accepted but never enforced. Slice 15 closes the create/mint half of #61's decision 2.
- **#52** — proposes the platform-owner Admin Console, the natural home for the "raise/remove a workspace-creation limit" control and the MFA enrollment surface.
- **#72** — control-plane adoption research; the typed-key and provisioned-DB questions live there.

## Accepted decisions (owner, 2026-10-05)

1. **Immediate gate = human session + confirmation secret.** Exact reuse of `confirmGate`. API-key callers structurally refused. (Not "human session only", not "account key + cap".)
2. **MFA mechanism = TOTP first, WebAuthn/passkeys later.**
3. **Rate limit = workspace creation only, 1/day per principal, platform owner exempt.** Key minting is not rate-limited (it is stamped by decision 1).

## Slice plan

| Slice | Goal | Depends on |
|---|---|---|
| **15** (immediate) | Human-stamp `POST /api/workspaces` and `POST /api/keys` via the existing `confirmGate`; add the secret field to the create/mint UI; update E2E | — |
| **16** | Workspace-creation daily limit (1/day, platform-owner exempt) | 15 |
| **17** | MFA (TOTP) step-up for destructive commands (deletion) | 15 |
| **18** | MFA (TOTP) step-up for workspace creation and key minting | 17 |
| **19** | Typed multi-tenant keys (analytics / agent-read / program-write) | 15 |

Slice 15 is first because it is the minimum sufficient change that closes the owner's stated fear ("agents create/delete 1000s of workspaces") **today**, reusing the mechanism already proven on delete — no new subsystems.

## Non-goals (explicitly out of scope)

- No generalized policy engine, no distributed-systems machinery, no speculative extension points (AGENTS.md #8).
- No rate limiting of file writes or other ops (owner chose workspace-creation only).
- No replacement of the confirmation-secret mechanism; MFA layers on top of it in slices 17-18.
