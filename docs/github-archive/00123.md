# Issue #123: Slice 15 — Human-stamped workspace creation and API-key minting (reuse the confirmation gate)

## Summary

A blind agent holding the account-wide key can currently create unlimited workspaces and mint unlimited keys. Deletion is already protected by a human-only confirmation gate; creation and minting are not. This slice extends the **existing** gate to `POST /api/workspaces` and `POST /api/keys`. This is the immediately-usable slice for the owner's own projects.

## Observed facts

- `confirmGate` (`src/server/index.ts:598`) refuses API-key callers outright, fails closed when no secret is set, and verifies a hashed confirmation secret. It is used by **one** route: `DELETE /api/workspaces/:id` (`src/server/index.ts:1107`).
- `POST /api/workspaces` (`src/server/index.ts:~1000-1100`) requires only an account-wide key — **no stamp**.
- `POST /api/keys` (`src/server/index.ts:1693`) requires only a valid key — **no stamp**.
- The frontend already implements a set-secret + confirm flow for delete (`src/main.ts:161-163`, `315-319`); the create-workspace modal (`src/main.ts:154`, submit at `333`) and key-mint form (`src/main.ts:199`) collect no secret.
- E2E `tests/e2e/workspace-lifecycle.spec.ts` creates workspaces and mints keys directly via the HTTP API (guest session token as bearer) — these will break and must be updated.

## Proposal

*(proposal)* Reuse `confirmGate` unchanged:

1. **Server.** In `POST /api/workspaces` and `POST /api/keys`, after authentication, call `confirmGate(res, auth, parsed.confirmSecret)` and return early on refusal. Pass the supplied secret through from the request body (same field name `confirmSecret` as delete).
2. **Frontend.** Add a "Confirmation secret" field to the New Workspace modal and the Generate API Key form; reuse the existing set-secret affordance when `state.confirmSecretSet` is false. Send `confirmSecret` in the request body.
3. **Tests.** Update `workspace-lifecycle.spec.ts` so API-path create/mint in tests supply a confirmation secret set through the human session flow, or drive those steps through the UI. Add an explicit assertion: **an API-key caller is refused (403) at create and at mint**, mirroring the existing delete-key refusal test (MR-3/MR-7).

No new subsystem. No schema change required.

## Acceptance criteria

- [ ] `POST /api/workspaces` with an API-key caller → 403, never creates.
- [ ] `POST /api/keys` with an API-key caller → 403, never mints.
- [ ] Both succeed from a human browser session with the correct confirmation secret.
- [ ] Both fail closed (412 `CONFIRM_SECRET_NOT_SET`) when no secret is configured.
- [ ] Dashboard create + mint modals collect and send the secret.
- [ ] Full E2E suite green (updated as above).
