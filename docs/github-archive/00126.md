## Summary

Once Slice 17 lands TOTP step-up for deletion, extend the same requirement to the other stamped operations: workspace creation and API-key minting. Same mechanism, no new subsystem.

Parent: #122

## Identity and lineage

- Parent: #122
- Depends on: Slice 17

## Research

- Slice 17 introduces a per-principal MFA record and a step-up check on `confirmGate`. Because Slice 15 routes create and mint through the same gate, this slice is primarily **applying** the Slice 17 check to the two additional routes, plus UI prompts for the code.
- Decide whether MFA is required whenever the principal has it enabled, or only for operations above a sensitivity threshold. Default: if MFA is enabled, all stamped operations require it — one rule, no policy engine.

## Proposal

*(proposal)*

1. Require a valid TOTP code on `POST /api/workspaces` and `POST /api/keys` for MFA-enabled principals.
2. Add the code field to the create/mint modals (alongside the confirmation secret from Slice 15).
3. Platform owner is **not** exempt from MFA (it protects the owner's own account too); the owner may choose to leave MFA disabled.

## Acceptance criteria

- [ ] An MFA-enabled principal cannot create a workspace or mint a key without a valid code.
- [ ] An MFA-enabled principal can do both with a valid code.
- [ ] Non-enrolled principals behave as today (secret only).
- [ ] API-key callers remain refused.

## Boundaries / non-goals

- No passkeys (separate later slice).
- No MFA requirement forced on principals who have not enrolled.

## Next action

Reuse the Slice 17 check on the two routes and add the code field to both modals.
