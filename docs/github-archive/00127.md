# Issue #127: Slice 19 — Typed multi-tenant keys (analytics / agent-read / program-write)

## Summary

Introduce key **classes** so different consumers hold different authority profiles: e.g. an analytics key that can query projections but never reach Postgres, an agent key that is read-only, and a program key that may write. Today every key is a bag of scopes (`read/write/files/delete/admin`) with no notion of consumer class.

## Research

- **Current model.** `octo.api_keys` (`supabase/migrations/20261001010000_slice2_files_and_api_keys.sql`) stores `workspace_id`, `role`, and a `scopes` array (`read/write/files/delete/admin`). `authorizeKeyMint` (`src/api/keys.ts`) enforces that a token may only narrow its own authority. `admin` is accepted at creation but **never enforced anywhere** (#61) — a latent bug this slice should resolve or remove.
- **Two possible shapes.**
  1. **Extend `scopes`** with new values (e.g. `analytics`, `sql`) and enforce them per route. Minimal schema change; reuses existing plumbing.
  2. **A `key_class` dimension** orthogonal to scopes (consumer identity: `analytics` / `agent` / `program` / `human`), with per-class default scope sets and route-level class checks. More explicit, more machinery.
- **Constraint.** Because **no client receives raw SQL** through Octo today (all access is the HTTP API; RAG `query_workspace` is retrieval, not SQL), "analytics can't reach Postgres" is already structurally true. The typed-key work formalizes distinct authority *profiles* on top of the API, and becomes load-bearing only when a provisioned-DB-per-workspace capability (#72) exists.
- **Recommendation to evaluate at build time:** start with shape 1 (extend `scopes` + enforce on the relevant routes, including finally enforcing/removing `admin`), and add a class dimension only if a concrete consumer needs it. This keeps the change minimum-sufficient.

## Proposal

*(proposal)* Define the accepted key classes and their authority profiles, map each onto enforced scopes, and enforce them on the routes that matter. Resolve the never-enforced `admin` scope as part of this.

## Acceptance criteria

- [ ] Each named key class has a documented authority profile.
- [ ] A key of class X is refused on routes outside X's profile.
- [ ] `admin` is either enforced or removed — no accepted-but-inert scope remains.
- [ ] Existing key flows (create/mint/revoke, workspace-scoped fence) still pass.

## Boundaries / non-goals

- No raw-SQL surface for clients (that is the #72 provisioned-DB question, not this slice).
- No new role hierarchy beyond what the classes require.

## Next action

Decide shape (extend scopes vs class dimension) with a one-page comparison, then implement the chosen profile enforcement.
