## Summary

Slice 18 of the robustness roadmap (issue #126). Slice 17 added a per-principal TOTP second factor and wired it into workspace deletion. This applies the same check to the other two human-stamped operations, so an MFA-enabled principal must present a current code (or a one-time recovery code) for **all** of creation, minting, and deletion.

- `POST /api/workspaces` and `POST /api/keys` pass `mfaCode` into the existing `confirmGate` with `requireMfa: true`. No new mechanism, no migration.
- The create modal, mint modal, and Access-page inline mint form render an authenticator-code input when MFA is enabled; the submit handlers forward `mfaCode`.
- Secret-only create/mint is refused `403 MFA_CODE_INVALID` when enrolled; non-enrolled principals and API-key callers are unaffected.
