# Issue #135: [SECURITY] ISS-1/ISS-2 — principal UUID is a bearer credential, and share routes disclose it (account-takeover chain)

- State: closed (2026-10-06)
- Opened by Pukujan on 2026-10-05
- Original: https://github.com/Pukujan-lab/octo-database/issues/135
- Labels: bug, plane:lead-owner, priority:p1

From the deep security audit in #134 (`docs/security/2026-10-05-deep-security-audit-issue-log.md`). These two findings are one exploit chain and should be fixed together.

## ISS-1 — raw principal UUID accepted as a bearer session token (High)

`authenticateRequest` treats any Bearer token matching `UUID_PATTERN` as a principal id and authenticates it directly, with **no secret, expiry, or revocation** (`src/server/index.ts:360-398`):

```ts
if (!UUID_PATTERN.test(token)) return null;
const rows = await queryService('SELECT ... FROM octo.principals WHERE id = $1', [token]);
if (rows.length === 0) return null;
bindRequestIdentity(pRow.id, null);
```

The principal's primary key *is* the credential — issued as the session token by guest login (`sessionToken: principal.id`, `index.ts:958`) and by the Google callback (`#token=${principal.id}`, `index.ts:905`).

Because `requireScope` returns `true` when no API key is present (`index.ts:585-588`), a UUID session also bypasses every scope check and carries the principal's full role.

Disclosure channels are real, not hypothetical: `signMediaUrl` writes `principalId` into the media-URL query string for principal-scoped tokens (`src/media/media-token.ts:78-79`), so every authenticated gallery media URL carries the viewer's UUID into browser history, `Referer` headers, and proxy/CDN logs.

## ISS-2 — share routes disclose the creator's principal UUID (High)

`dbListShares` / `dbInsertShare` return `created_by AS "createdBy"`, and both share routes serialize it (`db.ts:686-719,775-787`; `index.ts:2246-2250,2285-2286`). `createdBy` is not needed by any client.

## The chain

1. An admin lists a workspace's shares (`GET /api/workspaces/shares?workspaceId=...`) and reads the creator's principal UUID.
2. They replay it as `Authorization: Bearer <uuid>` — full, permanent impersonation of that principal (possibly the workspace owner or platform owner) across every workspace that principal belongs to.

## Fix

- **ISS-1 (root cause):** stop using the primary key as a bearer secret. Issue a signed, expiring, revocable session token (HMAC over `{principalId, exp}` with a server secret, or a `sessions` table) and validate that on the session path. Separately, stop emitting the principal UUID as a visible media-URL parameter — sign an opaque nonce or keep the id inside the HMAC payload only.
- **ISS-2:** strip `createdBy` from all client-facing share payloads. Map rows to an explicit response shape (`id, tokenPrefix, permission, validFrom, validUntil, revokedAt, accessCount, lastAccessedAt`) rather than spreading the DB row.

ISS-2 alone is a data-hygiene fix; ISS-1 is the load-bearing one — without it, a leaked UUID is not a credential.

## Out of scope for this issue

ISS-3 (thumbnail share→principal token upgrade), ISS-4 (job payload trust), ISS-5 (MFA recovery-code race), ISS-6 (hardcoded owner email), ISS-7 (dead `verifyApiKey`) are separate findings in the same log.

**Pukujan commented, 2026-10-06**

Fixed in #146 (auto-merge armed).

- **ISS-1**: session tokens are now an HMAC-signed, expiring envelope (`octo_sess_<id>.<exp>.<sig>`) minted at guest/OAuth login; a raw principal UUID is no longer accepted as a bearer credential.
- **ISS-2**: the share create/list responses no longer carry the creator's principal id.

New `OCTO_SESSION_SECRET` signs the tokens (per-process fallback when unset). Verified with tsc, 269 vitest, and 74 Playwright tests; the raw-UUID red test was confirmed against the pre-fix branch.

**Pukujan commented, 2026-10-06**

Resolved. ISS-1: session tokens are signed with `OCTO_SESSION_SECRET` and the raw principal UUID is no longer a credential (`src/server/auth` signed-token path); ISS-2: share create/list responses omit `createdBy` and any principal id.
