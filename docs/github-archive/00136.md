# Issue #136: [ROBUSTNESS] Workspace-creation daily limit is a check-then-act race (parallel creates bypass it)

- State: closed (2026-10-06)
- Opened by Pukujan on 2026-10-05
- Original: https://github.com/Pukujan-lab/octo-database/issues/136
- Labels: bug

Found by a local red-team/chaos probe driving the real HTTP API against an isolated database (not a unit test).

## Defect

The Slice 16 workspace-creation limit (1 per rolling 24h, `src/server/index.ts:1284-1295`) is a **check-then-act race**. The route counts the principal's created workspaces, then separately inserts a new one:

```ts
const createdLastDay = await dbCountCreatedWorkspacesSince(auth.principal.id, cutoff);
if (createdLastDay >= 1) { /* 429 */ }
...
const workspace = await dbCreateWorkspaceAtomic({ ... });
```

Two concurrent requests from the same principal can both read `createdLastDay === 0` and both proceed, minting **two** workspaces.

## Evidence

A fresh principal fired six parallel `POST /api/workspaces` (all with a valid confirmation secret):

```
statuses = [201, 429, 201, 429, 429, 429]   # 2 created, 4 limited
```

Expected: exactly one `201`, five `429`. Observed: two `201`.

## Contrast

The one-account-wide-key rule held correctly under the same concurrency (five parallel mints → `201=1, 409=4`) because a partial unique index enforces it in the database. The daily limit has no engine-level backstop, so it races.

## Impact

A principal (or a compromised browser session holding the confirmation secret) can exceed the intended workspace-creation rate by issuing parallel requests. Rate-limit bypass, not an authorization bypass.

## Suggested fix

Make the count and the insert atomic — e.g. take a per-principal `pg_advisory_xact_lock` before the count inside the same transaction that inserts the workspace, or add an engine-level constraint on the creation window. Keep it minimal; no new process or gate.
