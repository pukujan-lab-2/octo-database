## What this is

A single operational-events layer inside the existing Octo Postgres (`octo` schema): capture structured failures where they already happen, classify them with SQL views, and perform one deduplicated auto-heal through the existing job queue. No new database, no scheduler, no analytics engine, no graph store.

**Reality check on the framing.** Most of the named tools are the wrong layer for this repo and are rejected below. What is real: capture, SQL views, one deduped remediation, HTTP read-back. What is aspirational and deferred: graph diagnosis, Parquet history, multi-node telemetry.

## Architecture

`octo.ops_events`, one new append-only table in the existing `octo` schema. Written from exactly the two places failures are already caught: the outer 5xx handler (`src/server/index.ts`) and the worker fail/exception path (`src/jobs/worker.ts`). 4xx refusals are normal product behavior and are not captured.

Columns: `id`, `workspace_id UUID NULL` (nullable so platform-level errors — auth failures, pre-workspace 500s — are recordable), `source` (`api`|`worker`), `event_type`, `error_code`, `severity`, `detail JSONB`, `job_id`, `route`/`job_type`, `created_at`. FK to `octo.workspaces` `ON DELETE CASCADE` for workspace-scoped rows; SELECT restricted to the platform owner for null-workspace rows. Unbounded growth is accepted at current scale; revisit only if measurement shows a limit.

"Deterministic states" means: **no new state machine**. The state machine is `octo.jobs`' existing CHECK enum and its transition functions. Diagnosis is SQL views over `ops_events`; repair is the existing `POST /api/jobs/:id/retry`; auto-heal is one remediation job type whose enqueue is deduped by the existing `idempotency_key`.

### O3 — One auto-heal
One remediation job type for one known retryable class, enqueued with a deterministic `idempotency_key` derived from the failing job. Success check: force the same failure twice, assert exactly one remediation job exists; assert a remediation job that itself lands in `failed` enqueues nothing (no recursion).

## O1 packet

**PDD**
- User/actor: the platform owner (later an agent acting for the owner) diagnosing why something failed.
- Job: see the structured record of recent failures — what failed, where, with what code — without reading raw logs.
- Why: today a 5xx leaves only a log line; there is no queryable record, so operational improvement has nothing to build on.
- In scope: an `octo.ops_events` table; capture from the two existing failure sites; `GET /api/ops/events` read-back filtered by workspace and error code.
- Out of scope: dashboards, alerting, tracing/OTel, metrics, a scheduler, retries beyond the existing queue, any second observation system, 4xx capture, graph/Neo4j, Parquet/DuckDB, a state-machine framework.
- Reuse: the `octo.activity` write pattern (`recordActivity`, service pool) and the `GET /api/activity` read pattern; the RLS fence convention; the existing job queue for later repair.
- Observable success: a forced failing job and a forced route throw each produce exactly one correctly-shaped row, readable via `GET /api/ops/events`.

**SDD**
- Authority/canonical state: `octo.ops_events` in the existing Postgres; append-only.
- Capabilities: `read` (list ops events for an authorized workspace).
- API contract: `GET /api/ops/events?workspaceId=<id>&errorCode=<code>` -> `{ events: [...] }`.
- Provider/data flow: Postgres only. R2/Drive/DuckDB/Neo4j do not participate.
- Client surfaces: HTTP/JSON; SDK/CLI/MCP may follow later.
- Existing code reuse: `db.ts` service-pool helpers; the activity route as the template.
- Failure boundary: the writer must never break the request path (best-effort, like `attributeAgentAction`); capture failures are swallowed.

**EVAL/TDD**
- Public deterministic: migration applies; `recordOpsEvent` writes a correct row; the read route returns it and filters by workspace/error code.
- End-to-end: force a failing job via the existing drain harness and assert one row; a throwing test route asserts one row.
- Metamorphic/property: the same failure recorded twice yields two rows (append-only, no upsert); a null-workspace event is not visible to a non-owner principal.
- Hidden holdout: none.
- Production smoke: `curl` the read route against the deployed candidate and see a seeded row.

## Rejected alternatives

| Option | Why rejected |
|---|---|
| DAX / Power BI semantic layer | Power BI's expression language over a tabular model; Octo has no semantic model or Power BI deployment. Plain SQL views are the right analytics surface. |
| Dagger / DAG engine / scheduler | A container/CI execution layer and a distributed scheduler. `octo.jobs` is already the deterministic executor; a second is the machinery AGENTS.md rules 6/8/10 forbid. |
| State-machine framework (e.g. XState) | The state machine already exists as `octo.jobs`' CHECK enum + transition functions. A framework is a second source of truth. |
| OTel / OpenObserve now | Real but owned by #14 checkpoint 4; adopt there with evidence, not speculatively here. |
| Cedar / SMT policy layer | Wrong layer for an error log; no policy decision is being made. |
| Neo4j / graph diagnosis | Different projection (#12). The JSONB detail + event/error codes are the substrate; project later if warranted. |
| Import hades-v2's hash-chained ledger | Prior art for how the owner thinks about observations, but importing it creates a second observation system (rules 6/8/10). |
| A second observation table replacing `octo.activity` | `octo.activity` is the human-readable projection and stays; `ops_events` is a structured complement. |

`ops_events` grows without bound at current scale (a personal/small-team platform). Retention/partitioning is deferred until measurement shows a limit — the same posture as other tables.

### O3 — ops summary route

- **Goal:** the O2 views become readable over HTTP: `GET /api/ops/summary?workspaceId=` returning failure counts, per-job-type daily counts, and unhealthy jobs.
- **Files:** `src/server/db.ts` (one `dbGetOpsSummary(workspaceId)` reading the three views via the fenced `query()`); `src/server/index.ts` (one route copied from the `/api/ops/events` block at `:2682-2713`); `src/api/capabilities.ts` (one `ops.summary` entry, `requiredScope: 'read'`).

### O4 — agent diagnose and repair via MCP

- **Goal:** an agent can read failures and retry a failed job without a human.

- **Verification:** extend `tests/unit/mcp-server.test.ts` — tools are listed; `retry_job` moves a seeded `failed` job to `queued`; wrong-workspace call is refused.
- **Non-goals:** no new tables, no auto-triggering, no notification, no type filtering on retry, no autonomous repair loop.
- **Reuses:** `ops.list` route, O3 route, `POST /api/jobs/:id/retry` → `dbRetryJob`, existing key scopes.
- **Risk:** `retry_job` is a write surface. It inherits `requireScope('write')` from the existing route, so a read-only agent key cannot call it — verify the test asserts that, since it is the one place an agent gains a repair action.

## Verdicts on the named ideas (planner pass)

- **"DAX or something"** — answered: Postgres is the analytics engine and the three O2 `security_invoker` views are the measures. The remaining gap is *exposure*, not machinery: no HTTP route, no MCP tool, and `src/main.ts:220` renders only `/api/jobs` + `/api/activity`, while `src/api/capabilities.ts:118` exposes only `ops.list`. O3 closes it. No BI tool, no DAX import, no second database.
- **State machines** — already satisfied, zero work. `octo.jobs` has the CHECK enum, `claim_job()` as the single transition point, lease expiry as the reclaim signal, exponential backoff in `dbFailJob` (`src/server/db.ts:1060`), and `attempt`/`max_attempts`. A second state machine would duplicate it.
- **Auto-heal** — mostly shipped: dead workers self-heal via lease reclaim; transient failures retry with backoff; terminal failures have a deterministic repair (`POST /api/jobs/:id/retry` → `dbRetryJob`, which requeues any `failed` job — the archive/restore branch at `db.ts:965` is a busy-guard, not a type restriction). O4 is *plumbing to existing repair*, not new healing logic. No autonomous healer, no repair-policy table.
- **Graph engineering** — rejected as an engine (no engine inherits the `octo.*` RLS fence; see `docs/research/2026-10-05-scaling-data-engines.md`). As a SQL projection: **defer** — the only edge that exists is `ops_events.job_id → octo.jobs` (one hop), already joined by `ops_unhealthy_jobs`; with three job types there are no chains for `WITH RECURSIVE` to traverse. If ever asked again, the answer is one `security_invoker` view with a recursive CTE — zero new service — but it solves no accepted workflow today. *(This is the ops-diagnosis graph only; the research GraphRAG graph for agent knowledge work is a separate question.)*
- **DAG / Dagger task graphs** — speculative → defer. No accepted workflow needs one job to wait on another; `thumbnail`, `archive_file`, `restore_file` are independent file-scoped transitions. Minimal shape if it ever materializes: an `octo.job_dependencies` table plus one extra predicate in `claim_job`'s SELECT. Do not build it now.
- **Pydantic-style validation** — reject. Hand-rolled boundary validation is the established server pattern; zod appears only via the MCP SDK. Adding a validation library to the server is an unsolicited abstraction with no defect behind it.

## Retention (posture, no change)

`octo.ops_events` is append-only and unbounded, exactly like `octo.activity`, and captures failures only at single-digit workspaces — years of growth at megabyte scale. If the owner wants a knob, the minimal form is one `DELETE ... WHERE created_at < now() - interval` inside the existing hourly tick in `startSchedulers()` (`src/server/index.ts:599`), about five lines. Offered, not built.
