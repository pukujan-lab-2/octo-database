## Summary

Fixes **ISS-4** from the 2026-10-05 deep security audit (tracked by #142).

`handleThumbnailJob` read `storageKey` and `mimeType` straight from the
client-supplied job payload. A workspace member could therefore enqueue a
thumbnail job pointed at another tenant's object key — a confused-deputy read —
and the derivative was written to a key addressed only by `fileId`, allowing
cache poisoning of a derivative the caller does not own.

- The handler now resolves the file through the trusted service pool
  (`dbGetArchiveRecord`), **pinned to the job's workspace**, and uses the
  record's object key and MIME type. The payload supplies only the file id.
- A missing file is a benign no-op; a payload without `fileId` fails permanently.
- This matches the on-demand `GET /api/files/thumbnail` route, which already
  resolved the record rather than trusting the caller.
