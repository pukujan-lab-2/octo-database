## Summary

Closes the three remaining confirmed findings from the 2026-10-05 deep security audit (issue #142). ISS-4 shipped in #143 and ISS-5 in #139.

- **ISS-3 (MED-HIGH)** — `GET /api/files/thumbnail` minted a **principal-scoped** media redirect from a share-token path, so a logged-out share holder received a URL carrying the creator's principal UUID with a fresh 1h TTL. The fallback now stays **share-scoped** and is capped at the share's own expiry, so revoking or expiring the link also kills the media URL. (`src/server/index.ts`, `src/server/db.ts`)
- **ISS-6 (MEDIUM)** — Platform-owner authority was granted by matching a personal address baked into public source. Ownership now depends solely on `PLATFORM_OWNER_EMAIL`, so the privileged identity is no longer published and can be rotated via configuration. (`src/server/db.ts`)
- **ISS-7 (LOW)** — Deleted the dead `verifyApiKey` in `src/api/keys.ts`, which retained an unscoped by-hash lookup. The server verifies keys through `dbVerifyApiKey` (RLS-fenced + expiry); one path now remains.

## Deployment note (ISS-6)

Any deployment that relied on the literal must now set `PLATFORM_OWNER_EMAIL`. The mechanism already existed; no in-repo env or test depended on the literal.
