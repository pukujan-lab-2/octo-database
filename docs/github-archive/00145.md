## Summary

Slice O2 of the operational-event plan in #140. O1 (#141) captures structured failures into `octo.ops_events`; O2 makes that record queryable for "operational and data analytics" with three read-only views — no new table, route, or scheduler.

- `octo.ops_failure_counts` — failures grouped by `error_code` per workspace, with `event_count`, `first_seen`, `last_seen`.
- `octo.ops_failures_by_job_type_day` — failure counts by `job_type` and day.
- `octo.ops_unhealthy_jobs` — terminal `failed` jobs plus `running` jobs whose lease expired (the same condition `claim_job` treats as reclaimable).

## Security: `security_invoker`

Each view is declared `security_invoker = true` (PG 15+; CI is pg16). A plain definer view owned by the migration role would silently read **every** workspace's rows, bypassing the member/platform-owner policies and the slice-14 tenant fence on the underlying tables. With `security_invoker`, a caller's own RLS context applies.

## Test plan

`tests/e2e/ops-classification-views.spec.ts` seeds a known row set and asserts:
- aggregation correctness as the schema owner (counts, day grouping, unhealthy-job set)
- **the fence**: a workspace-scoped `octo_app` read through a view sees only its own workspace's rows, and a non-member sees none

Verified as a true red test: flipping `security_invoker` off makes the scoped read leak the other workspace's rows (3 → 5) and the spec fails.
