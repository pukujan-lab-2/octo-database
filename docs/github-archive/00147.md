## What this is

A placeholder for a future Kubernetes-based scaling posture for Octo:
- additional **load balancers** in front of more than one API node;
- **extra compute** for workers / background jobs;
- additional **server pods** so the HTTP/JSON API can run horizontally.

This is the container-orchestrated expression of the "multiple API nodes" stage that
#14 (Slice 12) already owns as a deliberate, evidence-gated scale path. #14 is the
authority on *when* scaling is justified; this issue is the future record of *what*
the Kubernetes-shaped answer would look like once that gate is met.

## Preconditions before this becomes executable

Per #14's scope control, these must be true first:
- the single-node path is useful and **measured** (DB connection pressure, job-queue depth);
- the API is already stateless enough to run a second node;
- a demonstrated load or availability need exists — not a synthetic scale target.

## Explicitly out of scope for now

- Any Kubernetes manifests, Helm charts, operators, or cluster provisioning.
- Managed-load-balancer or ingress configuration.
- A container registry / image pipeline change.
- Autoscaling policy, service mesh, or multi-region.
