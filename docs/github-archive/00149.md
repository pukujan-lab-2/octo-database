### Human-Understandable Summary

An agent working in an adopter repository (`personal-branding-project`) was directed by the repository owner to move that project's analytics off a local SQLite file onto "Postgres/pgvector or whatever Octo offers, including its DuckDB and Parquet for analytics". A capability check of this repository found that **none of that is present**.

What Octo actually exposes to a client: workspace identity and membership, file/object storage (upload, download, restore, thumbnails, gallery), a background jobs queue (`enqueue`/`run`), activity and operational-event feeds, and pgvector-backed **retrieval over documents a client ingests**. What it does not expose: DuckDB, Parquet, and any client-facing SQL, table, or query surface over workspace data. A client-facing raw-SQL surface is explicitly recorded as out of scope. pgvector does exist, but as Octo's own retrieval index — not as a general analytics engine a client can query.

**Consequence:** anyone who reads the stack's direction as "Octo is where the analytics live" will design against a capability that is not there, and will only discover it after building ingestion around a store that cannot answer the queries. That happened once already, in the session that produced this record. **Affected:** adopters of the stack who plan storage from the roadmap direction, and anyone reasoning about Octo's own roadmap who assumes an analytics/query tier is part of Octo rather than a separate store.

This is filed as a scope-clarity observation, not a defect report. Octo's own framing ("a self-hosted control plane") is accurate; the gap is that the boundary is easy to over-read.

2. **Enumerate every route in `src/server/index.ts`** → `workspaces`, `files` (+`content`/`download`/`thumbnail`/`upload`), `gallery`, `jobs` (+`run`), `keys`, `me` (+`mfa`), `activity`, `ops/events`, `shares`, `rag/documents`, `rag/query`, `auth`. 3. **Read the declared capability catalog** (`src/api/capabilities.ts`) → workspaces / files / gallery / jobs / activity / ops. No analytics or query capability.
4. **Live check** — `GET /api/capabilities` with a workspace-scoped key (`program-write` class: scopes `read`, `write`, `files`) returns `contractVersion: 1`, 11 capabilities, and `unavailable: []`. No analytics/query capability is offered or withheld; it does not exist.
5. **Retrieval is not currently usable either** — `POST /api/rag/query` returns `503 EMBEDDING_PROVIDER_NOT_CONFIGURED`, i.e. the server needs `OCTO_EMBEDDING_API_KEY` set before the one query-shaped surface works at all.

### Non-Binding Proposed Next Actions

*(proposal)* — none of the following exists today; each is a suggestion, not an implementation mandate.

- [ ] State the scope boundary explicitly in `README.md` / `docs/PDD.md`: Octo is a control plane — identity, files, jobs, and retrieval. It is not an analytics or query database, and clients receive no SQL surface.
- [ ] Where the roadmap implies an analytics tier, **name the separate store** rather than leaving it implied as an Octo feature, so adopters are not left to infer one.
- [ ] Document for adopters that each adopter keeps its own analytics store, and that Octo's role is artifact storage, job execution, and retrieval over ingested documents.
- [ ] If a provisioned-DB / query tier is genuinely wanted, open a design issue for it and link it from the scope statement, so the boundary is intentional rather than accidental.
