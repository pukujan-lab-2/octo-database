## Summary

- `deploy.sh` built and started the API without ever applying migrations, so a deploy could run new code against an old schema. That is the drift that left production missing slices 16/17/18 + ops views and 500-ing on `/api/me` after Google login.
- Adds `deploy/gravebuster/migrate.sh`: applies `supabase/migrations/*.sql` in lexical order and records each in `octo.schema_migrations`. Each migration runs in one transaction together with its tracking insert, so a failure leaves neither a half-applied migration nor a false "applied" row. Migrations already recorded are never re-run — required, since several use plain `CREATE POLICY` and are not idempotent.
- `deploy.sh` now starts `octo-db`, waits for `pg_isready`, runs `migrate.sh`, and only then starts the API. A migration failure aborts the deploy before any container swap.
- The Postgres init scripts record what they apply, so a freshly-initialized database is seen as current and the first deploy finds nothing to do.
- `MIGRATE_BASELINE=1 ./migrate.sh` adopts an existing database that predates tracking (records every present migration as applied, runs none) — a documented one-time step.
- CI gains an idempotence check: baseline the already-applied migrations, assert the count matches, then run again and assert nothing is applied.
- `docs/self-hosting.md` documents all of the above.
