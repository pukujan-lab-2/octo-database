## PDD

**User/actor:** The owner (and agents the owner hands Octo credentials to) who wants to stand up a real, independently connectable Postgres database for a project, addressed through an Octo workspace.

**Job:** Given a workspace, the owner (via API key, SDK, or MCP tool) provisions one real PostgreSQL database belonging to that workspace, receives its connection string, and connects to it directly with an ordinary Postgres client to create and use their own tables.

**Why:** The enabling capability for the owner's keys-to-agents intent, and what makes "my projects can start using octo db for postgres" true.

**Honest isolation story (read before accepting):**
- The per-workspace LOGIN role is **not a master credential and not a platform credential**: `NOSUPERUSER NOCREATEDB NOCREATEROLE`, `CONNECT` on its own database only. It **is** the owner of its own database, so inside that database it can do anything to its own data — that is the feature.
- The slice14 `tenant_scope_fence` / RLS machinery does **not** exist and will not be re-implemented inside provisioned databases. Isolation is the database boundary plus the scoped role. Full stop.
- This slice **deliberately creates one exception** to the invariant that agents hold only Octo API keys and never raw credentials (`AUTH_GUIDANCE`, `src/api/capabilities.ts:213`): the client of a provisioned DB holds a raw Postgres credential — for its own database only. It gets no Octo control-plane credential, and that credential cannot read `octo.*`.
- Provisioning needs a privileged connection that can `CREATE DATABASE` and `CREATE ROLE` cluster-wide (`OCTO_ADMIN_URL`). The current `octo_app`/`octo_service` roles deliberately cannot (`NOCREATEDB`, `slice14:31-38`). This is a new, larger trusted surface than `servicePool`; the provisioning module is its single grep-able boundary.
- Provisioned DBs on the same instance share CPU/RAM/disk and the `max_connections` budget with the control plane. Accepted posture (see sub-decision 1); this slice adds no pooling or resource limits.

**In scope:**
- Migration creating the `octo.workspace_databases` catalog, RLS-fenced in the same migration.
- A provisioning module behind the privileged connection: `CREATE ROLE` + `CREATE DATABASE` + ownership, synchronous in the request.
- One API route: `POST /api/workspaces/{id}/database`, returning the connection string exactly once.
- Capability-catalog entry, AUTH_GUIDANCE correction, activity event, MCP tool, SDK method.

**Out of scope (must not be added):**
- `DROP DATABASE` / deprovisioning / credential reset or re-view routes (a lost password is reset out-of-band by the owner).
- Connection pooling / PgBouncer / per-workspace connection caps; HA, replicas, clustering.
- A migration runner for client schemas — **the client owns its migrations** (pending sub-decision 2).
- RLS or any `octo.*`-style policy machinery inside provisioned DBs.
- Resource quotas, monitoring, size limits, lifecycle states beyond `active`.
- Provision-on-workspace-create (provisioning is an explicit, separate call).

**Reuse:** `pg` driver/pool idioms (`src/server/db.ts`); rawSecret-shown-once pattern (`src/server/index.ts:1339`, `:2126`); the auth chain (`authenticateRequest` / `requireScope` / `keyWorkspaceMatches` / membership); capability catalog + MCP adapter; server-side name derivation (`src/lib/provisioning-slug.ts`); env-template precedent.

**Observable success:** The owner calls the route on a workspace with an account-wide key, receives `connectionString` once, connects with a plain `pg` client, creates a table and inserts rows. A second call returns 409 and no second database/role exists. The credential cannot connect to any other workspace's database or to the `octo` control database. The same flow works through the MCP tool.

## SDD

**Authority/canonical state:** `octo.workspace_databases` is the canonical catalog (id, workspace_id, db_name, role_name, status, created_by, created_at, updated_at). The databases and roles are canonical in the Postgres cluster; the password is **never persisted** — it exists only in the once-returned connection string. The catalog is a tenant table like any other.

**Capabilities:** New `workspaces.provision_database`, `requiredScope: write`. Requires an **account-wide** key or human session; workspace-scoped keys rejected (403), same rule as workspace creation. Membership check applies (platform owner exempt). No confirmGate — provisioning is additive and creates nothing destructive.

**API contract:**
- `POST /api/workspaces/{id}/database` → `201 { database: { id, workspaceId, dbName, roleName, status, createdAt }, connectionString }`. `connectionString` returned **exactly once**.
- `409 DATABASE_EXISTS` when the workspace already has one (exactly one database per workspace).
- `403` workspace-scoped keys / non-members; `401` unauthenticated; `404` unknown workspace.
- Activity event `workspace.database_provisioned` (no secret in the event or any log).
- `db_name` / `role_name` **server-generated** from the workspace slug + short unique suffix and passed to DDL as quoted identifiers — `CREATE DATABASE`/`CREATE ROLE` cannot be parameterized, so the module interpolates only server-derived, validated names. Never accepted from the request body.

**Provider/data flow:** New module (e.g. `src/server/provisioning.ts`) holding a dedicated privileged pool from `OCTO_ADMIN_URL`. Per provision, autocommit (`CREATE DATABASE` cannot run in a transaction): `CREATE ROLE <role> LOGIN PASSWORD '<generated>' NOSUPERUSER NOCREATEDB NOCREATEROLE` → `CREATE DATABASE <db> OWNER <role>` → insert catalog row → build connection string → return it. The client role owns its database, so it can create schemas/tables and run its own migrations. `OCTO_ADMIN_URL` added to both `.env.example` files (values set out-of-band, never committed).

**Client surfaces:** MCP tool `provision_database` (forwards only) and an `OctoApi` SDK method (`src/mcp/client.ts`). No frontend surface in this slice.

**Existing code reuse/replacement:** New migration; new provisioning module; new route block in `src/server/index.ts` following the existing pattern; new `OCTO_CAPABILITIES` entry; one-line `AUTH_GUIDANCE.note` correction; new MCP tool + SDK method; `dbRecordActivity` for the event. Nothing existing replaced.

**Failure boundary (in scope):** name collision (regenerate/retry or fail clearly); provisioning failure mid-sequence (catalog row written last, so a failed CREATE leaves no catalog row; an orphaned db/role without a catalog row is an owner-visible anomaly resolved manually — no janitor); duplicate provision (409); `OCTO_ADMIN_URL` misconfigured (500, captured by the existing ops-event path). Nothing beyond this.

## Open questions for the owner

1. **Sub-decision 1 — same instance or separate Postgres instance?** **Recommendation: same instance for this slice.** Minimum change (no new service to deploy/back up/monitor); the scaling research notes same-host database-per-tenant gives genuine data separation while sharing CPU/RAM/disk — acceptable at single-digit workspaces. A separate instance is the upgrade path when a workspace needs true resource independence; the catalog's host fields make that a later change, not a rewrite.
2. **Sub-decision 2 — who runs the client's schema migrations?** **Recommendation: the client, via its own role.** The role owns its database, so the client connects and runs its own DDL; Octo builds no migration runner and stores no client schema knowledge. The alternative requires a new migration subsystem — out of scope.
3. **Optional gate check (recommend: nothing).** Workspace creation is human-gated; DB provisioning also consumes disk/connection budget, but the specified surface is an account-wide key without confirmGate. If the owner wants a human gate or a count quota here, say so at acceptance.
4. **Confirm the AUTH_GUIDANCE change** — this slice makes one deliberate exception to "tokens never expose database credentials." The one-line correction ships with the slice.

**Pukujan commented, 2026-10-06**

**Implemented — PR #155** (auto-merge armed on `main`).

Built the packet as specified, with one design correction the live cluster forced.

**What shipped**

- Migration `20261001130000_provisioned_databases.sql`: `octo.workspace_databases`, one row per workspace, server-generated `db_name`/`role_name`, the slice14 RESTRICTIVE tenant fence added in the same migration (the fence list is hardcoded and does not cover later tables), no credential column.
- `src/server/provisioning.ts`: the single grep-able privileged boundary (`OCTO_ADMIN_URL`). Role is `NOSUPERUSER NOCREATEDB NOCREATEROLE` and owns only its own database; `CONNECT` revoked from PUBLIC there.
- `POST /api/workspaces/:id/database` → `201 { database, connectionString }` once; `409` on a second call; refused to workspace-scoped keys; `workspace.database_provisioned` activity event that does not carry the credential.
- Capability, MCP tool, SDK method, env templates.

**Correction to the packet's isolation story**

The packet implied the credential would be refused a connection to the control database. Empirically it is not: every role inherits PUBLIC's `CONNECT`, and revoking that from PUBLIC would break `octo_app`/`octo_service`. Confinement is therefore **privilege-based, not connection-based** — the role holds no `USAGE` on the `octo` schema and no table grants, so every `octo.*` read and write is refused as a privilege denial. `REVOKE CONNECT ON DATABASE <control>` was removed as ineffective, and the verification asserts the privilege boundary instead. This is recorded in the module header and the migration comment.

**Verification**

- `scripts/verify-provisioned-database.ts` against the local cluster: all checks pass — two databases, role attributes, ownership, credential runs DDL+DML in its own DB, no `octo` USAGE, `octo.workspaces` read and write refused, cross-workspace connect refused. Now a `gates` step.
- End-to-end over HTTP: 17/17 (401/404/400 paths, first-provision 201, plain `pg` client `CREATE TABLE`/`INSERT`/`SELECT`, 409, distinct names, cross-workspace refusal, activity event with no leaked credential).
- `npm test` 289 passed, Python 89 passed, typecheck/ruff/mypy clean.

Open questions 1–4 in the packet are resolved by the implementation as recommended: same instance (the admin connection is the same cluster), the client runs its own migrations, the live-cluster check is in `gates`, and the `AUTH_GUIDANCE` change is in with the exception recorded.

**Follow-up PR #156 — the database is now vector-ready.** pgvector turns out **not to be a trusted extension**; verified against the production image:

```
$ psql "postgresql://probe_rw:.../probe_db" -c "CREATE EXTENSION IF NOT EXISTS vector;"
ERROR:  permission denied to create extension "vector"
HINT:  Must be superuser to create this extension.
```

A provisioned role is `NOSUPERUSER`, so a workspace could never enable it itself — and the owner's direction (#149) is explicitly "Postgres/pgvector". Provisioning now enables `vector` in the new database over the privileged connection, best-effort so a cluster without the extension still provisions a plain database. Verified against `pgvector/pgvector:pg16`: the credential's database is vector-ready and a `vector(3)` column with a `<->` nearest-neighbour query works, without the workspace holding the privilege to enable the extension.

**One deployment step remains** (recorded on #155): `octo-db` publishes no host port and sits only on `octo_internal`, so a provisioned database is reachable in-network only. Making it reachable from a project on another host is either a published port or a route through the existing Cloudflare Tunnel — an infrastructure decision, left to the owner. `OCTO_DB_PUBLIC_HOST`/`OCTO_DB_PUBLIC_PORT` is the seam.
