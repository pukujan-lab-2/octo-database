## Summary

A workspace can now own a **real PostgreSQL database**, created in the cluster and connectable by the owner's own client with an ordinary `pg` connection. This closes the gap that made Octo usable only as a control plane: a project can now point its analytics/application data at Octo and get a genuine database, not a logical boundary.

Closes #153.

## What changed

- **Migration** `20261001130000_provisioned_databases.sql` — `octo.workspace_databases`, one row per workspace (`workspace_id` UNIQUE), server-generated `db_name` / `role_name`, and the same `RESTRICTIVE tenant_scope_fence` as every other tenant table (the slice14 fence list is hardcoded and does not cover tables created later, so this migration adds it). **No credential column** — the password exists only in the connection string returned once.
- **`src/server/provisioning.ts`** — the single grep-able privileged boundary. `CREATE ROLE … NOSUPERUSER NOCREATEDB NOCREATEROLE`, `CREATE DATABASE … OWNER`, `REVOKE CONNECT … FROM PUBLIC`. Identifiers are server-derived, pattern-validated and quoted; nothing from a request body reaches a statement. `CREATE DATABASE` cannot run in a transaction, so statements are autocommit and the catalog row is written by the caller only after all of them succeed.
- **`POST /api/workspaces/:id/database`** — provisions, records the catalog row, records a `workspace.database_provisioned` activity event, and returns `{ database, connectionString }` **exactly once**. Refused to workspace-scoped keys; `409` on a second call; additive, so no confirmation gate.
- **Client surfaces** — capability `workspaces.provision_database`, MCP tool `provision_database`, SDK method `OctoApi.provisionDatabase`.
- **`AUTH_GUIDANCE`** — now records the one deliberate exception to "tokens never expose a database credential", and the stale KEY_CLASSES claim that no class exposes a SQL surface is corrected.
- **Env templates** — `OCTO_ADMIN_URL` (the privileged credential) plus optional `OCTO_DB_PUBLIC_HOST` / `OCTO_DB_PUBLIC_PORT`. Unset leaves the route failing with `PROVISIONING_NOT_CONFIGURED`.

## Isolation, honestly

Confinement is **privilege-based, not connection-based**. A minted role *can* open a session against the control database — PUBLIC holds CONNECT there and revoking it from PUBLIC would break `octo_app`/`octo_service` — but it holds **no `USAGE` on the `octo` schema** and no table grants, so every `octo.*` read and write is refused with a privilege denial. Isolation from other workspaces is the database boundary: `CONNECT` is revoked from PUBLIC on the provisioned database.

**Pukujan commented, 2026-10-06**

**One deployment step remains for the feature to be usable off-host** (code side is complete; this is infrastructure, not implementation).

The minted connection string points at `OCTO_DB_PUBLIC_HOST`/`OCTO_DB_PUBLIC_PORT`, defaulting to the admin connection's endpoint. In `deploy/gravebuster/docker-compose.yml` the `octo-db` service publishes **no host port** and sits only on the internal `octo_internal` network, so today only in-network clients can reach a provisioned database. The edge overlay (`docker-compose.edge.yml`) joins the `study-os_edge` Cloudflare Tunnel network, which is how the API/UI are reached.

Two ways to make provisioned databases reachable, both owner decisions because they change what is exposed:

1. **Publish a host port** — add `ports: ["${OCTO_DB_PUBLIC_PORT:-5432}:5432"]` to `octo-db`. Simplest; relies on the host firewall, since Postgres would then listen on the host's interface. Per-workspace credentials are already scoped and 32-char generated, so this is the platform-default model.
2. **Route through the existing tunnel** — attach `octo-db` to `study-os_edge` and add a Cloudflare TCP route to it, so no host port is opened. Fits the current edge, but needs tunnel-side configuration.

I have not changed the compose files, since exposing Postgres is an infrastructure decision rather than part of the slice's code. `OCTO_DB_PUBLIC_HOST`/`OCTO_DB_PUBLIC_PORT` is the seam either way — set them to whatever the chosen path resolves to and the returned connection strings follow.
