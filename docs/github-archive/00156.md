## Summary

Follow-up to #155 (Slice 20). A provisioned workspace database is now **vector-ready**: provisioning enables the `vector` extension in the new database over the privileged connection.

## Why

pgvector is **not a trusted extension**. Verified against the production image (`pgvector/pgvector:pg16`, pgvector 0.8.7):

```
$ psql "postgresql://probe_rw:.../probe_db" -c "CREATE EXTENSION IF NOT EXISTS vector;"
ERROR:  permission denied to create extension "vector"
HINT:  Must be superuser to create this extension.
```

A provisioned role is `NOSUPERUSER`, so a workspace could never enable it on its own. The owner's direction is explicitly "Postgres/pgvector" (#149), so without this a project moving onto Octo would get a database it could not do vector search in — the very capability the platform's own retrieval tier (Slice 8) is built on.

## Change

- `enablePgvector()` connects to the freshly created database as the admin and runs `CREATE EXTENSION IF NOT EXISTS vector`. **Best effort** — a cluster without the extension still provisions a plain database, so provisioning does not depend on an optional extension.
- The live check (`scripts/verify-provisioned-database.ts`) asserts vector-readiness **only where the cluster offers the extension**, so it is meaningful against the production image and does not fail on a bare Postgres.
