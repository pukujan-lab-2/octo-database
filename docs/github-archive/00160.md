# Issue #160: [BUG] Mobile: cannot switch or confirm workspaces after login; workspace-create dialog has no confirmation-secret help and does not auto-close

- State: closed (2026-10-06)
- Opened by Pukujan on 2026-10-06
- Original: https://github.com/Pukujan-lab/octo-database/issues/160
- Labels: bug, plane:lead-owner

## Summary

On a mobile viewport (≤700px), after signing in:

1. **No workspace switcher.** The sidebar picker is hidden by CSS, so the user cannot change workspaces.
2. **No confirmation a new workspace was created, and it does not become active.** After creating one, the page keeps showing the previously active workspace and there is no control on mobile to see or select the new one.
3. **No explanation of the confirmation secret.** The field gives no hint of what it is or why it is required.
4. **The create-workspace dialog does not close after a successful create** — it stays open until "Done" is pressed.

## Observed facts

1. The only workspace switcher is the sidebar `<select id="workspace-select" class="workspace-picker">` (`src/main.ts:246`), and switching is handled solely by its `change` event (`src/main.ts:302`).
2. At ≤700px the mobile media query hides it: `.workspace-label,.workspace-picker,.sidebar-spacer,.sidebar-note,.profile{display:none}` (`src/styles.css:13`). The topbar `.workspace-chip` is role-only and is also hidden at the same breakpoint. No alternate mobile switcher exists anywhere in the tree.
3. The accepted frontend brief requires the opposite: "Mobile layout preserves the workspace selector, key status cards, and readable tables without horizontal overflow." (`docs/frontend/DYAD_DASHBOARD_BRIEF.md:315`). Current CSS contradicts it.
4. On create, the app refetches `/api/workspaces` but never sets `state.workspace` to the new workspace, so the active workspace does not change (`src/main.ts:376-378`). The `workspace-created` modal shows only the one-time key secret (`src/main.ts:188`) — it does not name the created workspace, and on mobile the picker that would list it is hidden (2), so the user has no way to confirm it exists.
5. Confirmation-secret fields carry no helper text or tooltip: workspace create (`src/main.ts:184`), key create (`src/main.ts:186`), delete workspace (`src/main.ts:192-194`), and the Access inline form (`src/main.ts:235`). The only other mention is a settings row reading "Confirmation secret — Configured/Not configured" (`src/main.ts:235`) with no explanation.
6. After a successful create the dialog is set to `workspace-created` (`src/main.ts:378`) and closes only via the "Done" button (`data-action="done-secret"`, `src/main.ts:340`). The key-mint path instead closes immediately (`src/main.ts:384`), so the behavior is inconsistent.

## Reproduction

1. Open Octo in a browser narrowed to phone width (≤700px, e.g. DevTools device toolbar) and sign in (Google or Guest).
2. Observe the header: no workspace selector is present.
3. Tap **+ New Workspace**, fill in a name and the confirmation secret, and submit.
4. Observe: the dialog stays on "Workspace created" (secret box) until **Done**; after **Done** the page still shows the previous workspace, and on mobile there is no control to see or select the new one.

## Proposed fix *(proposal — not a mandate)*

- Keep a workspace switcher reachable at ≤700px (render the workspace `<select>` or an equivalent control in the topbar/heading on mobile rather than `display:none`).
- After a successful create, set `state.workspace` to the new workspace and load it, and name the created workspace (name/slug) in the confirmation.
- Add a short helper line/tooltip explaining the confirmation secret on every field that uses it — what it is, that it gates destructive/high-impact actions, and where it is set.
- Close the create-workspace dialog automatically after a successful create (or make the confirmation a non-blocking toast), matching the key-mint path.

## Boundaries / non-goals

- UI/UX defect report only; it does not prescribe a frontend framework or a redesign.
- Not a request for new security or policy machinery — only for the existing confirmation-secret behavior to be explained in the UI.
