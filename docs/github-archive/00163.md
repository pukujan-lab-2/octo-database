## Summary

An agent adopting Octo into the **design-bakery** project recommended giving it its own self-hosted Postgres — first outside Octo ("for independence"), then co-located on Octo's host as a peer to Octo's own Postgres — and never read or tried Octo's **managed provisioned-database layer** (`provision_database` / `POST /api/workspaces/<id>/database`, Slice 20). The owner caught it before anything was built.

Root cause: Octo's managed data layer was documented only inside Octo's own repo. From an adopting workspace there was **no signal** that Octo is the designated data layer, and nothing required the agent to check — so "host my own DB" (the default instinct) won.

This is the Octo-repo half of the fix (owner-chosen scope; no cross-repo change to design-bakery yet).

## Changes

- **`docs/consuming-octo.md`** (new) — canonical agent-facing guide:
  - The rule: do not provision/scaffold/recommend a database for an Octo-served project — not for independence, not co-located on the Octo host.
  - The narrow exception: only with a *demonstrated* concrete incompatibility, surfaced to the owner before building anything.
  - The exact path: `provision_database` (MCP) or `POST /api/workspaces/<id>/database` → connect with an ordinary Postgres client; connection string returned once; pgvector pre-enabled.
  - A copy-paste **boot block** for an adopter's `AGENTS.md` — the piece that gives an adopting workspace an in-workspace signal.
- **`README.md`** — pointer to the guide from the front door.
