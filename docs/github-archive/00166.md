## Problem

The live Octo database on gravebuster was created on 2026-10-01 by an init script that applied migrations **without** recording them, so `octo.schema_migrations` does not exist. Migration tracking was added later (`62f2d37`).

That makes the pending production promotion (PR #158) undeployable as-is: `deploy.sh` step 4 runs `migrate.sh`, which tries to re-apply every migration, and the first unguarded `CREATE POLICY` aborts the run. `deploy.sh` runs under `set -e`, so the deploy stops before the container swap.

The one-time `MIGRATE_BASELINE=1` remedy exists for exactly this, but it records **every migration file present**. Run from the checkout being deployed, it also records that checkout's *new* migration, which is then skipped forever — the schema silently drifts behind the code.

## Reproduction

Built a `pgvector/pgvector:pg16` database from the production commit `3f36fa9` (13 migrations, no tracking table), then ran the deploy path:

- **Plain run** → `ERROR: policy "principals_select_own" already exists`, exit 3, deploy aborted.
- **Baseline against the deploy set** → 14 recorded, `0 applied`, `octo.workspace_databases` absent (provisioning route would 500 at runtime).
- **Corrected two-step** (baseline at the database's commit, then deploy) → `1 applied, 13 already recorded`, exit 0, `octo.workspace_databases` created.

## Change

Documents the required ordering — baseline against the migration set the database already has, i.e. the commit that created it — in the `migrate.sh` header (at the point of the footgun) and `docs/self-hosting.md` § 3a. No runner logic changes.
