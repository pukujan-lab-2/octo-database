## What

`POST /api/graph/query` — a read-scoped, membership-checked read that runs `GRAPH.RO_QUERY` against one workspace's graph and returns `{ query, rows, metadata }`.

## Why the route is the isolation boundary

The graph engine inherits none of the `octo.*` RLS fence — it is outside the schema, outside `octo_app`, and outside the request pipeline that binds `request.workspace_id`. The graph name is derived from the **authenticated workspace UUID** inside the client, never accepted from the request, so no request value can name another workspace's graph. Only the read-only path (`GRAPH.RO_QUERY`) is exposed, so a mediated call cannot write.

## Fail-closed, optional engine

Like the embedding provider, the graph engine is optional: unset `OCTO_GRAPH_URL` leaves the surface reporting not-configured (`503 GRAPH_NOT_CONFIGURED`) and advertises `graph.query` as `unavailable`, rather than a half-wired engine. Authorization (scope → key-workspace match → membership) runs **before** the provider probe, so an unauthorized caller learns nothing about configuration.

## Eval

`tests/e2e/graph-read.spec.ts` pins the fence without an engine (401 unauthenticated / 403 cross-key / 403 non-member / 400 malformed id / 503 unconfigured) and, where an engine is present, that a read against an unprojected workspace returns empty rows rather than an error. A FalkorDB service is wired into `gates.yml` so the configured path runs in CI instead of skipping.
