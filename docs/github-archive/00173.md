## Summary

A workspace's provisioned database could only be reached with the connection string provisioning returned once — a credential the caller must store, addressing a host/port the caller has to be able to route to. Now **an Octo API key alone runs SQL against the workspace's own database**: no connection string, no hostname, no IP.

- **`POST /api/workspaces/:id/query`** — `{ sql, params?, rowLimit? }` → `{ columns, rows, rowCount, statementCount, truncated }`.
- **`src/server/query.ts`** connects as the workspace's OWN `NOSUPERUSER` role with its own password — never as the privileged provisioning credential, whose session client SQL could `RESET ROLE` back to and reach the whole cluster.
- **Read scope** opens a read-only transaction (and uses the extended protocol, so a second statement cannot escape it). **Write scope** with no parameters uses the simple protocol, so one request can carry a whole migration.
- The role's password is stored encrypted (AES-256-GCM, keyed from `OCTO_MFA_SECRET`) in a new `octo.workspace_database_credentials` table: RLS with no policies, granted only to the `BYPASSRLS` service role, so the fenced app pool can never read it. Kept out of `octo.workspace_databases`, which is the tenant-visible catalog and must carry no credential.
- A **workspace-scoped key is allowed** here for its own workspace — unlike provisioning, running SQL against your own workspace's database is what a scoped key is for.
- Capability `workspaces.query`, MCP tool `query_workspace_database`, and updated `docs/consuming-octo.md` / `README.md`.
