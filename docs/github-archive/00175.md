### Human-Understandable Summary

Octo stores files in a private R2 bucket and only hands out download links that expire after one hour. That is the right default for backups, galleries, and other private workspace files. It is the wrong shape for a website that needs to publish an image.

A blog cover, an Open Graph image, or a media-library asset has to keep a normal web address that browsers and link-preview crawlers can open with no login, including next year. An expiring signed URL cannot be stored on a post. design-bakery, the first site moving its images onto Octo, had to stand up its own doorway: the site API fetches the private object with the workspace key and streams it at `/api/public/assets/<file id>`. That works for the site as it is now. It is the wrong serving path once a site holds on the order of 100,000 images, because every view downloads the bytes through the API.

What the owner asked for, and what most sites already do, is a permanent Cloudflare address for files a site explicitly publishes:

- The existing private `octo` bucket stays private. Backups and unpublished files do not become readable.
- Publishing is a separate action. It copies or places that one object into a dedicated public R2 bucket, or a public prefix, fronted by a Cloudflare custom domain.
- Octo returns one stable address, for example `https://files.example.com/<file id>`. The adopter stores that address the way it used to store a Supabase public URL.
- Knowing the address is enough to read the file. The bucket is not a browsable directory. Object keys stay unguessable.
- Unpublishing removes that address. Everything that was never published still requires the workspace key, and those links still expire.

This log requests that capability. It is a proposal, not an implementation mandate.

### Reproducibility Steps / Evidence

1. Upload a file with `POST /api/files/upload`. The object lands in the private R2 bucket named by `OCTO_R2_BUCKET` / `R2_BUCKET`, default `octo` (`src/storage/r2-client.ts`). The call returns a file id, not a public URL.
2. The only anonymous media URL Octo builds is `signMediaUrl` (`src/media/media-token.ts`). `DEFAULT_TTL_SECONDS` is 3600. The signature dies after an hour, and a missing `OCTO_MEDIA_SECRET` invalidates every URL on process restart.
3. `<img>` and social crawlers cannot send `Authorization`. A URL stored on a blog post therefore cannot be an Octo signed URL.
4. design-bakery's workaround, on branch `task/TASK-DB-0074-octo-data-layer`: upload with a `db-public-` name, store `GET /api/public/assets/<file id>`, and have the site API stream the bytes with the workspace key. A 70-byte PNG round-tripped through that route on 2026-10-06. The route refuses any workspace file whose name lacks the prefix.
5. That workaround leaves the API on the path for every image view. At roughly 100,000 images, or one post that is widely shared, that is the bottleneck. R2 plus Cloudflare's cache is the path that takes the API out of it.
6. Making the existing `octo` bucket public would publish every object whose key leaks, including backups. The request is a second public bucket or a public prefix, used only by an explicit publish action.

### Non-Binding Proposed Next Actions

- [ ] Add an explicit publish action for one file. Unpublished files stay on the private bucket and keep the expiring signed URL.
- [ ] Serve published objects from a dedicated public R2 bucket, or a public prefix, on a Cloudflare custom domain. Do not enable public access on the existing private bucket.
- [ ] Return one stable HTTPS URL from publish. Adopters store that URL. It does not expire and does not require the workspace key.
- [ ] Unpublish removes the public address. Private files remain unreadable without the workspace key.
- [ ] Leave directory listing off. Object keys stay unguessable ids.
