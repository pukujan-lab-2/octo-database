## Summary

Issue #12 (Slice 10). The graph engine had a read path but nothing ever wrote to it — no application code projected canonical rows into a graph, so the engine was dark and `query_graph` could only return empty. This adds the projector and its routes.

- **Canonical reads** (`dbReadEpistemicGraph`, `dbEpistemicWatermark`) run on the fenced pool, so the same RLS membership gate that guards the ledger guards the projector's input.
- **`projectWorkspaceGraph`** is destroy-and-rebuild: the graph is a read model, so a rebuild always converges to the same shape for the same rows, and a partially-written prior projection cannot survive. Only the projector reaches the write path.
- **`POST /api/graph/project`** (write scope + operator) rebuilds and records the outcome; **`GET /api/graph/health`** (read scope) reports the watermark, counts, and whether the graph is stale against the live canonical ledger.
- **Isolation is unchanged**: the graph name is derived from the authenticated workspace UUID in the client, never accepted from a request, and the write path keeps that boundary.
- Rows are flattened to primitives before they reach the engine: FalkorDB properties hold only primitives, and `pg` hands back `timestamptz` as `Date` objects and `jsonb` as objects.

Capabilities (`graph.project`, `graph.health`) and the MCP tools (`project_graph`, `graph_health`) follow the existing pattern.
