## Summary

Issue #12's slice packet says "Existing jobs drive projection/rebuild," but the projector shipped reachable only through `POST /api/graph/project`. The generic job enqueue route accepts any job type, so a queued `graph_rebuild` was accepted and then failed with `UNKNOWN_JOB_TYPE` — a silent hole. This wires the queue to the projector:

- **`processJob` handles `graph_rebuild`** — a destroy-and-rebuild of the workspace's graph from canonical rows, the same operation the on-demand project route performs. The job's workspace is the authority and the graph name is derived from it by the client, so a rebuild cannot cross tenants. Unconfigured `OCTO_GRAPH_URL` fails the job with `GRAPH_NOT_CONFIGURED` (non-retryable) rather than looping; an engine error records a failed projection and retries.
- **Trusted-pool reads/writes for the worker.** The scheduler drains with no caller identity, so the ledger read and the projection write go through the service pool (`...Service` variants), as the archive and thumbnail jobs already do. The fenced pool would fail closed and silently project an empty graph from a ledger RLS hid — the exact failure this avoids.
- **Workspace deletion drops the workspace's graph**, so the in-memory engine does not accumulate orphaned graphs. (Owner recorded this as a slice-E item: "`GRAPH.DELETE` belongs with the projection lifecycle.")
