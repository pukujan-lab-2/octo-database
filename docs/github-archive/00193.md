## Human-Understandable Summary
With one workspace selected in Octo's **Access** view, the **API keys** table lists the signed-in principal's keys belonging to multiple unrelated workspaces, along with an account-wide key. The page heading and workspace context suggest the list belongs to the selected workspace, but it is account-scoped. Keys from other workspaces also show **Revoke** and allowance-edit affordances without an explicit owning-workspace column.

The observer was signed in as a platform owner; code inspection shows this behavior results from principal-wide key listing, not a platform-owner-specific branch. Listing a key here does **not** demonstrate the key can operate outside its stored workspace binding, and the API list does not return raw key secrets.

## Reproducibility Steps / Evidence
1. Sign in as a user/principal who owns keys for two or more workspaces (observed example was a platform owner).
2. Select one workspace in the picker and open **Access**.
3. Observe **API keys** table. It includes keys apparently owned by other selected workspaces and the account-wide key.
4. Switch workspace; the table remains principal-scoped because the frontend fetches `GET /api/keys` without `workspaceId`.
5. Source trace:
   - `src/main.ts:91-115`: workspace loader appends `?workspaceId=` to most requests but fetches `/api/keys` unscoped.
   - `src/server/index.ts:2492-2509`: endpoint calls `dbListApiKeys(auth.principal.id)`.
   - `src/server/db.ts:786-805`: SQL has `WHERE principal_id = $1`, no selected-workspace filter.
   - `src/main.ts:279-288`: renders all returned keys in the selected workspace's Access view.
   - `src/server/index.ts:2686-2752`: PATCH/DELETE apply principal-ownership checks; this report is **not** proof of cross-principal escalation.

## Observed Consequence and Workaround
- Account-level credentials appear inside a workspace-level page without the workspace they belong to.
- Risk of operator confusion or revoking/editing the wrong key; no observed credential misuse or cross-workspace data disclosure.
- Workaround: verify each key's origin before editing/revoking; preferably manage account-wide keys in a separate account-level view.

### Follow-up source check: API-key workspace isolation fence

After filing, I checked the database enforcement path to distinguish the **human-session UI finding** from a potential workspace-key security issue.

- [`src/server/index.ts:400–455`](https://github.com/Pukujan/octo-database/blob/b224b2134f89a0ec04b6f259b0c9e7fbdaba28e9/src/server/index.ts#L400-L455): an authenticated workspace key binds its own `workspaceId` through `bindRequestIdentity`.
- [`src/server/db.ts:93–147`](https://github.com/Pukujan/octo-database/blob/b224b2134f89a0ec04b6f259b0c9e7fbdaba28e9/src/server/db.ts#L93-L147): the application query path sets `request.workspace_id` within a transaction.
- [`supabase/migrations/20261001080000_slice14_key_scope_isolation.sql:102–135`](https://github.com/Pukujan/octo-database/blob/b224b2134f89a0ec04b6f259b0c9e7fbdaba28e9/supabase/migrations/20261001080000_slice14_key_scope_isolation.sql#L102-L135): a **RESTRICTIVE RLS** fence explicitly covers `octo.api_keys` and permits rows from only the key's bound workspace when scope is present.
- [`src/server/index.ts:2719–2751`](https://github.com/Pukujan/octo-database/blob/b224b2134f89a0ec04b6f259b0c9e7fbdaba28e9/src/server/index.ts#L2719-L2751): key revocation checks `delete` scope and principal ownership; the database RLS fence is intended to apply in addition.

**Revised interpretation:** The observed all-keys listing occurs in the owner's **human session**, which is intentionally not workspace-scoped at the database level; it is therefore a **workspace-context/discoverability defect**. The source includes a database isolation safeguard for workspace-bound API keys. No API-key-based cross-workspace enumeration or revocation has been demonstrated. Whether the target deployment has the migration applied and uses the fenced runtime role was **not** independently tested.

**Suggested acceptance test:** Authenticate as a workspace-scoped key with `read`/`delete` grants under a principal that owns multiple workspaces; verify `GET /api/keys` returns no other-workspace key metadata and `DELETE /api/keys/<other-workspace-key-id>` cannot revoke that key. Also test the intended all-keys listing for the human owner session. This would validate enforcement independently of UI presentation.

This follow-up refines evidence for #193; it does not create an additional security finding.
