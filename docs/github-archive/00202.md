# Issue #202: Durability: a host loss must never lose workspace data — get the backup offsite and make it verifiable

- State: open
- Opened by Pukujan on 2026-10-10
- Original: https://github.com/Pukujan-lab/octo-database/issues/202

## What happened

`gravebuster` went offline 2026-10-09 (off the tailnet, SSH unreachable, different tailnet account). It hosted an Octo instance whose Postgres held live workspace data — including design-bakery's `octo_ws_design_bakery_c192afbc` (33 blog posts + media-library rows).

Octo was re-hosted on the owner's MacBook Pro as a **fresh** instance. The old workspace does not exist there. So today:

- The **old DB rows are unreachable** — not proven erased, but only recoverable if gravebuster's disk returns.
- The **only copy of the Mac instance's DB is on the Mac**, and its nightly backup writes to `~/octo-backups/` on that same laptop.

That is the actual defect: **the backup and the database share a single point of failure.** A dead laptop loses both.

## Evidence (verified 2026-10-10)

- R2 `octo` (306 objects) and `octo-public` (195 objects) both list fine — **file bytes survived** because R2 is Cloudflare's, never gravebuster's.
- A scan of `octo`, `octo-public`, `hades`, `fossil`, `cortex` for `octo-backups`/`backups`/`*.dump` prefixes found **nothing** — no database dump has ever left the host.
- `deploy/mac/backup.sh` prints `offsite: skipped (rclone or r2: remote not configured)` on every run.

## Work requested

1. **Offsite the database dump to R2.** The script already attempts this; it needs `rclone` installed on the Mac (Homebrew is absent — this is the one manual step, needs `sudo`) and an `r2:` remote configured from the existing R2 credentials. Confirm a dump actually lands in an R2 bucket and that the local-only path is no longer taken.
2. **Retention that bounds duplication.** `OCTO_BACKUP_KEEP` default is being set to `1` (one rolling copy). Also fixed: the prune step looked for `octo-<stamp>-files-*.tar.gz` while the archive is named `octo-files-<stamp>.tar.gz`, so file archives were **never pruned** — the one genuinely unbounded accumulation. Both are in the `deploy/mac/backup.sh` change accompanying this issue.
3. **Make the backup verifiable, not just present.** A backup nobody has restored is a guess. A periodic restore-into-a-throwaway-database check (does `pg_restore` succeed, do the expected tables and row counts appear) should run and report, so "backup exists" becomes "backup works".
4. **State the recovery contract in one place** — where the dump lives, how to restore it, what is covered (whole cluster: control plane + all workspaces + provisioned DBs) and what is not (R2 file bytes are separate, Supabase legacy is separate).

## Out of scope

No new secret-management system, no rotation ceremony, no second backup tool — one dump, offsite, verified. Follow the anti-overengineering contract in AGENTS.md.

## 2026-10-31: offsite works now, but the dump covers only one database

Re-checked on the Pro:

- `deploy/mac/backup.sh` runs nightly at 03:30 and copies to R2 `octo-backups` (rclone is configured now). A restic container also backs up `~/octo-backups`.
- **Gap:** the script runs `pg_dump -U postgres -d postgres`, so only the control-plane database is dumped. Every provisioned workspace database (`octo_ws_*`) is left out. The largest, `octo_ws_legal_graph_rag_0eef115f`, is 14 GB; `octo_ws_nyc_neighbourhood_e5f1aa5e` is 1.1 GB. The last dump was 9.7 MB, which is why it looked small.

Fix: dump every database in the cluster (loop over `pg_database`, or `pg_dumpall --globals-only` plus one `pg_dump -Fc` per database), copy each to R2.

Planned with the VPS move (owner decision 2026-10-31): Postgres primary on the VPS, a live streaming replica on the Pro over Tailscale, and pgBackRest (or WAL-G) archiving to R2 in place of the nightly dump. No managed Postgres.
