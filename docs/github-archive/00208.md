## Problem and consequence

The Access page listed every API key the principal owned in one flat table, and its "Scope" column only ever said "Workspace" or "Account-wide" — it never named which workspace a key belonged to. Keys from unrelated projects piled into a single undifferentiated list, and the per-key allowance editors rendered as four loose checkbox rows below the table that did not line up with it.

## What changes

- **Keys are scoped to the active workspace.** The list shows this workspace's keys plus account-wide keys that can act here; other projects' keys stay out of the way. The Scope column is replaced by a Workspace column that names the workspace.
- **Allowance editing collapses into a per-row dropdown** whose summary reads back the current scopes (e.g. `read, write, files ▾`), replacing the loose stack of checkbox rows.
- **Per-key verbs move behind a `...` menu** instead of a bare Revoke button in the row.
- **The keys and share-links tables gain a filter field and a table/cards view toggle.**
- Both dropdowns open **in flow rather than as overlays**: an absolutely positioned menu is clipped by the table's `overflow-x: auto` container, which was cutting off the last row's action menu.

## How to verify

- `npx tsc --noEmit`, `npx vitest run` (357 tests), and the `api-key-allowances`, `api-key-mobile`, `shares`, and `dashboard-ui` Playwright specs all pass locally.
- In the browser: the keys table names each key's workspace, the filter narrows the list and keeps focus, the Table/Cards toggle switches views, and the last row's `...` menu is fully visible.

## What stays unchanged

The keys API's shape apart from the new optional `?workspaceId` filter and the added `workspaceName` field, the confirm-code gate on allowance edits, and the share-links table's data.
