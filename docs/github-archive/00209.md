# Issue #209: Frontend v2 — regenerate the Octo workspace portal with app-builder-automation

- State: open
- Opened by Pukujan on 2026-10-10
- Original: https://github.com/Pukujan-lab/octo-database/issues/209

## Direction

Replace Octo's hand-written frontend with a **version 2** built from scratch by the owner's own generator, [`app-builder-automation`](https://github.com/Pukujan/app-builder-automation). Owner direction, 2026-10-10:

> make a version 2 of this frontend, completely from scratch, getting rid of the frontend, get the api contracts and requirements, then make a new ui completely from scratch using my github repo app builder automation

The current frontend is a single vanilla-TS SPA (`src/main.ts` + `src/styles.css`, string-template render, full re-render per state change). It is retired. The replacement is generated, then hand-finished, against **the same API** — no server changes.

## Lineage

- `docs/UI_DIRECTION.md` (owner correction on #74) already directs a from-scratch visual rebuild: dark default, five workspace views (Overview / Files / Gallery / Operations / Access), keep the existing API as the data/action boundary, preserve the public read-only share viewer. This issue executes that direction with a specific tool.
- `AGENTS.md` items #3 (control dashboard), #5 (workspace gallery), #8 (operations page); `PROJECT.md` frontend principle.
- Owner direction to use `app-builder-automation` (2026-10-10).

## Observed facts

- `app-builder-automation`'s generator exists and its loop is implemented: `node server/src/index.mjs generate --spec <md> --out <dir>` runs a blueprint → tool-using agent → **typecheck gate + completeness gate** (spec-declared `data-testid` hooks present, starter placeholder gone), feeding failures back for repair. Substrate is `templates/react-vite-shadcn/`.
- A local gateway is live at `http://127.0.0.1:4000/v1` and serves `ih/cb/deepseek-v4.1-flash`, `ih/cbcn/deepseek-v4-pro`, `ih/cx/gpt-5.6-luna`, and others; a completion through it succeeds.
- **Blocker to clear first:** ABA's generator hardcodes its *data-access* prompt block to its own analytics fixture (`GET /api/views/:name`, `v_*` views) in `server/src/prompts.mjs`, injected into every system prompt. It would actively mislead the model for Octo. It needs a `--data-access <file>` flag (ABA PR, separate repo).
- `app-builder-automation/.env` currently has no `BUILDER_*` vars, so the generator is not yet configured on this machine. ABA requires a non-empty `BUILDER_API_KEY`.
- Octo's API is ~30 routes in `src/server/index.ts`: guest + Google login, MFA, `confirm-challenge`/`confirm-secret`, workspaces, files (upload/download/content/thumbnail/archive/restore/delete), gallery, keys, shares + a public share viewer, capabilities, jobs/retry, activity, ops. Auth is a bearer `sessionToken` in `localStorage` (`octo_token`), 20-minute token + idle expiry, Turnstile on guest login.

**Inferred, not observed:** a pro-tier model can produce a complete five-view portal in one run that speaks Octo's real auth. To be proven by browser verification, not assumed — ABA's gates cannot catch a wrong-but-compiling fetch/auth layer.

## Acceptance criteria *(proposed)*

- Guest login and Google login work; the 20-minute expiry watchdog and the confirm-code gate (`POST /api/me/confirm-challenge` → display code → attach on destructive calls; first-run 412 `CONFIRM_SECRET_NOT_SET`) work.
- The five views (Overview / Files / Gallery / Operations / Access) render **real** workspace data and reach the real actions.
- Upload → Gallery → download, key mint through the confirm-code gate, allowance editing, share create + public viewer, and job retry all work in a browser against the local server.
- The public read-only share route and its standalone viewer are preserved.
- The old `src/main.ts`, `src/styles.css`, and root `index.html` are deleted; root `dev`/`build` scripts point at the new frontend.
- `gates` is green, including a typecheck of the new frontend; the e2e suite is updated to the new `data-testid` hooks and passes.

## Boundaries / non-goals

- No server or API changes; the API stays the data/action boundary (per `UI_DIRECTION.md`).
- No new auth, testing, or process machinery beyond wiring the existing `gates` to the new layout.
- RAG / epistemic / graph / workspace-query routes stay out of the UI.
- No change to production promotion or the deploy path.
- One hand-edit set on the generated app (Vite proxy block + `build.outDir`), recorded so it is re-applied on regeneration.
