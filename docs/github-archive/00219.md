## Summary
- Adds `docs/research/2026-10-11-tenancy-capacity-dbw-and-bucket-layout.md`: the measured, durable answer to the recurring "can we change DB-per-workspace / should we go multi-bucket / what about 50+ workspaces and 100+ users" question. Verdict: change nothing — connections are per-request (`src/server/query.ts` opens a fresh short-lived client per request, not a pool per workspace), so the binding limit is `max_connections`=100 under concurrency, not workspace count. Keep one R2 bucket (R2 allows 1,000,000 buckets/account — the 1,000 ceiling people cite is S3's; and R2 tokens cannot be scoped to a prefix, so per-workspace buckets buy no real isolation). Live numbers included (5 DBs, 39 MB, control DB ~10 MB).
- Adds a scope note to `docs/research/2026-10-05-scaling-data-engines.md`: that report covers the **control-plane** shared-schema/RLS tier; the shipped **data plane** is Slice 20 database-per-workspace, covered by the new companion doc. Without this note the older line "do NOT split into database-per-tenant" reads as a verdict on workspace data, which it was never about.
