## Summary
The MCP authorization server capped every OAuth client at `read files`, so a connector like ChatGPT was read-only by construction — no way for the owner to grant write or delete regardless of what the client asked for.

- `OAUTH_ALLOWED_SCOPES` widens from `['read','files']` to all four scopes (`read`, `write`, `delete`, `files`).
- The consent page now renders **one checkbox per scope**, pre-selected to exactly what the client requested. A read-only client still yields a read-only token unless the human deliberately opts in — the safe default is unchanged; only the ceiling moves.
- `handleAuthorizePost` reads repeated `scope` fields via `form.getAll` (a checkbox submits one entry per checked box), and refuses an empty grant with a clear 400.
- Copy updated: "Allow access", and the note now says the granted permissions are recorded on the connection.

**No migration.** The granted set already reaches the token through the existing `scope` claim, and the refresh grant reuses the stored scope verbatim, so a refresh can never widen.

**Operational note:** refreshing a token reuses its original scope, so an already-issued read-only token (e.g. the live ChatGPT connector) stays read-only. Reconnect the client to pick up new scopes.
