### Human-Understandable Summary
An agent uploaded nine documents into an Octo workspace with `upload_file`, then could not find any of them with `query_workspace` (semantic search) — not even by searching for exact, distinctive phrases from documents whose contents it had just successfully downloaded. It read this as a retrieval-relevance problem and went looking for a broken index.

The actual cause is structural, not a bug in search: **Octo has two independent lanes and nothing bridges them.**

1. **Files lane** — `upload_file` stores bytes in R2 and writes a row to `octo.files`. That is all it does.
2. **Retrieval (RAG) lane** — `query_workspace` searches `octo.chunks` / `octo.embeddings`, which are populated *only* by `POST /api/rag/documents` (a completely separate ingest call with its own body shape: `{workspaceId, title, text}`).

A file being stored in Octo does **not** imply it is indexed. `upload_file` never calls the embedding pipeline, and no job does either (the worker handles only `thumbnail`, `archive_file`, `restore_file`, `graph_rebuild`). So for a workspace that has only ever used the files lane, `query_workspace` returns `matches: []` for *everything* — correctly, because nothing was ever indexed.

Two things make this worse than it needs to be:
- **The failure is silent.** `matches: []` is indistinguishable from "the index exists but nothing matched." The caller cannot tell "nothing is indexed" from "nothing is relevant," which is exactly the confusion observed.
- **It compounded with a real config gap.** `EMBEDDING_PROVIDER_NOT_CONFIGURED` was genuinely true on the host until 2026-10-13 (the embedding key had not been set after the deploy moved to the MacBook Pro), so even the *correct* ingest path would have 503'd before today. That earlier error made "embeddings are broken" a plausible theory when the dominant cause was "the pipeline was never invoked."

### Reproducibility Steps / Evidence
1. `upload_file` nine markdown/docx documents into the `chatgpt` workspace. All succeed.
2. `list_files` → returns 9 rows; `download_file` retrieves their contents (the lane works).
3. `query_workspace` with exact phrases from those documents → `{"matches": []}`.
4. Direct DB check of the two lanes (read-only):
   - `octo.files` for the workspace → **9 rows** (e.g. `Context/MASTER_CONTEXT_2026-10-12.md`, `Context/UPDATE_2026-10-12_RC_REJECTION.md`).
   - `octo.documents` → **0**; `octo.document_versions` → **0**; `octo.chunks` → **0**; `octo.embeddings` → **0**; `octo.embedding_configs` → **0**.
5. Code: `POST /api/files/upload` (`src/server/index.ts`, ~L2005) writes the object and `octo.files` only. The only callers of `embedTexts` / `dbReplaceChunksAndEmbeddings` / `dbEnsureEmbeddingConfig` are the `/api/rag/documents` and `/api/rag/query` routes. `src/jobs/worker.ts` has no RAG/ingest job type.

### Non-Binding Proposed Next Actions
*(proposal)*
- [ ] Make the unindexed state **legible**: when a workspace has zero rows in `octo.chunks`, `query_workspace` / `POST /api/rag/query` should say so (e.g. `NO_INDEXED_DOCUMENTS`) rather than returning a bare `matches: []`.
- [ ] Decide the intended relationship between the two lanes. Either (a) `upload_file` also enqueues a RAG ingest job for text-extractable types, or (b) it stays a pure byte store and the docs state plainly that semantic search requires a separate `POST /api/rag/documents` call. (b) is the smaller change.
- [ ] If (a): add an ingest job type to the worker (text/markdown first; PDF extraction is still refused by `extractText`).
- [ ] Confirm `OCTO_EMBEDDING_*` is part of the documented deploy `.env` for any host, so a host migration cannot silently drop it again.
- [ ] Update `docs/consuming-octo.md` to describe the files lane vs the retrieval lane explicitly.
