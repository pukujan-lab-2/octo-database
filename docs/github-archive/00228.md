### Human-Understandable Summary

The repository layout no longer describes the product it contains, and it is drifting further with each slice. The naming is the visible symptom; underneath it sits a dead data layer from the Supabase-hosted origin.

**A. Two frontend trees with a version suffix.** `frontend/` and `frontend-v2/` are both tracked (96 and 120 files). Only `frontend-v2/` is live — the root `dev`/`build` scripts, `Dockerfile.web`, `vite.config.ts`, `playwright.config.ts` and the `gates` workflow all point at it. `frontend/` is referenced by nothing except two `*:legacy` npm scripts. The `-v2` suffix is a migration artifact: once v1 is deleted the name carries no information, and while v1 exists a reader cannot tell which tree is authoritative without grepping.

**B. `supabase/migrations/` is a misnomer — but the migrations themselves are live.** That folder holds 18 plain SQL migrations and no Supabase project config (`config.toml`, `seed.sql`, functions — none present). They are not an ancient artifact: `mcp_oauth.sql` was added 2026-10-10, and `deploy/gravebuster/migrate.sh` applies them to plain self-hosted Postgres on every deploy. The *name* is the leftover, not the content. Renaming is a pure path change with a handful of references (see evidence).

**C. The genuinely dead artifact: a whole Supabase-era data layer that the live server does not use.** Nine backend files import `@supabase/supabase-js` and take a `SupabaseClient` parameter (`src/auth/authorization.ts`, `src/auth/session.ts`, `src/auth/workspace-service.ts`, `src/media/gallery-service.ts`, `src/media/share-service.ts`, `src/storage/file-service.ts`, `src/jobs/job-service.ts`, `src/api/keys.ts`, `src/lib/supabase.ts`). The running server never constructs a Supabase client — `src/lib/supabase.ts#createOctoClient` has zero callers, and `src/server/index.ts` uses `pg` directly through `src/server/db.ts` (`dbPool` / `servicePool` / `queryService`). The `SupabaseClient`-taking functions are reachable only from `tests/` through `tests/mocks/mock-supabase.ts`; the live server imports just the pure helpers that happen to live in the same files (`hashApiKeySecret`, `authorizeKeyMint`, `parseKeyScopes`, `hashShareToken`). So Octo carries two parallel data-access layers, one of them dead, and the dead one is what keeps the word "Supabase" threaded through the code.

**D. State and documents are scattered across many homes.** "Current state" lives in `HANDOFF.md` (root), `planning/WORK_HANDOFF.md`, `checkpoints/CURRENT.md`, `.continuity/config.json`, `.coord/*.json`, and `.content-system/system-version.json`. "Specs" live in `docs/specs/`, `docs/superpowers/specs/`, `docs/productization/`, and `docs/frontend/`. `docs/` mixes dated research files, research *folders* that collide with sibling file stems, security notes, productization packets, and assets with no organizing scheme. Generated caches (`.mypy_cache/`, `.ruff_cache/`) are neither tracked nor gitignored, so they show as permanent untracked noise.

The owner's target direction is a **managed monolith organized MVC-style**: one deployable, one obvious place for each kind of thing. The current layout works against that. This issue logs the drift and proposes the consolidation; it is a proposal, not a mandate.

### Non-Binding Proposed Next Actions

*(proposal)* — all of this is a proposal; none of it is authorized until the owner accepts it.

- [ ] **Pick the target shape first.** Confirm what "managed monolith, MVC" means concretely — in particular whether the two deployables (`octo-web` + `octo-api`) collapse into one Node process that serves both API and built frontend (the API already has `src/server/static-file.ts`, so this is partially built), and whether `src/`'s domain folders (`auth/`, `storage/`, `media/`, …) become an MVC split or keep domains under an MVC-flavored root.
- [ ] **Remove the dead Supabase data layer (item C).** Delete `src/lib/supabase.ts` and the `SupabaseClient`-taking functions, and re-home the pure helpers the live server actually uses (`hashApiKeySecret`, `authorizeKeyMint`, `parseKeyScopes`, `hashShareToken`, `isShareActive`, `canTransition`, …) out of the Supabase-era files. Retire `tests/mocks/mock-supabase.ts` and re-point the integration/security tests at the real `pg` path. This is the change that actually removes "Supabase" from the code; it is more than a rename and needs its own acceptance criteria.
- [ ] **Delete the dead `frontend/` tree** once confirmed unreferenced, and drop the `-v2` suffix from the survivor. Update the `*:legacy` npm scripts in the same change.
- [ ] **Rename `supabase/migrations/`** (`db/migrations/` or `migrations/`) and update the four code references above plus the `docs/self-hosting.md` § 3a baseline note. Historical prose in `docs/`/`checkpoints/` stays as written.
- [ ] **Give `docs/` a scheme** — one rule for research vs. specs vs. productization vs. assets — and resolve the file/folder stem collisions.
- [ ] **Consolidate the "current state" files** to a single obvious home, or document explicitly which one wins (`.continuity/config.json` already names `checkpoints/CURRENT.md` as canonical).
- [ ] **Add `.mypy_cache/` and `.ruff_cache/` to `.gitignore`.**
