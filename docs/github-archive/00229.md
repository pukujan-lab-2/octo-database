### Observed Consequence and Workaround

**Observed consequence.** Octo's ownership boundary is stated in three places that do not agree, and the least correct statement is the one being actively pursued.

**1. Octo is an adopter, and its own repository already says so.** Octo does not appear in the certified set (`Pukujan/agent-stack-train` `stack-releases.json` certifies only `project-continuity-modules`, `content-generation-modules`, `agent-custom-setup`, and `observational-issue-ops`). It carries a `stack-manifest.json` with empty pins that follows the train, and its helper pins are current (synced 2026-10-11, `348da81`). Octo's `PROJECT.md` lists **"Git/GitHub — source code and repository-owned project continuity"** as a durable-state home. That is the correct relationship: a stack *consumer*, not a stack component.

**2. Issue #54 proposes to invert that relationship.** #54 would make Octo's PostgreSQL `octo.activity` and `octo.evidence` tables a *"private System of Record"* whose SHA-256 evidence hashes link into public GitHub issue receipts. A System of Record originates governance state; the receipt links to it. That is the inverse of Octo's own `PROJECT.md` statement and of PCM's github-progression contract, which forbids a local canonical ledger and treats checked-in projections as non-authoritative. If implemented as written, two repositories would each believe they hold the authoritative record of the same event.

**3. The drift #54 predicted has already happened, in miniature.** #54 warns that hand-copied OIO artifacts drift. They have:

- Octo's installed `.github/ISSUE_TEMPLATE/observational-issue.yml` is a **stale pre-OIO copy**. It uses the retired shape — `Contributor Plane`, `Priority Rating (1–100)`, `Risk & Blocker Classification`, `Human-Understandable Summary` — not the current OIO shape (`Issue Type`, `Filer Origin`, `Filing Authorization Evidence`, ontology versions, priority path + concept ID). Octo's live issues (#228, #227) still carry `plane:lead-owner` / `priority:pN` labels produced by that old form.
- Octo has **no `ontology/` directory**. It never installed OIO's project ontology, so it cannot supply the `Project Priority Path` or `Project Priority Concept ID` the canonical template requires. This issue log records both as `not-installed` for that reason.
- Consequently Octo's `.github/workflows/issue-triage.yml` still parses `Contributor Plane`, while OIO's canonical intake expects ontology-versioned fields. The two ends of the same protocol disagree.

**Workaround.** None needed today: nothing is broken at runtime, and Octo's pins are current. The workaround is *not to build the #54 System-of-Record path* until the boundary is ratified. Agents currently reason about Octo's place in the stack from three conflicting sources, and each new session re-derives it.

### Non-Binding Proposed Next Actions

*(proposal)*

- **Ratify Octo's boundary in one paragraph.** Octo is an **adopter**, not a certified component; its database owns runtime state (file catalog, workspace membership, per-workspace project databases), coordination hot-state, and a read-only drift index; **git owns governance**. Record the supersession on #54.
- **State the boundary test explicitly.** A datum belongs in Octo's database when a *machine must ask it at runtime*; it belongs in git when a *human must decide about it and history must prove it*. Do not move tickets, triage, task lifecycle, or provenance into Octo.
- **Adopt one-way derivation for `octo.activity` / `octo.evidence`.** GitHub carries `SHA-256(payload)`; Octo stores the private payload bytes plus the GitHub receipt reference. Verification runs one direction (recompute Octo's hash, compare to GitHub's). On conflict, GitHub's hash wins and the Octo payload is treated as corrupt. Octo is a hash-anchored private archive, not an authority. Forbid the inverse — an Octo row must never be the reason a GitHub issue opens, closes, or is prioritized.
- **Re-run the OIO adopter installer on Octo** to install the canonical issue template, project ontology, and triage workflow. This is #54's own proposal and it removes the drift by construction instead of by hand-edit.
- **Evaluate a scheduled drift query over `capture-ops` output.** Octo already emits git state, repository shape, test inventory, and server health as JSON (`npm run capture-ops`). A scheduled read-only query over those snapshots — "which repository's prose pin disagrees with the certified train" — is the outside-observer watchdog the 2026-10-06 issue log asked for, and it writes nothing into the governance layer. This directly addresses the class of staleness observed across the stack in the same session.
- **Keep coordination hot-state in a database, not in committed JSON.** ACS's boss lease, claim queue, and heartbeat currently live in committed `.coord/*.json`; ACS's own contract admits "issue prose is not an atomic lock." A database row with an atomic conditional update plus RLS is the enforced form of the same state. Database = live scratchpad (lease, current holder, queue); git = ledger (each claim/accept appended as a checkpoint). Never the inverse.
- **Sequence #202 (durability) after this boundary is ratified**, since the one-way model makes the payload store's offsite backup load-bearing.
