## Human-Understandable Summary

An adopter building citation retrieval needs to store authorities and directed citation/structure edges in the existing hosted FalkorDB, using workspace-scoped Octo access. The exposed Legal RAG MCP currently supports an epistemic ledger projection, not an independent authority graph. A synthetic live test confirmed that a citation target stored in claim provenance survives as JSON metadata but does not become an authority-to-authority edge.

Please investigate the smallest existing or additional API/MCP capability that supports this use case. Prefer reuse of the current hosted engine and existing import libraries; do not provision another database. This issue logs an observed integration gap and a proposed capability contract. It does not authorize implementation, deployment, or changes to existing data.

## Affected App, Adopter, Users, or Systems
A legal citation-retrieval prototype consuming Octo through workspace-scoped API/MCP access. Its public starter, KeyArgo/legal-graphrag-starter, describes 119,770 authorities and 160,793 directed citation/structure relationships. Dataset-scale import was not attempted.

## Observed Consequence and Workaround
Observed live through the connected Legal RAG MCP:
- record_epistemic accepted two explicitly synthetic authority entities, one synthetic citation claim, evidence, and a supporting claim_evidence link.
- project_graph succeeded; graph_health then reported configured=true and stale=false.
- The resulting topology was Claim --SUBJECT--> source Entity and Claim --CITES--> Evidence.
- The citation target Entity ID was retained inside serialized claim provenance. No source Entity --CITES--> target Entity edge was produced.
- A direct authority-to-authority CITES query returned no rows.
- A two-query client adapter successfully read the source's claim, parsed provenance, and fetched the target Entity by ID.

Workaround: metadata-based target resolution for a tiny demonstration, or the starter's local NetworkX graph. Neither demonstrates efficient reverse citations, multi-hop retrieval, bulk ingestion, or ranking at dataset scale.

Observed in pinned source:
- projector.ts already uses internal batches of 500 and creates ID indexes for Entity, Claim, Evidence, Perspective, and Belief. Lack of indexes or internal batching is NOT the reported defect.
- projectWorkspaceGraph deletes the workspace graph before reconstructing it from canonical ledger rows.
- The graph route family exposes ledger rebuild, health, and read-only query. Graph selection is server-derived from workspace identity; query parameters are scalar-only.
- No independent citation-graph import/namespace capability is exposed in the MCP inspected during this session. Other access paths and the exact live deployment SHA remain unverified.

2. Record a synthetic citation claim with subjectEntityId=A and provenance containing predicate=CITES, targetEntityId=B, and a unique test recordKey.

4. Project the graph; verify health and ledger readback.
5. Inspect nodes and relationships through query_graph.
6. Run:
   `MATCH (a:Entity)-[:CITES]->(b:Entity) WHERE a.id = $source RETURN b.id`
   Observed: zero rows.
7. Read claims through `(c:Claim)-[:SUBJECT]->(a:Entity)`, parse targetEntityId from provenance in the client, then fetch B by ID.
   Observed: successful target resolution; no native citation edge.
8. Compare the topology to projector.ts. Do not run a rebuild over an independently imported graph to reproduce potential data loss.
