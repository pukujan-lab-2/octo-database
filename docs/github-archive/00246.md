# Issue #246: Account and workspace vault: temp grants, decoys, and key health

- State: closed (2026-10-17)
- Opened by Pukujan on 2026-10-17
- Original: https://github.com/Pukujan-lab/octo-database/issues/246

Owner asked to log this and build it. It is the event cabinet from the hackathon pain, and it is wider than #92 and different from #184.

## What the owner does

- Puts any new login, token, URL, or note into Octo. The cabinet is a password-manager store: label, kind, username, URL, secret, notes.
- Account cabinet: the item belongs to the principal and is not tied to a workspace.
- Workspace cabinet: the same principal assigns the item to one workspace. An account grant does not read workspace items, and a workspace grant reads only that workspace.
- At an event, mints a temporary grant in the dashboard and hands it to their own agent or a collaborator's agent. Pasting it returns every item in that cabinet.
- Default lifetime is 24 hours. The lifetime is an integer number of hours from 5 through 72 (3 days), so 5 hours and 10 hours are valid. 24 is the default even though it is not a 5-hour step.
- The agent that holds a grant can request a decoy grant for the same cabinet. The decoy uses the same open call and the same JSON shape. Secret, username, and notes are stand-ins derived from the grant and the item id. They are never the stored values. The response does not say that it is a decoy. Opening a decoy records `tripped_at`. A decoy can only mint another decoy.
- A health pass checks what it can. Cloudflare tokens whose URL is on `api.cloudflare.com` or `dash.cloudflare.com` are verified against Cloudflare's token verify endpoint. Other token URLs are checked with the bearer secret; 401 or 403 marks the item stale. URL items are checked with HEAD. Login passwords are scored with zxcvbn and reported, not deleted for being weak. An item that cannot be checked and is still unchecked after 30 days is marked stale. An item that stays stale for 14 days is deleted on the next health pass.
- The dashboard has a Keys view for both cabinets, grants (including tripped decoys), and health.

## What this does not do

- It does not stand up Infisical, OpenBao, or Vaultwarden. Infisical was removed for idle RAM, and the planning notes defer OpenBao. Crypto is the same OpenSSL AES-256-GCM envelope already used for MFA secrets, under a separate `OCTO_VAULT_KEY`. Password scoring uses zxcvbn. Grant tokens are hashed with the existing API-key hash.
- A normal `octo_live_` API key cannot read the vault or mint a grant. `confirmGate` still requires a human session to store, delete, mint a real grant, or run health (health can delete stale items).
- Stored vendor secrets are not rotated.

## Done when

- [ ] Account and workspace items round-trip encrypted at rest, and list responses omit the secret.
- [ ] A real `octo_vault_` grant reads only its cabinet. An account grant does not return workspace items.
- [ ] A decoy grant returns the same shape, never the stored secret, and sets `tripped_at`.
- [ ] Expiry defaults to 24 hours and rejects values outside 5–72 hours.
- [ ] Health marks a rejected token stale and the pass removes items stale for 14 days.
- [ ] The Keys view can add an item, mint a grant, and show health.
- [ ] `OCTO_VAULT_KEY` unset answers 503 `VAULT_NOT_CONFIGURED`.
