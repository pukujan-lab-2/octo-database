## Summary

- The dashboard showed **0 B** for every file and for the workspace's recorded-storage total, even though the bytes were in R2 and round-tripped correctly on upload and download.
- Root cause: `octo.files.size_bytes` is `BIGINT`, and node-postgres returns BIGINT columns as **strings** (`"11"`). `dbInsertFile`, `dbListWorkspaceFiles`, and `dbGetFile` projected the column straight through, so `sizeBytes` arrived as a string and the frontend's `formatBytes()` treats any non-finite number as `0 B`.
- Fix: cast the three projections to `double precision`, which node-postgres parses as a real number (verified against the live `octo-api` container against the production database: `{"raw":"11","casted":11}` — string vs number).
- The e2e catalog spec now asserts the rendered size cell, so a regression here fails CI instead of silently showing 0 B.

Verified live before the fix: upload returned `sizeBytes: "11"` (string) but `/api/files/content` returned the exact stored bytes (`hello world`), and R2 health is connected — so storage itself was never broken; only the number's type crossing the API was.
