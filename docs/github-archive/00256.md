## Summary
- Adds `POST /api/vault/open/lease`, where an agent holding a cabinet grant names a stored item (`label` or `itemId`) and Octo mints a per-agent working key (`octo_tmp_…`, 15-day default, 1–30 days).
- Adds `GET /api/vault/leases` and confirm-gated `DELETE /api/vault/leases/:id` so the owner can list and revoke individual working keys.
- The cabinet (`GET /api/vault/open`) now returns each item's relay routes alongside the item, so an agent sees where to attach its working key.
- Re-minting for the same `(grant, item)` revokes the previous active lease in one transaction, so a leaked key is rotated by asking again.
- Decoy grants are refused: a working key is a real credential to Octo's relay, not a decoy.

The working key is structurally fenced: distinct prefix (`octo_tmp_`), distinct table (`octo.vault_leases`), distinct resolver. It cannot open the cabinet or list vault items — every non-relay path 401s.
