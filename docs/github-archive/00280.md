## Why

An agent holding an `octo_vault_…` grant reported two contradictory things: that Octo "has no vault endpoint", and that the "temp key" it was given returned real plaintext secrets. Both follow from the guide, which described the grant as a way to *avoid* holding a vendor credential. It is not — it is a cabinet reader.

Verified against the live instance:

| Token | `GET /api/vault/open` | `/api/workspaces` |
| --- | --- | --- |
| `octo_vault_…` (grant) | `200`, every item with real `secret` and `notes` | `401` |
| `octo_live_ws_…` (API key) | `401` | `200` |

## What changed

`docs/consuming-octo.md`:

- A table of the three token families — prefix, name, who holds it, what it can see.
- A section stating plainly that a grant returns real plaintext secrets, is reusable for its whole lifetime, and is not a temp key; the working key (`octo_tmp_…`) is the agent-facing temp key and never sees the vendor secret.
- Agent and owner rules: agents ask for a working key, never a grant; owners mint grants only as deliberate cabinet disclosure.
- Exact `/api/vault/*` paths, with a note that there is no vault subdomain and that `401` on `/api/workspaces` with a vault token is expected.
- The same rule added to the boot block adopters copy into their `AGENTS.md`, so a fresh session cannot repeat the confusion.

Docs only; no server, route, or UI change.
