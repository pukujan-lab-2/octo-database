## Summary

- `GET /api/vault/open` with a grant now returns the cabinet's **inventory** — label, description, kind, url, `hasSecret`, `hasNotes`, routes — and decrypts nothing. Before this, a grant returned every stored secret in plaintext, so one token handed an agent the owner's real vendor keys. The only way to spend a credential is now a working key on a relay route, where Octo injects it server-side.
- Minting a working key requires a route. An item that carries its own `url` gets a bearer route derived from it on first mint, so a key and its url stored together are usable with no hand-made setup; an explicit route still wins. An item with neither answers `400 ROUTE_REQUIRED` instead of minting a key that has nowhere to go.
- A narrowed ("decoy") grant keeps the same cabinet and shorter lifetime but can no longer mint another grant.
- The service rail bands services five letters at a time — `#` first, then A–E, F–J, K–O, P–T, U–Z — and the keys table shows 10 rows a page.
- `docs/consuming-octo.md` now describes the three token families as built, and says plainly that a grant is an inventory, not a reader.
