### Priority Rating

2.1 — the grant endpoint family does not honor the documented "an agent holding a grant names a stored key and Octo mints one for it" contract when the item has no route.

## Affected

Any agent handed an `octo_vault_…` grant whose target item was imported without a URL or route. In the observed cabinet, 74 of 170 items are `kind: token` with `url: null` and `routes: []`, including the item this session needed (`wan video generation ACCOUNT TOKEN`, `6e58ccb8-9eda-4771-896e-0395fb5461ea`). Only the dashboard owner (Google session) can unblock such an item.

## Observed consequence

A grant can list the cabinet and request a working key:

```
GET  /api/vault/open        -> 200 (inventory only; never decrypts)
POST /api/vault/open/lease  -> 400 ROUTE_REQUIRED
```

Reproduced 2026-10-19 against `https://octodb.design-bakery.com` with a valid grant (token redacted):

```
$ curl -s -X POST -H "Authorization: Bearer $OCTO_GRANT" \
    -H 'Content-Type: application/json' \
    -d '{"label":"wan video generation ACCOUNT TOKEN","expiresInDays":1}' \
    https://octodb.design-bakery.com/api/vault/open/lease
{"error":"ROUTE_REQUIRED: that item has no relay route. Give it a url, or add a route from the dashboard."}

$ curl -s -X POST ... -d '{"itemId":"6e58ccb8-9eda-4771-896e-0395fb5461ea","expiresInDays":1}' ...
{"error":"ROUTE_REQUIRED: that item has no relay route. Give it a url, or add a route from the dashboard."}
```

The two endpoints that would resolve it are session-only, and the grant gets a generic auth failure rather than an authorization explanation:

```
GET  /api/vault/items/{id}                      -> 401 {"error":"UNAUTHORIZED: sign in to use the vault."}
POST /api/vault/items/{id}/routes               -> 401 {"error":"UNAUTHORIZED: sign in to use the vault."}
POST /api/vault/grants                          -> 401 {"error":"UNAUTHORIZED: sign in to use the vault."}
```

**Workaround:** the owner signs into the portal (Google/guest session), sets a URL on the item or adds a route, after which `open/lease` succeeds. Without that, the grant has no path to the secret.

## Evidence confidence

confirmed — directly reproduced against the live instance; the code path matches (`ensureDerivedRoute` returns no routes when `item.url` is null, so `mintLease` short-circuits at `ROUTE_REQUIRED`).

## Impact if unresolved

moderate — the advertised grant hand-off cannot serve the common imported-secret case (token with no URL). The platform itself is unaffected and the owner can recover manually from the dashboard, but an agent cannot self-serve and cannot even tell from the response that a dashboard action is required.

## Likelihood

observed — occurred on the first route-less item this session attempted; 74 items in the same cabinet share the shape.

## Exposure

active-production — the live instance at `octodb.design-bakery.com`; duration: since the grant/relay split was introduced (observed 2026-10-19).

## Recoverability

manual-recovery — owner login to the portal, then set `url` on the item or add a route; no data is lost or corrupted by the failed lease.

## Risk if the observation remains unresolved

Every route-less secret remains unusable by any grant, so the grant mechanism silently degrades into an inventory viewer. Because the failure is a 400 with a prose hint rather than a machine-readable prerequisite, an agent cannot programmatically distinguish "ask the owner to add a route" from "wrong label" or "expired grant", and the generic 401 on the item/route endpoints reads like a session-expiry problem rather than a credential-scope limit.

## Risk introduced by a proposed change

Accepting a caller-supplied `baseUrl` at lease time widens what a grant can reach: a leaked grant could exfiltrate the stored secret to an attacker-controlled origin via the relay. Mitigation: restrict the URL to an allowlist of known vendor origins, require HTTPS, and surface the derived route to the owner as a dashboard-visible artifact. Returning a structured error code alone carries no added risk.

## Release relevance

affects — the grant/relay capability is a productized slice; this is a contract gap within it, not a deploy blocker.

## Named product outcome and cost of delay

Outcome: "an agent holding a grant names a stored key and Octo mints one for it" (portal copy, `frontend` vault view). Cost of delay: agents must round-trip to the owner for every imported secret, defeating unattended use.

## Cost of delay

Owner-in-the-loop for each new credential; every agent session that hits a route-less item stalls until a human signs in.

## Smallest useful slice

Return a distinct, documented error code (e.g. `ROUTE_REQUIRED` with an `itemId` and a `requires: owner-dashboard` field) and document the prerequisite in the grant hand-off docs. Optionally allow `open/lease` to accept `baseUrl` + `authScheme` for a route-less token, gated by an origin allowlist.

## Reproducibility steps and evidence

1. Mint or obtain an `octo_vault_…` grant from the dashboard.
2. `GET /api/vault/open` with `Authorization: Bearer $OCTO_GRANT` → 200 with `items`.
3. Pick an item where `kind` is `token` or `login`, `hasSecret` is true, `url` is null, and `routes` is empty.
4. `POST /api/vault/open/lease` with `{"itemId":"<id>","expiresInDays":1}` → `400 ROUTE_REQUIRED`.
5. `GET /api/vault/items/<id>` and `POST /api/vault/items/<id>/routes` with the same grant → `401 UNAUTHORIZED: sign in to use the vault.`
6. Confirm `POST /api/vault/open/decoy` yields a grant flagged `decoy: true`, and that `open/lease` with it returns `403 FORBIDDEN: that grant cannot mint a working key.` — i.e. the self-service escape hatch is closed.

Observed result: the grant can see the cabinet but cannot reach or route the secret. Expected (per portal copy): the grant can mint a working key for a named stored key.

## Non-binding proposed next actions

*(proposal)*

- Add a structured error payload to `ROUTE_REQUIRED` that names the item and the required owner action, so an agent can surface an actionable message instead of retrying.
- Decide whether `open/lease` should accept `baseUrl` + `authScheme` for route-less items; if yes, constrain it to an allowlisted vendor-origin set and make the derived route owner-visible.
- Return `403 FORBIDDEN: a vault grant cannot call this endpoint` (or similar) from vault routes that require a session, instead of the generic `401 UNAUTHORIZED: sign in to use the vault.`, to distinguish scope limits from session expiry.
- Document the prerequisite ("item must have a URL or an existing route before a grant can mint a working key") in the grant hand-off documentation.
