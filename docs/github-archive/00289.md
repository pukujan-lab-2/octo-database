### Priority Rating

2.1 — the follow-up to #285 is a contract gap: the documented "retry with baseUrl" recovery is a no-op after the first attempt.

## Affected

Any agent that calls `POST /api/vault/open/lease` with a `baseUrl` for an item that already has a route — including the agent's own previous lease. In the observed case, the item `wan video generation ACCOUNT TOKEN` (`6e58ccb8-9eda-4771-896e-0395fb5461ea`) is now permanently bound to `https://dashscope-intl.aliyuncs.com/api/v1` because that was the first guess, and the correct region could not be tried.

## Observed consequence

First lease (no route existed) created the route and returned it:

```
POST /api/vault/open/lease
{"itemId":"6e58ccb8-...","expiresInDays":1,
 "baseUrl":"https://dashscope-intl.aliyuncs.com/api/v1","authScheme":"bearer"}
-> 201, routes[0].baseUrl = "https://dashscope-intl.aliyuncs.com/api/v1"
```

Second lease naming a different origin returned the **same** route with no error, no warning, and no indication the supplied value was discarded:

```
POST /api/vault/open/lease
{"itemId":"6e58ccb8-...","expiresInDays":1,
 "baseUrl":"https://dashscope.aliyuncs.com/api/v1","authScheme":"bearer"}
-> 201, routes[0].baseUrl = "https://dashscope-intl.aliyuncs.com/api/v1"   <-- supplied baseUrl ignored
```

The grant has no corrective path: `DELETE /api/vault/items/{id}/routes/{routeId}` sits behind `authenticateRequest`, so a grant gets `401 UNAUTHORIZED: sign in to use the vault.` The only remedy is the owner signing in and removing the route from the dashboard.

**Workaround:** owner logs into the portal and removes the route; the next lease then derives a fresh one from the supplied `baseUrl`.

## Evidence confidence

confirmed — reproduced twice against the live instance on 2026-10-19; the code path is unambiguous at `src/routes/vault.ts:751` (`if (existing.length > 0) return existing;` executes before `supplied?.baseUrl` is ever read at line 752).

## Impact if unresolved

moderate — the #285 recovery instruction ("Retry with baseUrl") is false after the first call. A single wrong guess by an agent permanently misroutes an item until a human intervenes, and the failure surfaces downstream as an opaque vendor error (`InvalidApiKey`) rather than a routing error, so the agent debugs the credential instead of the route.

## Likelihood

observed — occurred on the first retry in this session; any item that needs more than one origin attempt hits it deterministically.

## Exposure

active-production — live instance `octodb.design-bakery.com`; duration: since the #285 fix was deployed (observed 2026-10-19).

## Recoverability

manual-recovery — owner removes the route from the dashboard. No data is lost; the item and its secret are untouched.

## Risk if the observation remains unresolved

Misrouted items fail with a vendor authentication error that looks like a bad credential, so agents and owners are pushed toward rotating a working key that was never the problem. Because the wrong route persists in the owner's cabinet, it also shows up as legitimate configuration after the fact, making the misrouting hard to distinguish from intent during review.

## Risk introduced by a proposed change

Allowing a grant to overwrite or delete an existing route widens grant authority over the owner's cabinet: a leaked grant could repoint a stored secret at an attacker-controlled origin, and the relay would forward it. Mitigation: scope route mutation to routes the same grant derived (`name` suffix `(from lease)`), reject overwriting owner-authored routes, and return a structured conflict instead of a silent success. Separately, note that the existing #285 behavior already lets a grant bind a secret to an arbitrary `baseUrl` on first use — that surface predates this issue and is not changed by fixing the pinning.

## Release relevance

affects — the grant/relay slice's recovery contract; not a deploy blocker.

## Named product outcome and cost of delay

Outcome: an agent holding a grant can make a route-less stored key usable without owner involvement (#285). Cost of delay: the first guess is final, so the capability works only when the agent guesses the origin correctly on the first attempt.

## Cost of delay

Every mis-guessed origin requires an owner dashboard session; the agent cannot self-correct and cannot report the actual cause from the API response.

## Smallest useful slice

When `supplied.baseUrl` differs from the existing derived route's `baseUrl`, either (a) update that route if it was grant-derived, or (b) return `409 ROUTE_CONFLICT` with `existingBaseUrl` and the route id so the caller knows the supplied value was not applied. Option (b) alone removes the silent-failure trap and costs no new authority.

## Reproducibility steps and evidence

1. Take a grant and an item with `url: null, routes: []`.
2. `POST /api/vault/open/lease` with `{"itemId":"<id>","expiresInDays":1,"baseUrl":"https://origin-a.example/api/v1","authScheme":"bearer"}` → `201`; the returned route carries `origin-a`.
3. `POST /api/vault/open/lease` with the same body but `baseUrl: "https://origin-b.example/api/v1"` → `201`; the returned route still carries `origin-a`, with no error field.
4. `DELETE /api/vault/items/<id>/routes/<routeId>` with the grant → `401 UNAUTHORIZED: sign in to use the vault.`
5. `GET /api/vault/open` → the item shows the `origin-a` route persisted.

Observed result: the second `baseUrl` is discarded silently and the grant cannot remove the route.
Expected: either the derived route is repointed, or the conflict is reported.

## Non-binding proposed next actions

*(proposal)*

- Compare `supplied.baseUrl` against the existing derived route and return `409 ROUTE_CONFLICT` with the current `baseUrl` and `routeId` when they differ, instead of a silent `201`.
- Consider allowing a grant to repoint or delete routes whose name ends in `(from lease)`, leaving owner-authored routes immutable.
- Include the effective `baseUrl` in every lease response alongside the route, so callers can assert what was actually applied.
- Document that `baseUrl` is only honored when no route exists yet.
