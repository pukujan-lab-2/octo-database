## Summary

Closes #289. A working key was pinned to one route's base URL, and a lease-time `baseUrl` was silently discarded once any route existed — the agent had no way to correct a misrouted item, and an item with no url could not be used at all.

A working key is now a **free-form credential**:

- The lease records *how* to inject the secret (`auth_scheme`, `auth_header`, `body_field`, `basic_username`) plus an optional default upstream (`base_url`). Migration `20261019200000_vault_lease_free_target.sql` adds those columns and `octo.consume_vault_lease_by_key`.
- New `ANY /api/vault/proxy[/<target>]`: the caller names any `http(s)` target in `x-octo-target`, `?target=`, or the path after `/api/vault/proxy`. A relative path resolves against the lease's default upstream.
- `POST /api/vault/open/lease` no longer requires a route or an item url, and no longer invents an auto route. A lease-time recipe wins, then an existing dashboard route, then the item's own url. The response carries `proxy: { url, targetHeader, defaultTarget }`.
- Dashboard routes keep working through `ANY /api/vault/relay/<routeKey>/…`; the relay and the proxy share one forwarding path.
- `docs/consuming-octo.md` documents the proxy as the primary way to spend a working key.
