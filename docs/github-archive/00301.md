### Affected App, Adopter, Users, or Systems
Octo workspace consumers wanting general-purpose RAG across notes, code, research, contact records, or documents; specifically the separate `Pukujan/private-context-storage` consumer and Octo's document RAG endpoints.

### Observed Consequence and Workaround
**Observed in source:** Octo `src/routes/rag.ts` embeds a query and calls `dbMatchChunks`; the SQL `octo.match_chunks` ranks via pgvector cosine distance. No BM25/FTS+vector rank fusion was found in the inspected built-in RAG query path. The consumer `Pukujan/private-context-storage/engine/retrieve.py` separately implements LlamaIndex BM25 over selected source documents. Those BM25 and Octo vector corpora need not contain the same documents, versions, or chunks.

**Already working:** Octo semantic retrieval was queried read-only through MCP on 2026-10-22 and returned scored matches with `qwen3-embedding:0.6b`, provenance IDs, and paragraph-aware chunker metadata. Do not describe embeddings or document RAG as absent.

**Potential consequence:** Keyword-sensitive questions (identifiers, exact names, technical strings) may lose recall under vector-only querying. This is a hypothesis, **not a measured retrieval defect**. Workaround: consumer-specific BM25 over readable Octo documents or exact SQL/file reads; graph/SQL remain authoritative for structured counts/status.

### Risk if the Observation Remains Unresolved

### Risk Introduced by a Proposed Change
An always-on cross-service hybrid engine could duplicate a consumer's retrieval logic; corpus/version mismatches could generate misleading fused ranks; indiscriminate RAG use could corrupt exact SQL/ledger-based counts or status reasoning.
