### Affected App, Adopter, Users, or Systems

### Observed Consequence and Workaround
**Implemented in source:** `src/analytics/engine.ts`, `src/analytics/registration.ts`, `src/analytics/job.ts`, `src/routes/analytics.ts`, and `src/mcp/server.ts` implement an ephemeral in-process DuckDB engine over caller-registered, immutable Parquet parts in Octo storage, plus MCP tools `register_dataset`, `query_dataset`, `get_analytics_query_status`, `get_analytics_result`.

**Observed connected-client gap:** On 2026-10-22 ChatGPT's Octo connection listed **25 tools** and did **not** expose any of the four analytics tools, while repository MCP code registers **29 total**. Therefore the owner could not initiate the existing MCP analytics workflow from that particular connection. This **does not prove** the deployed Octo server lacks analytics; tool schema refresh, deployment revision, or connector manifest mismatch are unresolved.

**Separate capability limit (by design):** `src/analytics/specs.ts` currently offers only `job-failures-by-type-month@1` over registered Parquet containing `job_type`, `state`, `created_at`. A request for arbitrary analytical SQL or ad hoc counts across other datasets is not implemented by this named-spec surface. The existing workspace PostgreSQL SQL tool queries a **different**, operational store and does not replace DuckDB-over-Parquet.

**Available workaround:** Use existing Octo HTTP analytics routes if deployed; consumers may use their existing own analytics clients. The full path cannot be proven from the connected ChatGPT MCP session.
