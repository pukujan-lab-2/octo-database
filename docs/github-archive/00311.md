## Summary

Closes the gap identified in #301. `POST /api/rag/query` was vector-only: it embedded the question and ordered chunks by cosine distance, so an exact identifier (`ZQX-7741-OMEGA`, an error code, a UUID) could only surface if the embedding model happened to place it near the query — which it usually does not.

Retrieval now runs two arms over the same `octo.chunks` rows and fuses their rankings:

- **Lexical arm** — a generated `content_tsv` column with a GIN index. The query is built by unnesting `to_tsvector` of the *same* config that produced the indexed vectors, so punctuation and stopwords are handled identically on both sides, and each lexeme is quoted so operator characters cannot reach the tsquery grammar.
- **Vector arm** — the existing HNSW cosine index.
- **Fusion** — Reciprocal Rank Fusion, k=60. Each arm contributes 4×`limit` candidates so a chunk mid-ranked by one arm but top-ranked by the other still fuses in.

RRF rather than a weighted score sum because `ts_rank` and cosine similarity are not on a comparable scale; any fixed weight would be a tuning guess.

Both arms read one table, so the corpora cannot drift apart. The lexical arm does not join `octo.embeddings`, so a chunk whose embedding is missing stays findable by text. `octo.match_chunks` is preserved as the vector-only primitive.

## API

Response gains `mode: "hybrid"`. Each match reports which arms found it:

| field | meaning |
|---|---|
| `similarity` | cosine similarity, `null` for a lexical-only match |
| `lexicalScore` | `ts_rank`, `null` for a vector-only match |
| `score` | RRF score, always present |

A consumer that only reads `similarity` still works; the NULL pattern says which arm produced each row.
