### Summary

A parked future direction for how Octo delivers vendor credentials to publicly hosted sites (e.g. `nyc.design-bakery.com`) without the real key ever living on the public host. Today such a site holds the vendor key in its environment on the owner's Mac. The researched direction is: the site holds only a short-lived `octo_tmp_` working key, Octo's proxy injects the real secret server-side, and the working key is re-minted on a schedule or per job so any leak is self-limiting.

This record parks the direction and states what is not yet decided or built. It asserts no defect: the current vault works as designed for agents. It exists so a future slice can reopen the question with the evidence gathered on 2026-10-28, and so the open research questions are not lost.

Out of scope for this record: the separate task of a marketing/showcase page and demo video about this direction. That is tracked separately.

### What was actually researched

A talk outline for "Letting AI agents use credentials they never see" (Chase Erickson, Solutions Engineer, Infisical) describes Infisical's Agent Vault: secrets are stored in Infisical, a secret sync pushes them into the Daytona org and keeps them current including rotation, and a proxy adds the credential to requests bound for configured services so the agent never sees it.

Octo's vault already implements the same core mechanism: the caller holds an `octo_tmp_` working key, and `/api/vault/proxy` decrypts the stored item and injects it into the upstream request (`src/routes/vault-relay.ts:234-295`, `src/lib/relay-egress.ts:222-255`).

### Findings about the current implementation

These are properties of the code as it stands, recorded because each one constrains the parked design.

**Sub-day rotation is not currently expressible.** `parseLeaseDays` accepts only a whole number of days from 1 through 30 (`src/lib/vault-policy.ts:73-85`); grants are clamped to 5 through 72 hours (`src/lib/vault-policy.ts:14-18`). An hourly re-mint cadence therefore requires a units change, not a smaller constant.

**Concurrent workers cannot hold leases on the same item under the same grant.** `idx_vault_leases_active` is a partial unique index on `(parent_grant_id, item_id) WHERE revoked_at IS NULL` (`db/migrations/20261017200000_vault_routes_and_leases.sql:58-59`), and `dbInsertVaultLeaseService` revokes the prior lease for that pair inside the mint transaction (`src/server/db.ts:3217-3223`). Per-job minting by two workers on the same item would therefore revoke each other's keys. This is the main structural blocker for a per-job model.

**Vendor-secret rotation is already instant, for free.** `consume_vault_lease_by_key` joins `octo.vault_items` and returns `secret_encrypted` live (`db/migrations/20261019200000_vault_lease_free_target.sql:41-59`), so updating an item's secret takes effect on every outstanding lease's next request with no propagation step and no re-mint. This is a genuine advantage over a sync-based model, which must push the new value.

**Revocation cascades.** `vault_leases.parent_grant_id` references `vault_grants(id) ON DELETE CASCADE` (`db/migrations/20261017200000_vault_routes_and_leases.sql:47`), so deleting a grant removes every lease minted from it.

**Egress target is unconstrained.** `resolveTarget` accepts any absolute `http(s)` URL the caller names (`src/routes/vault-relay.ts:204-227`), and `buildProxyRequest` performs no host check (`src/lib/relay-egress.ts:222-255`). There is no allowlist and no check against loopback, RFC1918, or cloud-metadata addresses. A leaked working key can therefore direct the real secret at an arbitrary endpoint. This was a deliberate 2026-10-19 decision (PR #292) to make the working key free-form; whether it is acceptable for a public-facing site is an open question below, not a defect in the agent-facing design.

**No rate limit on the proxy.** `/api/vault/proxy` forwards every request and there is no per-lease or per-principal throttle. On a public site, each visitor request spends the owner's vendor quota.

**Streaming already works.** `forwardUpstream` pipes the upstream body through to the response (`src/routes/vault-relay.ts:151-198`), so SSE and long LLM responses pass through unchanged.

**Workspace scoping is an exact match, not a hierarchy.** `dbListVaultItemsForGrant` filters `workspace_id IS NOT DISTINCT FROM $2::uuid` (`src/server/db.ts:2946-2958`), so a workspace-scoped grant sees only that workspace's items and an account-scoped grant sees only account-level items. A workspace's agent cannot fall back to an account-wide item.

**Grants are inventory-only.** A grant lists items (label, kind, url, `hasSecret`, routes) and mints leases; it never returns a stored secret (`src/routes/vault.ts:143-155`, `:688-709`). This is what makes it safe to leave a grant on a host as the standing credential while leases stay short-lived.

**At rest** items are AES-256-GCM sealed with a key derived from `OCTO_MFA_SECRET` (`src/lib/mfa.ts:58-84`), the same key material as TOTP. There is no rotation of that key.

### The three deployment shapes considered

- A. Octo pushes a new working key into the site's environment. Requires write access to the host and a restart, because environment changes are only read at process start. Rotation cadence becomes deploy cadence.
- B. The site holds a grant and mints its own leases. The site calls `/api/vault/open/lease` at start and re-mints before expiry. Nothing is pushed; the standing credential is a grant, which cannot read a secret. Deleting the grant cascades to every lease.
- C. The site runs inside an Octo-managed container. No credential on the public host at all; the vendor secret never crosses a network boundary. This is a deployment-platform capability, materially larger than the vault, and not scoped here.

### Comparison against the Infisical model, as described in the talk

Where Infisical appears ahead, per the talk outline (not verified against its documentation):

- Workload identity. Infisical's agent authentication is described as using OIDC, Kubernetes service accounts, or cloud identity rather than a static token in an environment variable. Octo has no equivalent; every path ends in a static `octo_vault_` or `octo_tmp_` string on disk.
- Rotation as a product feature. Infisical rotates and propagates. Octo does not rotate.

Where Octo is ahead:

- Vendor-secret rotation is instant with no propagation (the live join above).
- Revocation cascades from one grant to all its leases.
- The stored secret never leaves Octo, whereas a sync model places copies in the consuming platform.

Where they are equivalent: for a public site on the same host, a temp key and an ordinary environment variable grant the same vendor access to anyone with code execution on that host. The difference is that a leaked temp key is revocable without a vendor rotation.

### Open research questions

1. Should the hourly/per-job cadence be a units change to the lease policy, and what default should a queued workload get versus a long-running service?
2. Should concurrent leases per `(grant, item)` be allowed, or should each job get its own grant, given the unique index and the revoke-on-mint behaviour?
3. Should a lease carry an allowed-host list for the free-form proxy, and if so is it per lease, per item, or per grant?
4. Does a public-facing deployment need a proxy rate limit separate from any existing principal-level limits?
5. Is workload identity worth adopting, and from where, so a hosted site need not store a long-lived grant?
6. Is the container-deployment shape (C) in scope for Octo at all, or is it a separate product?
7. Does `OCTO_MFA_SECRET` need its own rotation story now that it seals user credentials and not only TOTP seeds?

### Hypotheses (unverified)

- (hypothesis) Per-job minting is the strongest fit for queued workloads, because the leak window equals job duration rather than a fixed interval. Experiment to confirm: measure whether the unique-index constraint can be relaxed without weakening revocation.

### Counter-signal

The current free-form proxy target was a deliberate owner decision on 2026-10-19 (PR #292) to stop pinning working keys to routes. Any move toward host binding would partly reverse that, so the benefit must be weighed against the ergonomics it was introduced to provide.

### Honest Caveat

The Infisical comparison rests on a public talk outline, not on Infisical's documentation or a hands-on evaluation. Claims about its workload identity and rotation are as described in that outline and may be incomplete. Nothing here establishes that the parked direction is better than the current deployment; only that the differences are understood well enough to research further.
