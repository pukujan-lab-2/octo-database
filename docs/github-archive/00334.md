### Summary

The credential-plane film (`/credential-plane`) markets four credential capabilities that are not built yet. This log records them so they can be discussed and scheduled rather than silently living only in the marketing copy.

The direction, as the owner stated it:

1. **Per-service minted keys, auto-renewing.** A master/setup key wires every environment once and mints each service its own key. The minted key renews itself on a schedule and keeps working. The master key can then be thrown away — it expires in minutes to bound blast radius — and nothing that survives setup can reach the vault.
2. **One rotation, one surface.** Rotation happens from the Octo dashboard only, not per vendor.
3. **Live access logs per minted key.** Every use is recorded: which key, where it was called from, and how.
4. **Leak detection and notification.** Octo notices a key used from an unknown location or otherwise anomalous activity and raises a system notification.

The film shows all four as if shipped. That was an explicit owner decision ("we dont have it yet we are allowed to use this for hype").

### Acceptance Criteria

- [ ] A setup key can be issued with a short TTL (minutes to one hour) and expires on its own after wiring environments. (proposed)
- [ ] A minted per-service key can be issued with an auto-renewing lease and keeps working after the setup key expires. (proposed)
- [ ] The dashboard lists minted keys with last-use, source location, and renewal state. (proposed)
- [ ] Rotation of a minted key is initiated from the dashboard. (proposed)
- [ ] Anomalous-source use of a minted key produces a notification. (proposed)

### Boundaries and Next Action

Out of scope for this log: the film, the site copy, and any credential-plane UI change. This is a capability record, not a slice packet.

Next action: decide which of the four is the smallest useful slice and open a slice packet for it.
