### Summary

**Bug (verified):** document search never sees part of every document. When `chunkText` ends a chunk early at a paragraph or sentence break, the next chunk still starts 700 characters after the previous start. Everything between the early end and that next start is put in no chunk, so lexical and vector search can't find it.

On one real 13,961-character note, 1,002 characters (7.2%) are in no chunk, including six of its 32 section headings. Searching the live instance for text in those headings returns 20 matches, and none of them contains the text.

**Gaps (proposals; none of this exists yet).** These came up while using Octo for research records:

1. Chunk Markdown on headings, so one chunk holds one section.
2. Search over claim statements, not only documents.
3. A way to say how evidence is known (measured, primary source, secondary, inference) on evidence or claims.
4. A subject filter on `claims-as-of`, and return `subjectEntityId` in its rows.

### Symptoms

- `POST /api/rag/query` for a phrase that is in a document returns chunks from that document, but none containing the phrase.
- The document version reports `chunkCount: 20`; the union of those chunks does not cover the document.

### Hypotheses (unverified)

- H1: All documents with paragraph or sentence breaks are affected at a similar rate (about 5–10% of text). Only one real document and one synthetic input were measured.

### Counter-signal

- Plain text with no `\n\n` or `. ` in the second half of each 800-character window has no gaps, which is why the current test passes.

### Honest Caveat

- The proposed fix was checked on a patched copy of `pipeline.ts`: the note goes to 26 chunks and 0 gaps, the minimal input to 0 gaps. It was not run against the repo's test suite.

### Problems vs Gaps

- **Problem (demonstrated):** the chunk-gap bug above.
- **Gaps (not defects):** heading-aware chunking, claim search, a source-quality field, subject filter on `claims-as-of`. Each would make research retrieval precise; none is broken today.

### Reproducibility Steps and Evidence

1. Minimal, offline, using the repo's own function (run with `./node_modules/.bin/tsx` from the repo root):

   ```ts
   import { chunkText } from './src/rag/pipeline.ts';
   const text = 'a'.repeat(500) + '\n\n' + 'b'.repeat(1500);
   const chunks = chunkText(text, { chunkSize: 800, chunkOverlap: 100 } as any);
   let covered = 0;
   for (const c of chunks) {
     if (c.startOffset > covered) console.log('gap', covered, c.startOffset);
     covered = Math.max(covered, c.endOffset);
   }
   ```

   Output: `gap 501 700`. The first chunk ends at the paragraph break (501), the second starts at 700.

2. The same check on the real note: 13,961 characters, 20 chunks, 8 gaps, 1,002 characters (7.2%) not in any chunk. Gaps contain the headings of findings F5, F7, F11, F15, F18 and F28.
3. Live: `POST /api/rag/query` with `"69 of 137 merged PRs"` and with `"No stack repo has a milestone, no issue has an issue type"` → 20 matches each, 0 contain the phrase. `GET /api/rag/documents/<id>` → `chunkCount: 20`.

**Suggested fix** *(proposal)*: start the next chunk from where this one ended, keeping the overlap and always moving forward:

```ts
if (end >= normalized.length) break;
start = Math.max(end - overlap, start + 1);
```
