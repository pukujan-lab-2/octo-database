### Summary

**Proposal**: a one-line **env pull**. A machine or agent fetches the secrets it needs from the Octo vault with its agent key and writes them into the process environment or a `.env` file. The vault becomes the only source of truth, and the hand-kept copies stop being authoritative: `~/Documents/projects/.env` on the Air and `~/.hack_env` on the MacBook Pro.

### Identity and Lineage

- Leaf issue: this issue. Depends on: 360. Related: #334, #358 (`scripts/import-env-to-vault.ts`).
- Platform side: server-management plan, phase 3.

### Symptoms

1. On 2026-10-30, 28 secrets were imported from both machines' env files. The owner's vault now holds 207 items, but every machine still reads its own file. *(verified)*
2. A new secret today has to be appended by hand to each machine's file. The Komodo key was copied to both machines manually. *(verified)*

### Proposed shape (hypothesis)

- An endpoint returns the vault items selected by label or by a named set, for a key with the vault-read power.
- A small script or MCP tool: `octo env pull [set] > .env` or `eval $(octo env pull --export [set])`.
- Named sets per machine or app, e.g. `komodo` or `nyc-map-agent`, so an app pulls only what it needs.

### Acceptance Criteria

- [ ] A fresh machine with only an agent key gets a working `.env` for a named set in one command. (proposed)
- [ ] Adding a secret in the dashboard reaches the next pull with no file edits. (proposed)
