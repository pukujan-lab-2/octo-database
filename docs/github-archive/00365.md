# Issue #365: [ISSUE]: Retrieval needs file ingest with table structure, page positions on chunks, and optional reranking

- Labels: observational-issue, proposal, account:owner, needs-filer-stamp, needs-impact-evidence, needs-issue-type, needs-priority-definition, needs-record-context, needs-record-schema, needs-release-relevance, ontology:project-1.0.0, status:resolved, needs-lifecycle-status, ontology:oio-1.1.0

### Summary

Octo's retrieval accepts plain text only and stores chunks without their source position. An adopter that loads real manuals (PDFs with tables, scanned pages) has to do the hard part of retrieval outside Octo: reading the file, keeping tables intact, and tracking page numbers. This proposes three platform additions; each can be accepted, split or closed on its own.

Evidence from the chatbots/website-copilot project (Pukujan/voice-agent-research), IRS Publication 17 (2025), 7 PDF pages, 18 questions written before any run, 12 of them answered from tables:

- The same pages loaded as our own plain-text passages answered 13/18; loaded through Docling (layout and table structure) they answered 18/18, 14/18 when graded strictly. The misses came from tables flattened into lumps and sentences cut across chunks, not from misread characters.
- Page numbers only survive because the adopter writes `[page N]` into the text by hand and parses it back out.

### Proposals

1. **File ingest with structure.** `POST /api/rag/documents` (or ingest from an uploaded file, which also closes #227) accepts PDF/DOCX/images and runs a local layout-aware parser (for example Docling, or a document vision model such as PaddleOCR-VL, Apache-2.0) so tables come out row by row with their column names. Runs on the operator's hardware; documents never leave it.
2. **Source position on every chunk.** Store page number (and optionally the bounding box) per chunk and return them with each match, so apps can cite "page 97" without embedding markers in the text.
3. **Optional reranking.** An opt-in second pass over the top candidates (a small local cross-encoder) before `limit` is applied.

Out of scope, stays in apps: deciding whether a passage answers the question, quoting, and saying "I don't know".

### Acceptance Criteria

- [ ] (1) Ingesting a PDF with a table returns chunks where each table row keeps its header labels; a table is never split mid-row.
- [ ] (1) For digital PDFs, every number in a parsed chunk appears in that page's PDF text layer (a cheap check that catches parser or vision-model misreads) (proposed).
- [ ] (2) Each match from `/api/rag/query` carries `page` (and `bbox` when known).
- [ ] (3) With reranking on, results are reordered but the response shape is unchanged; off by default.
- [ ] Text ingest keeps working exactly as today.

### Boundaries and Next Action

Out of scope: hosted/cloud parsers (documents must stay on the operator's machines); answer judging.
Next action: the owner decides which of 1–3 to accept; each becomes its own slice.

## Impact evidence from an adopter (website copilot, manual-guidance mode)

We ran the same 18-question test on IRS Pub 17 (7 pages: 2 filing-requirement tables, the standard-deduction tables, and text). 12 questions need a table cell, 3 need text, and 3 should get "I don't know". Each loader's passages went into Octo RAG in the same workspace, and the same answer step ran on top (Jev picks the passage and the sentences to quote).

| How the PDF was turned into passages | Score | Table questions |
|---|---|---|
| Plain text layer + Octo's character chunker | 13/18 | 7/12 |
| Docling (layout + table structure, CPU) | 18/18, but 4 passes quoted merged table cells, so 14/18 strictly | 12/12 (8 clean) |
| PaddleOCR-VL-1.6 (vision model), table rows kept one per line | **17/18** | **11/12** |

What this shows:
- **Character chunking breaks tables.** A row like "Married filing jointly, both 65 or older: 34,700" gets cut or separated from its column headers, so the right number is never retrieved. Only 7 of 12 table questions passed.
- **Structure-aware ingest fixes most of it.** Both parsers that keep table rows together passed 11–12 of 12.
- **Every adopter that loads PDFs, forms or manuals hits this.** That's why we think it belongs in Octo ingest (#227, #357) rather than in each app.

## What worked, as a concrete proposal

1. **Reader:** PaddleOCR-VL-1.6. It's #4 on the OmniDocBench leaderboard (96.34, TableTEDS 94.76), 0.9B parameters, Apache-2.0.
   - The native Paddle pipeline was heavy: about 14 GB RAM plus the full 8 GB GPU on an RTX 4060 laptop.
   - The same model runs in llama.cpp (supported since build b8110, GGUF available) in about 1–2 GB, on CUDA, Apple Metal or CPU.
   - Suggested deployment: a reader service that tries a GPU host first and falls back to CPU. Ingest is a batch job, so a slow fallback is fine.
2. **Passages:**
   - Each table row is one line, cells joined with " | ".
   - Long tables are split by rows, repeating the header row in each piece.
   - Each passage stays under the chunk size, so it's never re-split (#357).
   - Each passage is tagged with its source page.
3. **Safety check before indexing:**
   - Every number in a passage must appear in that page's PDF text layer; otherwise the passage is flagged and not indexed.
   - On this test, 0 of 89 passages were flagged.
   - For scans with no text layer: two readers must agree, and the owner reviews the pages where they disagree.
4. **Return with each match:** `documentId`, `title` and page (see also #364), so apps can cite "page 9".

## Priority from our side

High for any manual or document-answering adopter. Without this, the copilot either answers "I don't know" to table questions or each app has to run its own OCR stack outside Octo, which is the duplication the platform is meant to remove.

Remaining misses, for completeness:
- PaddleOCR-VL: 1 miss. The answer was in a footnote under the table, and it ended up in a separate passage from the table.
- Docling: merged several rows of one table into a single passage.
