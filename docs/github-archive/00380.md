# Issue #380: [ISSUE]: Embedding model loads with a 32k context and takes ~5.8 GB on the Pro; cap it at 2k

- State: closed (2026-10-31)
- Opened by Pukujan on 2026-10-31
- Original: https://github.com/Pukujan-lab/octo-database/issues/380
- Labels: observational-issue, proposal, account:owner, needs-filer-stamp, needs-impact-evidence, needs-issue-type, needs-priority-definition, needs-record-context, needs-record-schema, needs-release-relevance, ontology:project-1.0.0, status:open, needs-lifecycle-status, ontology:oio-1.1.0

### Summary

The embedding model on the Pro (`qwen3-embedding:0.6b`, served by Ollama) loads with its full 32,768-token context. Each time it loads it takes about **4.2–5.8 GB of RAM** on a 16 GB machine that also runs Octo, design-bakery, the PaddleOCR reader and other services. Octo's passages are 800 characters (`chunkSize: 800` in `src/routes/rag.ts` and `scripts/reembed-rag.ts`, about 200–250 tokens) and queries are one sentence, so almost all of that reserved memory is never used.

Observed 2026-10-30 on `mac-pro`:
- `ollama ps`: `qwen3-embedding:0.6b  5.8 GB  100% GPU  CONTEXT 32768`
- The Ollama `llama-server` process RSS was 4,194 MB, and system-wide free memory dropped to 17% while it was loaded.
- `ollama show`: 595.78M parameters, Q8_0, so the weights are about 0.6 GB. The rest is the context reservation.

It is loaded on demand and unloads after Ollama's keep-alive (about 5 minutes), so this is a spike on every search or indexing burst, not a constant drain. The spikes are what squeeze other services on the box.

### Proposal

Cap the embedding context at **2,048 tokens**: several times the largest passage, and expected to bring each load to about 1–1.5 GB. `embedTexts` calls the OpenAI-compatible `/v1/embeddings`, which cannot pass `num_ctx`, so the options are:
1. An Ollama model variant with `PARAMETER num_ctx 2048` (for example `qwen3-embedding:0.6b-ctx2k`), with `OCTO_EMBEDDING_MODEL` pointed at it. Same weights, so the vectors are unchanged for inputs under 2,048 tokens. Check whether a changed model name makes Octo treat existing rows as a different embedding config.
2. Set `OLLAMA_CONTEXT_LENGTH=2048` for the Ollama app on the Pro. This is simplest, but it affects every Ollama model there.
3. Call Ollama's native `/api/embed` with `options.num_ctx`.

Optional: also set a short keep-alive, or `OLLAMA_NUM_PARALLEL=1` if parallel slots multiply the reservation.

### Acceptance Criteria

- [ ] `ollama ps` shows the embedding model at a 2,048 context, using about 1.5 GB or less.
- [ ] Before the change, the largest stored chunk is confirmed to be under 2,048 tokens. Inputs over the cap must not be silently truncated, or the cap must be raised.
- [ ] Search results are identical before and after on a fixed query set (same weights, so the vectors should be identical).
- [ ] No re-embed is triggered unless one is needed.

### Boundaries and Next Action

Out of scope: changing the embedding model or dimensions.
Next action: the owner picks option 1, 2 or 3; the Octo session applies it on the Pro and verifies.

### Symptoms

RAM on the Pro drops sharply (to 17% free) whenever Octo searches or indexes; other local models (LFM3 for the copilot, the PaddleOCR reader) compete for what's left.

### Hypotheses (unverified)

The default 32k context comes from the model's metadata; Ollama sizes its working memory (KV cache) for the full context and for each parallel slot.

### Honest Caveat

The 1–1.5 GB figure is an estimate, not measured yet.

**Pukujan commented, 2026-10-31**

Done on the Pro (owner chose option 1).

**One change to option 1:** the model name is part of each workspace's `octo.embedding_configs` row (`model = qwen3-embedding:0.6b`), so a new name such as `…-ctx2k` would have made searches miss every stored chunk until a full re-embed. Instead the same tag was rebuilt with the cap, so Octo's config is untouched:

```
ollama cp qwen3-embedding:0.6b qwen3-embedding:0.6b-orig     # backup, shares the same blobs
# ~/embed-check/Modelfile: FROM qwen3-embedding:0.6b-orig / PARAMETER num_ctx 2048
ollama create qwen3-embedding:0.6b -f ~/embed-check/Modelfile
```

**Results (2026-10-31 on mac-pro):**
- [x] `ollama ps`: 2.1 GB at CONTEXT 2048, down from 5.8 GB at 32768. The `llama-server` RSS is **1,107 MB**, down from 4,194 MB.
- [x] Largest stored chunk: 837 bytes (2,250 chunks), far under 2,048 tokens. Chunks are capped at 800 characters, so nothing gets truncated.
- [x] Vectors before and after, for two sample queries and the longest stored chunk: cosine 1.00000000, max element difference 0. Search results cannot change.
- [x] No re-embed; `OCTO_EMBEDDING_MODEL` and the API container are unchanged. A live `/api/rag/query` returned 200 with the source chunk ranked first.

**Caveat:** `ollama pull qwen3-embedding:0.6b` would bring back the 32k default; re-run the `ollama create` line after any pull.
