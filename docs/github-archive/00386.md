# Issue #386: Store embeddings as halfvec at 512 dimensions (about 4x smaller vectors and index)

- State: closed (2026-10-31)
- Opened by Pukujan on 2026-10-31
- Original: https://github.com/Pukujan-lab/octo-database/issues/386
- Labels: status:resolved

## Why

Embeddings are most of Octo's database, and ordinary compression does not shrink them. Measured on the Pro, 2026-10-31:

| Table | Raw embeddings (TOAST) | HNSW index | Text |
|---|---|---|---|
| `legal_graph.chunk` (807k rows) | 4.5 GB | 6.3 GB | 1.5 GB |
| `octo.embeddings` (96k rows, now 133k) | 0.54 GB | 0.8 GB | small |

That is about 14 KB per chunk. The HNSW index also has to sit in RAM to be fast. The new server (OVH SYS-1, 32 GB) runs Postgres next to many other services.

## Work requested

Do both steps in one change, so existing data is converted once:

1. **`halfvec`.** Store embeddings as pgvector `halfvec` (16-bit) and build the HNSW index on `halfvec`. Halves vectors and index.
2. **512 dimensions.** `qwen3-embedding` is trained for shorter vectors (Matryoshka), so cut 1024 to 512 dimensions. Halves them again.

Existing rows convert in place, with no re-embedding: `l2_normalize(subvector(embedding::halfvec, 1, 512))` (pgvector 0.8.6 is installed). Query embeddings must be cut and normalized the same way (`OCTO_EMBEDDING_DIMENSIONS`, or truncate in `src/rag/embeddings.ts`). New workspaces get the new format by default.

Expected: about 4x smaller vectors and index, roughly 14 KB to 3-4 KB per chunk, and the legal index from 6.3 GB to about 1.5-2 GB (estimates).

## Done when

- Existing workspaces are converted, the HNSW index is rebuilt, and search still answers.
- Recall on existing RAG queries, checked before and after, is close (top results largely the same).

Related: #389 (disk-based index), #391 (filtered search scans every vector).
