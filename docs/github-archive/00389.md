## Later, when vectors outgrow RAM

After `halfvec` and 512 dimensions (#386), the next step is an index that lives on disk rather than in RAM, so vector search no longer competes with the many services on the server for memory.

- **VectorChord** (`tensorchord/vchord-postgres`, RaBitQ quantization) is the first choice: a Postgres extension, same SQL, index on NVMe. **pgvectorscale** (StreamingDiskANN) is the alternative.
- The quantized index gives approximate order; the reranker (#365, and the server fallback in the reranker issue) restores the final order.
- Needs NVMe. The new server (OVH SYS-1) has 2×512 GB NVMe.

## When to do it

When the HNSW index no longer fits comfortably in the RAM Postgres gets, or when one workspace reaches millions of chunks. Not before.

## Done when

A large workspace (the legal one, 807k chunks) searches through the disk index at about the same recall as HNSW, with the index's RAM use a fraction of today's 6.3 GB.
