# Issue #391: RAG: filtered search scans every vector (slow on big workspaces)

- State: open
- Opened by Pukujan on 2026-10-31
- Original: https://github.com/Pukujan-lab/octo-database/issues/391

## Problem

Filtered RAG search (`/api/rag/query` with `filter.titlePrefix`, `documentIds` or `latestVersionOnly`) skips the HNSW index and compares the query with every embedding in the workspace. Time grows with workspace size.

`octo.match_chunks_hybrid` sorts the filtered branch by `(e.embedding <=> query_embedding) + 0`, which forces an exact scan over the allowed chunks.

## Measured on the Pro (2026-10-31)

Chatbots factory workspace, 131k embeddings (32k titled `irs/`), timed while a bulk ingest was also running:

| Search | Time |
|---|---|
| No filter | ~1.6 s |
| `titlePrefix: "irs/"` | ~1.0 s (vector half alone: 2.0 s exact) |
| `latestVersionOnly: true` | ~6.8 s |
| Same `irs/` vector half with `hnsw.iterative_scan = relaxed_order` and no `+ 0` | 0.9 s |
| Live site queries (`titlePrefix`) in `pg_stat_activity` | ~50 s |

The chatbots README already notes "about 15 s per query at 32,000 passages".

The live ~50 s is unexplained: the same call from psql takes 1–7 s, and table statistics are fresh. Possibly contention with the ingest, or different parameters from the site. Worth an `EXPLAIN (ANALYZE)` of a real call.

## Possible fix

pgvector is 0.8.6, which supports iterative index scans. Let the filtered branch use the index (drop `+ 0`, set `hnsw.iterative_scan` on the function). Also check the `latestVersionOnly` subquery, which runs once per row.

## Done when

A filtered search on a ~130k-chunk workspace returns in about the same time as an unfiltered one.

Root cause of the unexplained ~50-80 s: row-level security called `octo.is_workspace_member()` once per row for the request role (0.7 s as owner vs 80.3 s as `octo_app`). Fixed in #396 (access checked once per search). Applied live on the server 2026-10-31: `/api/rag/query` 80 s → 1.3 s. The filtered-branch `+ 0` exact scan from this issue is still open.

**Pukujan commented, 2026-11-01**

**New measurements for this issue: a search narrowed to one business's whole prefix takes 2.1 s at 200,000 chunks, against 0.24 s unfiltered, and three separate steps of `match_chunks_hybrid` each cost about 0.75 s.**

Source: Pukujan-lab/voice-agent-research#107 (the website copilot loads each business's site under its own title prefix, so every search it makes is a filtered one). Observed 2026-11-01 with `eval/size/bench.py` in that repo (PR to follow): a scratch `pgvector/pgvector:pg16` container, Octo's RAG tables (`documents`, `document_versions`, `chunks` with the generated `content_tsv` and GIN index, `embeddings` as `halfvec(512)` with the default HNSW index), and `octo.match_chunks_hybrid` copied unchanged from `20261031020000_rag_halfvec_512.sql`. Synthetic site, feature-hashed embeddings, no reranker, 100 queries per row, one backend on a 2-CPU Docker VM, so absolute times are only comparable to each other.

| Passages in the workspace | No filter, p50 | `titlePrefix` = the whole business, p50 | `titlePrefix` = business/language/page type, p50 | Small business (2,000 passages) in the same workspace, p50 |
|---|---|---|---|---|
| 10,000 | 23 ms | 53 ms | 15 ms | 18 ms |
| 50,000 | 71 ms | 363 ms | 59 ms | 39 ms |
| 200,000 | 238 ms | 2,112 ms | 375 ms | 209 ms |

Time grows with the number of chunks under the prefix (50,000 to 200,000: 4x the chunks, 5.8x the time), not with the workspace. A small tenant is fine; one large tenant is not. A straight-line extrapolation to 1,000,000 chunks under one prefix is about 10 s *(inference, not measured: the scratch VM cannot hold 1M)*.

**Where the 2.1 s goes** (200,000 chunks, prefix = every chunk, each part run alone as the function writes it, p50 of 5):

| Part | Time |
|---|---|
| `allowed` CTE: join `chunks`, `document_versions`, `documents` and test `left(d.title, …) = prefix` for every chunk | 725 ms |
| Filtered vector arm, `ORDER BY (embedding <=> q) + 0` over `allowed` (exact scan) | 787 ms |
| Filtered lexical arm, `c.id IN (SELECT chunk_id FROM allowed)` | 781 ms |
| Same vector arm on the HNSW index with `SET hnsw.iterative_scan = relaxed_order`, no `+ 0` | **2 ms** |
| Lexical arm with no prefix | 19 ms |

So the proposal in the description (drop `+ 0`, use iterative scans) fixes the vector arm completely (787 ms to 2 ms here) and is not enough alone: building `allowed` and intersecting the lexical arm with it cost about as much again. Suggestions *(proposal; none of it is implemented)*: (1) an index that serves the prefix test, for example `documents (workspace_id, title text_pattern_ops)` and a `title LIKE prefix || '%'` form, or the title prefix copied onto `chunks`; (2) apply the prefix as a post-filter on the lexical arm's GIN hits with a larger candidate limit instead of materializing `allowed`; (3) keep exact scans only when the allowed set is small.

Recall was not affected by any of this (recall@10 of 0.98 to 1.0 on the synthetic site at every size and filter), so the change is about speed only.

Counter-signal: the live workspace measured 1.5 s p50 and 2.4 s p90 for the IRS library on 2026-11-01 (145,519 indexed passages, reranker on, titlePrefix over five prefixes), well below the 50 s in the description, so something has already improved there; I did not look at what.
