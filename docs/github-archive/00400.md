# Issue #400: UX analytics: self-hosted Umami, provisioned by Octo per workspace and user

- State: open
- Opened by Pukujan on 2026-10-31
- Original: https://github.com/Pukujan-lab/octo-database/issues/400

Child of #340. Sibling of #342: Phoenix covers agent traces; this covers **UX and product analytics**, meaning every click and how people use each app.

## Why

The owner does UX work, so event counts alone are not enough. UX work needs heatmaps, session replays, rage and dead clicks, scroll depth, funnels and paths.

## Why Umami, not PostHog

A comparison of 66 tools from about 140 sources (2026-10-31) picked self-hosted **Umami v3.4+**:

- MIT licence; needs only the app and Postgres.
- Has session replay (since v3.1), click and scroll heatmaps (since v3.2), and funnels.
- Has a free admin API: one admin key, teams, websites, and users with roles.

Self-hosted PostHog was dropped:

- The free edition allows 1 project per organization.
- It runs about 40 services.
- PostHog says it is unlikely to scale past a couple hundred thousand events a month.
- It has no versioned releases.

Gaps in Umami:

- No surveys or A/B tests. Add GrowthBook (A/B tests) or Formbricks (surveys) only for apps that need them.
- Rage and dead click detection is unconfirmed.

Fallbacks:

- Rybbit (ClickHouse) plus free Microsoft Clarity on public sites only.
- PostHog Cloud, about $50–150 a month at 2–5M events.

## Plan

### Step 0: load test on the server

Measure before committing:

- ingest rate and RAM;
- Postgres size per million events;
- replay size per session;
- dashboard query speed at roughly 2× expected volume.

### Step 1: run Umami on the server

- A Komodo stack in `Pukujan-lab/server-management`, with memory limits.
- **A separate Postgres from Octo's**, because replays would bloat Octo's WAL, replica and R2 dump.
- Behind the Cloudflare tunnel.
- Replay and event retention set.

### Step 2: Octo provisions it per workspace and user

| Octo | Umami |
|---|---|
| team or client | team |
| workspace | website, created through the API; Octo keeps its website ID (the tracking key) |
| workspace members | team users with roles (owner, manager, member, view-only) |
| workspace deleted | website deleted |

- The Octo dashboard shows an **Analytics** link per workspace.
- Form fields are masked in replays by default, so SSN, date of birth and email are never recorded.

### Step 3: first projects

The voice agent and the NYC map agent, then Precedent, kresilo and Design Bakery.

## Done when

- Umami runs on the server.
- Turning analytics on for a workspace creates its website and adds its members.
- The voice agent and the NYC map agent send clicks and replays there.
- Old replays expire on schedule.

## Load test on the vps (2026-10-31)

Throwaway Umami v3.4.1 with its own Postgres 17, now removed.

- **Ingest:** about 450 events/s through `/api/batch` (500 events per call), the same at 4 or 16 parallel senders. That is about 39M events a day, far above need.
- **Memory:** about 300 MB for the app and under 400 MB for Postgres while ingesting.
- **Disk:** about 0.9 GB per 1M events. `website_event` has 14 indexes; the table data itself is about 150 MB per 1M.
- **Bulk inserts are slow** because of those indexes. Fine for live traffic, but plan retention to cap the table.
- **Replays** live in `session_replay` (rrweb chunks stored as `bytea`) and **heatmaps** in `heatmap_event`, both in Postgres.
- **API:**
  - Replay and heatmap settings per website: `replayConfig` (`sampleRate`, `maskLevel: strict`, `maxDuration`).
  - `GET /api/websites/{id}/replays/{replayId}` returns raw rrweb events.
  - `GET /api/websites/{id}/heatmaps` returns heatmap points.
- **Not measured:** real replay size per session, and dashboard query speed at volume. The test was cut short to avoid generating more fake data. Measure both with real traffic from the first app.

## Next idea: agents that do UX review

Because the replay and heatmap data come back from the API, an agent can do the first pass of UX review:

1. Each night, pull bad sessions: rage clicks, dropped funnel steps, errors.
2. Play them back headless and summarise the friction.
3. File findings with evidence.
4. Later: synthetic-persona browser agents on every preview deploy, and fix PRs measured by an A/B test.

Build this after Umami is live.
