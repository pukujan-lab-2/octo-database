Nothing checked how workspace provisioning, the file archive lifecycle and key revocation behave when their steps interleave or fail halfway.

## Problem and consequence

These three flows run several steps with no lock around them, and each step can fail. Tests only hit the orderings someone thought to write. A bad ordering could lose file bytes or leave state that lies about where they are, and no test would notice.

## What changes

- `verification/tla/`: three TLA+ models that follow the code step by step, with ten TLC configs, `check.sh` and a README.
  - `WorkspaceProvisioning.tla`: auto-provisioning and the manual database route racing for one workspace.
  - `FileLifecycle.tla`: `archiveFile` and `restoreFile`, the one-job-per-file queue, delete, worker crashes, bad Drive bytes, and the on-demand restore a download runs.
  - `KeyRevocation.tla`: revoking a key while requests are in flight, and the confirm gate with its two-minute window.
- `gates.yml`: the `gates` job downloads `tla2tools.jar` v1.7.4, checks its SHA-256 and runs `check.sh`. Each config must give its expected exit code.

## Before and after

Before: no model; these orderings were untested.
After: TLC checks every reachable state of each model on every PR. Four configs pin behavior the code has today:

1. **Restore can overwrite good bytes.** When archive verification fails, or the state update after it fails, the Drive locator is saved without `archive_hash`. A later restore has nothing to check the Drive copy against and writes it over the good R2 copy. Saving the hash with the locator fixes it; the `FileLifecycle` config checks that fix with crashes and on-demand restores.
2. **Archive can drop bytes a download just restored.** An archive job that loaded the file as archived prunes R2 while an on-demand restore writes it back. The file ends `active_r2` with no R2 bytes. Drive keeps them, so nothing is lost, but downloads fail until a restore job runs.
3. **Provisioning can orphan a database.** Two requests both pass the check and both create a database; the loser's insert fails on the unique key and leaves its database and role behind.
4. **In-flight requests finish after a revoke.** A request that authenticated before the revoke still writes.

The rest hold: a revoked key starts no request, a plain API key never passes the confirm gate, and a session skips codes only inside the window after a pass.
