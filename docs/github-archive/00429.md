# Issue #429: Restore can overwrite good R2 bytes with an unchecked Drive copy

### Summary

A restore can write a bad Drive copy over the good R2 bytes. When archive verification fails, or the state update after it fails, `archiveFile` saves the Drive locator but not `archive_hash`. `restoreFile` only checks the Drive copy when a hash is recorded, so a later restore of that file writes whatever Drive returns into R2 and marks the file active.

### Identity and Lineage

- related: #419 (the TLA+ model that found it, config `FileLifecycleUnhashedRestore`, landed in #424)

### Acceptance Criteria

1. Both failure branches in `archiveFile` that record a locator also record `archiveHash`.
2. A unit test shows a restore after a failed verification refuses the bad copy and leaves R2 untouched.
3. `verification/tla/check.sh` passes with the config flipped to a control, and the PDD and known gaps no longer list this.

### Boundaries and Next Action

- Changes `src/storage/archive-service.ts`, its unit test, the TLA+ configs and docs. No migration: production has no affected rows.
- Next action: open the fix pull request.

### Symptoms

1. TLC reaches a file with no good copy in eleven states: archive, verify fails, restore writes the bad Drive copy over R2.

### Hypotheses (unverified)

- **H1: only the missing hash allows it.** Would confirm: the model passes `NoLoss` with the hash recorded alongside the locator (it does, config `FileLifecycle`). Would refute: a counterexample with the hash recorded.

### Counter-signal

Drive returning bytes that differ from what was uploaded is rare; the usual verify failure is an unreadable copy, which restore already handles by keeping the file archived.

### Honest Caveat

Found by the model and by reading the code; not reproduced against real Drive.

### Problems vs Gaps

- Problem: restore trusts an unchecked Drive copy after a failed archive.
- Gap: none beyond that.

### Proposal *(proposal)*

Record the hash of the R2 bytes in every update that records a locator.
