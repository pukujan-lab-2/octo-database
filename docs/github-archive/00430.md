A restore could write an unchecked Drive copy over a file's good R2 bytes.

## Problem and consequence

When archive verification failed, or the state update after it failed, `archiveFile` saved the Drive locator but not `archive_hash`. `restoreFile` only checks the Drive copy when a hash is recorded, so restoring that file wrote whatever Drive returned into R2 and marked it active. The file could end with no good copy.

## What changes

- `src/storage/archive-service.ts`: both failure branches that save the locator also save the hash of the R2 bytes.
- `tests/unit/archive-service.test.ts`: an archive whose verification fails, then a restore of that file. The restore is refused with `ARCHIVE_HASH_MISMATCH` and R2 keeps the original bytes. The state-update-failure test also checks the hash is saved. Both assertions fail without the fix.
- `verification/tla/`: `FileLifecycleUnhashedRestore` becomes the control `FileLifecycleNoHash`, and the model notes the code now saves the hash with the locator.
- `docs/PDD.md` and `docs/ARCHITECTURE.md`: the property now holds; the known gap is gone.

## Before and after

Before: a failed archive followed by a restore could lose the file's bytes.
After: the restore sees the hash mismatch, marks the file for reconciliation and leaves R2 alone.
