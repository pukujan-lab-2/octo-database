### Summary

`octo.agent_key_uses` gets a row for every API key use and nothing deletes them: about 185,000 rows (41 MB) between Oct 30 and Nov 1 on the VPS. The Operations tables (jobs, activity) have no sorting or filtering, and there is no view of the key use log or of workspace database sizes.

### Identity and Lineage

- related: #362 (the key use log and its leak alert)

### Acceptance Criteria

1. An hourly sweep deletes key-use rows older than 30 days, keeping each key's first successful use per IP so the new-IP alert still works.
2. Jobs, activity, the key use log and workspace databases each show in a table that sorts by any column, filters by text and by its main categories, and pages.
3. The key use log groups uses by key, IP, route and outcome with counts and first and last seen.
4. Workspace databases lists each of the caller's workspace databases with its size.

### Boundaries and Next Action

- No new frontend dependency; one shared table component.
- Next action: open the pull request.

### Symptoms

1. `agent_key_uses` grows about 20 MB a day with no cleanup.
2. The owner called the current tables hard to read and asked for sorting and filtering.

### Hypotheses (unverified)

- **H1:** keeping the earliest successful row per key and IP is enough for the new-IP alert. Would refute: the alert query needs older rows than that.

### Counter-signal

Disk is 19% used today, so the growth is not urgent.

### Honest Caveat

The growth rate comes from two days of data.

### Problems vs Gaps

- Problem: an unbounded log table.
- Gap: no detailed table views.

### Proposal *(proposal)*

An hourly prune, plus a shared table component used by four views.
