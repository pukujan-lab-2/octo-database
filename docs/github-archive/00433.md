The key use log grows about 20 MB a day with no cleanup, and the Operations tables can't be sorted or filtered.

## Problem and consequence

`octo.agent_key_uses` gets a row for every API key request and nothing deletes them (185,000 rows in two days on the VPS). The jobs table and activity list on Operations show a fixed slice with no sorting, search or filters, and the app has no view of the key use log or of workspace database sizes.

## What changes

- `src/server/db.ts`: `dbPruneKeyUses` deletes key-use rows older than 30 days but keeps each key's first successful use per IP, so the new-IP alert still knows which IPs it has seen. `dbListKeyUseSummary` groups uses by key, IP, method, route and outcome. `dbListWorkspaceDatabases` lists databases for a set of workspaces. The jobs and activity lists return up to 500 and 1,000 rows instead of 50.
- `src/server/queue.ts`: the hourly retention sweep also runs the prune.
- `src/server/provisioning.ts`: `databaseSizes` reads `pg_database_size` for the named databases.
- `GET /api/keys/uses` (`src/routes/keys.ts`) and `GET /api/databases` (`src/routes/workspaces.ts`), both `read` scope, with rows in `tests/e2e/route-table.ts`. A workspace key only sees its own workspace in `/api/databases`.
- `frontend/src/components/portal/DataTable.tsx`: one table component with sortable headers, text search, per-column select filters, a row count and paging. No new dependency.
- Operations: jobs (filter by state and job type, retry kept), activity (filter by event type) and a new workspace databases table with sizes.
- Access: a new key use log table (filter by key, IP, method and outcome).

## Before and after

Before: the key use log grows without limit, and the tables show the latest 24 to 50 rows in a fixed order.
After: key-use rows older than 30 days are deleted every hour, and all four tables sort by any column, search, filter and page.
