### Summary

Agents can send traces and eval scores to Octo, but cannot read them back, and Octo's MCP server has no trace or eval tools. Phoenix's own viewer needs a login that agents don't have, so an agent session cannot see its own traces, sessions or eval scores.

### Identity and Lineage

- related: #268 (OTLP ingress to Phoenix), #342 (eval scores), #432

### Acceptance Criteria

1. `GET /api/workspaces/<id>/otel/read/<resource>` returns Phoenix's data for the workspace's own project, for spans, traces, sessions, span annotations, trace annotations, session annotations and annotation configs. It takes the normal Octo key with the read scope and the same workspace checks as the write routes.
2. The project is always the workspace's slug and is never taken from the caller. Phoenix endpoints that look up by a global id, and Phoenix's workspace-agnostic resources (datasets, experiments, prompts), are not exposed.
3. MCP has tools to read trace data, send an eval score, and get the viewer link, each tied to a capability so keys only see what they can use. The capabilities list and the route table include the new route.
4. `docs/consuming-octo.md` explains how an agent sends and reads traces and evals.

### Boundaries and Next Action

- No new viewer. Phoenix stays the one viewer.
- Phoenix datasets, experiments and prompts are out of scope: Phoenix does not separate them per workspace.
- Next action: open the pull request.

### Symptoms

1. `src/routes/traces.ts` has only two write routes and a link route. `src/mcp/server.ts` has no trace tool.
2. A session following the link lands on `/phoenix/login`, as seen in the Phoenix log on 2026-11-01.

### Hypotheses (unverified)

- **H1:** Phoenix's project-scoped REST endpoints return only that project's data. Would refute: a spans read for one project returning another's spans. The 2026-11-01 probe returned chatbots-factory spans for that project only.

### Counter-signal

Writes already work: 617 spans and 91 eval scores reached Phoenix in 24 hours.

### Honest Caveat

Checked against Phoenix 20.27.0's `openapi.json` on the VPS, and one spans read.

### Problems vs Gaps

- Problem: agents cannot read their own traces.
- Gap: no MCP tools for traces or evals, and no docs.

### Proposal *(proposal)*

One read route with an allow-list of project-scoped resources, three MCP tools, docs.
