Agents could send traces and eval scores to Octo but could not read them back, and Octo's MCP server had no trace tools.

## Problem and consequence

Reading a workspace's traces meant logging in to Phoenix, which has its own users and which agents cannot do. No MCP tool covered traces or evals, and the docs did not mention them.

## What changes

- `src/routes/traces.ts`: `GET /api/workspaces/<id>/otel/read/<resource>` for spans, traces, sessions, span annotations, trace annotations, session annotations and annotation configs. It asks Phoenix for the workspace's own project only: the project is the workspace slug in the Phoenix path, and the caller's query (limit, cursor, filters) passes through. It uses the read scope and the same key and membership checks as the write routes. A project Phoenix has not created yet reads as an empty result.
- Not exposed: Phoenix datasets, experiments, prompts and lookups by global id, which Phoenix does not separate per workspace.
- `src/api/capabilities.ts`: a `traces.read` action.
- `src/mcp/server.ts` and `client.ts`: tools `read_traces`, `record_eval_scores` and `get_trace_link`, each tied to its capability, and a `traces` guide topic.
- `tests/e2e/route-table.ts`: rows for the seven read routes.
- `tests/unit/traces-read.test.ts` and `tests/unit/mcp-server.test.ts`: the fence, the allow-list, a non-member and a key bound to another workspace, the empty project, and the new tools.
- `docs/consuming-octo.md`: a "Traces and eval scores" section.

## Before and after

Before: an agent sends traces and never sees them, and MCP has no trace tool.
After: an agent reads its own traces and scores through the Octo key, over HTTP or MCP.
