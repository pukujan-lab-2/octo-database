Opening Phoenix asked for a second login, and agents had no MCP tools for UX analytics.

## Problem and consequence

The Phoenix viewer has its own users, so the owner signed in twice. Umami's data had no agent route, and the MCP `guide` did not say which tool fits which need.

## What changes

- Phoenix with the Octo session. `POST /api/phoenix/session` (a person's session, platform owner only) sets a signed, expiring cookie scoped to `/phoenix`. `GET /api/phoenix/auth` is the web server's forward-auth check: the cookie must verify and its principal must still be the platform owner in the database. `deploy/gravebuster/Caddyfile` runs that check and only then adds Phoenix's admin token; `docker-compose.vps.yml` passes `OCTO_PHOENIX_SECRET` to the web container. The Services button sets the cookie, then opens the viewer. Phoenix keeps its own login for anyone who reaches it another way.
- UX analytics for agents. `GET /api/workspaces/:id/ux-analytics/read/<resource>` (stats, pageviews, metrics, events, sessions, replays, active) reads the workspace's own Umami website; MCP tools `get_ux_analytics`, `enable_ux_analytics`, `read_ux_analytics`; capabilities `ux_analytics.status` and `ux_analytics.read`.
- MCP `guide` topics `ux` and `recipes` (which tool fits which need), and the connect-time instructions list the topics.
- Metamorphic tests (`tests/unit/traces-ux-metamorphic.test.ts`): the project and website fence under generated queries, query-order invariance, allow-list closure under mutation, the viewer cookie under every one-character change and expiry, and tool visibility growing with scopes.
- TLA+ models `PhoenixGate` and `ToolScope` with six configs in `verification/tla/`, run by `gates`.
- This branch also carries #442's trace read route and MCP tools (PR 443).

## Before and after

Before: two logins for traces, and no agent view of UX data.
After: one sign-in for the owner, and agents read both through their Octo key.
