### Summary

The VPS keeps Phoenix and the embedding model running all day, though nothing uses them most of the time. On 2026-11-01 the embedder (`octo-embed`) held 1.5 GB and Phoenix (`octo-phoenix`) held 460 MB while idle.

### Identity and Lineage

- related: #445 (Phoenix opened from the Octo session)

### Acceptance Criteria

1. Phoenix and the embedder stop after 30 idle minutes.
2. The next request starts them again and succeeds: the owner opening `/phoenix`, a trace sent or read through the API, and an embedding call.
3. A deploy that starts them does not keep them running forever.

### Boundaries and Next Action

- Uses Sablier (open source, `sablierapp/sablier`) and its Caddy plugin in the web container, which already runs Caddy. No Octo code change.
- Umami is out of scope here: its public route goes from the Cloudflare tunnel straight to its container, so it needs a tunnel route change first.
- Next action: open the pull request.

### Symptoms

1. `docker stats` on the VPS, 2026-11-01: `octo-embed` 1.52 GiB, `octo-phoenix` 458 MiB, with no ingest or viewer use at the time.

### Hypotheses (unverified)

- **H1:** The first request after an idle period waits a few seconds for Phoenix and up to about 20 seconds for the embedder, which loads its model. Would refute: timeouts in the API's embedding or trace calls after a cold start.

### Counter-signal

Bulk ingest that pauses for more than 30 minutes pays the start delay again.

### Honest Caveat

Start times are estimates until measured on the VPS.

### Problems vs Gaps

- Problem: about 2 GB held by idle services.

### Proposal *(proposal)*

Label both containers for Sablier, run Sablier with the Docker provider, and put Sablier's blocking check in front of `/phoenix` and in front of internal listeners that the API uses for Phoenix and the embedder.

**Pukujan commented, 2026-11-01**

Two things to settle before #449 goes to production, from the VPS-wide plan in Pukujan-lab/server-management#80:

1. **Pin Sablier 1.19.1, not 1.18.0.** 1.18.0 has sablierapp/sablier#1110, reported on this exact setup (Caddy plugin with the Docker provider). An expired session can be dropped without stopping its container, which then runs forever. 1.19.0 fixes it.
2. **One Sablier per Docker host.** Sablier finds containers by the `sablier.enable` label only, and has no way to scope itself to one compose project. With `auto-warm-externally-started=true`, a second instance would adopt and stop the other one's containers. legal-engine and other services on the VPS are about to go on-demand too, so Sablier will move into a shared `platform` stack owned by server-management. It will run 1.19.1 with sessions kept on a volume (`--storage.file`), on an external Docker network called `sablier`.

What this means for Octo:
- If you promote before the shared stack exists, bump the image to 1.19.1 first. That is safe on its own.
- Once the shared stack is live, a small Octo PR will drop the `sablier` service and add the external `sablier` network to `octo-web`. Labels, health checks and Caddy routes stay as they are. The URL `http://sablier:10000` stays the same, because the shared container keeps that alias.
- Please don't start a second Sablier anywhere else on the VPS in the meantime.
