Phoenix and the embedding model run all day on the VPS, holding about 2 GB, though nothing uses them most of the time.

## Problem and consequence

On 2026-11-01 `octo-embed` held 1.5 GB and `octo-phoenix` 460 MB with no traffic. The owner wants idle services stopped and started again on demand.

## What changes

- A `sablier` container (`sablierapp/sablier` 1.18.0, Docker provider) stops containers labelled `sablier.enable` after 30 idle minutes. A container started some other way, such as by a deploy, gets the same 30 minutes before it stops.
- `octo-web`'s Caddy is now built with Sablier's plugin (Caddy 2.11.2, plugin 1.0.2).
- `/phoenix` runs the Octo cookie check first, so a request without a valid cookie never starts Phoenix. A request that passes starts Phoenix and waits for it.
- The API reaches Phoenix and the embedder through two Caddy listeners on the internal network (`octo-web:6006`, `octo-web:11434`), set in `docker-compose.vps.yml`. A trace, a trace read or an embedding call starts the service it needs and waits for it.
- Phoenix and the embedder get health checks, so Sablier forwards a request only once the service answers.

## Before and after

Before: about 2 GB held around the clock.
After: nothing held while idle. The first request after an idle period waits for the start.

## How to verify

- The custom Caddy builds, and `caddy validate` accepts the Caddyfile.
- A live run against stand-in containers, with the same names, labels and Caddyfile (idle time cut to 30 s):
  - `/phoenix/` with no cookie answered 401, and Phoenix stayed stopped.
  - With a valid cookie, it started Phoenix and answered with the admin token attached.
  - The API listener started the embedder.
  - Both stopped about 40 s after the last request.
- `gates` must pass. After deploy, check that both containers stop after 30 idle minutes and that opening `/phoenix` brings Phoenix back.

## What stays unchanged

No Octo code change. Umami stays always on: its public route goes from the Cloudflare tunnel straight to its container, so it needs that route pointed at the web container first.
