# Issue #457: [OBSERVATION]: A key-value store with expiry and atomic counters would save adopters a hand-built table

- State: open
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/octo-database/issues/457
- Labels: observational-issue, proposal

### Summary

The voice-agent-research repository (a website copilot that many businesses install) needs a small amount of short-lived, shared state in Octo: resume snapshots for dropped calls, caller-verification locks, and rate-limit counters. Octo has no key-value store with expiry and no atomic counter, so the adopter built both on top of the workspace SQL surface: a `copilot_kv(k text primary key, v jsonb, exp timestamptz, touched timestamptz)` table, an upsert for set, and an `insert ... on conflict do update ... returning` for a counter. It works (checked against the live chatbots workspace on 2026-11-01: set, get, counter and expiry all behave; about 67 ms per round trip), but every adopter that needs this will write the same table and the same sweep. This is a non-binding proposal; the adopter does not keep a local copy and does not touch this repository.

### Identity and Lineage

Leaf: this issue. Parent: none. Depends on: none. Related: Pukujan-lab/voice-agent-research#100 (the parent that needed it) and #102 (the child that built the workaround).

### Acceptance Criteria

*(proposal)* If Octo offered this, an adopter could:

- `PUT` / `GET` / `DELETE` a JSON value by key in a workspace, with an optional time to live, and never read an expired value.
- Increment a named counter atomically and get the new count back, with the expiry fixed at the first increment.
- Rely on Octo to remove expired rows and to cap the number of rows per namespace, instead of running its own sweep.

### Boundaries and Next Action

In scope: a decision on whether a workspace key-value surface with expiry belongs in Octo. Out of scope: the adopter's own code, which already works through the SQL surface. Next action: the owner decides; nothing is blocked meanwhile.

### Symptoms

1. **No expiry.** The SQL surface has no row time to live, so the adopter filters `exp > now()` on every read and deletes expired rows itself every 64 writes.
2. **No atomic counter primitive.** A counter needs a hand-written `insert ... on conflict do update ... returning`; the adopter tested 50 parallel increments from two instances for no lost or doubled count.
3. **No row cap.** Keeping a table to a fixed size needs a second `delete ... offset` statement.

### Hypotheses (unverified)

- **H1. Other adopters will need the same three things.** Status: unverified. Would confirm: a second adopter writes a similar table. Would refute: no other adopter keeps short-lived shared state. Experiment: ask the adopters.

### Counter-signal

The SQL surface already does the job, so this is a convenience, not a blocker. Octo's own rule is that adopters consume it and do not change it.

### Honest Caveat

Observed once, on one workspace, by one adopter. The 67 ms figure is the mean of five reads from a laptop.

### Problems vs Gaps
