# Self-host Umami, rent PostHog only for gaps

**Short answer:** for this setup, run **self-hosted Umami (v3.4+)** on your own server as the analytics core that Octo provisions. It is MIT-licensed and runs on Node plus Postgres alone. It now has session replay and click/scroll heatmaps. It also has the cleanest free API for creating websites, teams and users. **PostHog self-hosted is ruled out.** Its free edition is limited **in code** to one project per organization, and PostHog says it is "unlikely to scale past a couple 100ks events". **No open-source tool matches PostHog's full checklist.** Only PostHog Cloud ships autocapture, rage/dead clicks, scrollmaps, surveys and experiments in one product. At your volume it costs about **$0 to $150 a month** if you keep to 6 projects and mostly anonymous events. **Rybbit** (ClickHouse, scales better, no heatmaps) is the fallback if Umami's Postgres fails a load test. You can add **free Microsoft Clarity** for rage and dead clicks, but only on public sites, never the legal app. Two things decide the final pick: Umami's ingest and replay storage at your real volume, and whether Umami captures rage/dead clicks. Both need a test on the real server.

| Pick | Role | Monthly cost |
|---|---|---|
| 1. Umami self-hosted | Core: events, funnels, replay, heatmaps, API provisioning | $0 licence, server already owned |
| 2. Rybbit self-hosted (+ Clarity) | Fallback if Umami can't keep up | $0 |
| 3. PostHog Cloud (pay-as-you-go) | Everything in one, if tenant logins don't matter | ~$0-150 at 1-5M anonymous events |
| 4. OpenReplay CE | Deep replay + devtools for the voice copilot | $0, needs ~8 GB RAM |
| 5. OpenPanel | If A/B tests matter more than heatmaps | $0 |

## PostHog self-host fails on projects, scale and support, not on features

PostHog self-hosted has the same feature code as Cloud, but the free licence turns off what you need most. PostHog's own docs say **"All paid-plan features are Cloud-only"** for self-hosters. They also suggest self-hosting may not suit you above **300k events, 1k recordings or 300k flag calls**, and recommend Cloud at about 1M events a month ([PostHog self-host docs](https://posthog.com/docs/self-host)). The open-source disclaimer is blunter: everything runs on one machine and is "unlikely to scale past a couple 100ks events" without serious scaling work. PostHog will not help debug or recover lost data. Self-hosters lose unlimited projects, RBAC, audit logs, custom retention and recording downloads ([PostHog disclaimer](https://posthog.com/docs/self-host/open-source/disclaimer.md)). The project limit is not just licence wording. In `posthog/api/project.py`, an organization without the paid feature "can only have one non-demo project" ([project.py](https://raw.githubusercontent.com/PostHog/posthog/master/posthog/api/project.py)). Self-hosted installs also block a user who already has an organization from creating another ([organization.py](https://raw.githubusercontent.com/PostHog/posthog/master/posthog/api/organization.py)). So the only free multi-tenant model is **one separate owner login per app**. Octo cannot manage that cleanly through one admin.

The stack is heavy too. The current hobby compose file defines **about 40 services**, including ClickHouse, Redpanda, Temporal, Elasticsearch, SeaweedFS and headless Chromium ([docker-compose.hobby.yml](https://raw.githubusercontent.com/PostHog/posthog/master/docker-compose.hobby.yml)). The installer warns "You REALLY need 8GB or more" ([deploy-hobby](https://raw.githubusercontent.com/PostHog/posthog/master/bin/deploy-hobby)). A 2026 deploy on an 8 vCPU / 32 GB node ran about 42 pods and took about an hour to boot for the first time. The same writer found the proprietary `ee/` code is imported about 500 times, so removing it stops the app from starting ([Meidinger, 2026-09](https://jeremy-meidinger.de/blog/self-hosting-posthog-part-1/)). PostHog publishes no tagged releases, so you always run `latest` ([deploy-hobby](https://raw.githubusercontent.com/PostHog/posthog/master/bin/deploy-hobby)). Maintainers close custom-config issues as unsupported ([PostHog #43915](https://github.com/PostHog/posthog/issues/43915)). On a box with 22 GB free that also runs Octo, PostHog would technically fit. It would take most of the RAM and still be outside its supported volume.

## Umami 3.2+ is the best open-source fit, but not a full PostHog replacement

Umami changed the most in 2026. **v3.1 (April) added rrweb-based session replay** ([Umami v3.1.0](https://github.com/umami-software/umami/releases/tag/v3.1.0)). **v3.2 (June) added click and scroll heatmaps**, built from captured replay snapshots, with self-hosted heatmap storage. It also splits replay payloads into chunks and rejects oversized ones ([Umami v3.2.0](https://github.com/umami-software/umami/releases/tag/v3.2.0); [Heise](https://www.heise.de/en/news/Umami-3-2-0-Heatmaps-and-improved-web-analytics-11347552.html)). On Umami Cloud, replay and heatmaps need the $200/mo Business plan. Self-hosted, you pay nothing per session ([temps.sh, vendor blog](https://temps.sh/blog/best-self-hosted-session-replay-tools-2026)). It is MIT-licensed with no proprietary `ee/` folder ([Umami licence](https://raw.githubusercontent.com/umami-software/umami/master/LICENSE)). The project is very active: about 39.8k stars, and v3.4.1 shipped on 2026-10-23 as a security hotfix that "All self-hosted users should upgrade" to ([Umami releases](https://github.com/umami-software/umami/releases)).

For Octo, Umami's main strength is provisioning. **v3.4 added account API keys** that keep each user's and team's permissions ([Umami v3.4.0](https://github.com/umami-software/umami/releases/tag/v3.4.0)). The API covers `/api/websites`, `/api/teams`, team users, team websites, `/api/users` and admin routes ([Umami API tree](https://github.com/umami-software/umami/tree/master/src/app/api)). It has global roles (admin, user, view-only) and team roles (owner, manager, member, view-only) ([constants.ts](https://raw.githubusercontent.com/umami-software/umami/master/src/lib/constants.ts)). That maps directly onto Octo: **one team per Octo workspace**, websites inside it, and Octo users added with a team role, all with one admin key. Umami v3 runs **only on PostgreSQL**, with ClickHouse as an optional analytics backend ([Umami v3.0.0](https://github.com/umami-software/umami/releases/tag/v3.0.0); [v3.4.0](https://github.com/umami-software/umami/releases/tag/v3.4.0)). It is the only shortlisted tool that can live on your existing Postgres 17. A plain `pg_dump` backs it up, which fits the nightly dump to R2.

Umami has real gaps. The notes do not confirm **click autocapture as queryable events, rage/dead-click detection, surveys or A/B tests**. Its funnels and journeys were not re-checked against v3. Replay and heatmaps are four to six months old and not widely tested. The biggest risk is storage. Umami's replay data appears to go into Postgres, though the source does not confirm this. An independent benchmark measured a 50-second session at **~377 KB gzipped** ([Krama PR #179](https://github.com/NachikethaKG/Krama/pull/179)). At that size, tens of thousands of replays a month would add gigabytes to the main database, its WAL and the planned streaming replica. Give Umami **its own database, or its own Postgres container**, rather than the Octo database, and keep replay retention at 30 days.

## Rybbit, OpenReplay and OpenPanel each cover a different gap

**Rybbit** is the fallback built for scale. It stores events in ClickHouse, with Postgres 17.4 for metadata and Redis ([Rybbit compose](https://raw.githubusercontent.com/rybbit-io/rybbit/master/docker-compose.yml)). One template measured about **0.9 GB at idle** ([Server Compass](https://servercompass.app/templates/rybbit)). A third-party guide says a 1 GB ClickHouse "comfortably handles a few million events per month" ([Railway](https://railway.com/deploy/rybbit-analytics)). It has funnels, journeys, retention, session replay with inputs masked automatically, error tracking, and unlimited sites per organization under AGPL-3.0 ([Rybbit GitHub](https://github.com/rybbit-io/rybbit); [Rybbit replay](https://rybbit.com/features/session-replay)). Provisioning works well: org API keys survive members leaving, and members see only the sites assigned to them ([Rybbit API](https://rybbit.com/pl/docs/api/getting-started); [Rybbit org settings](https://rybbit.com/docs/organization-settings)). Its weakness for UX work is that **it has no heatmaps** ([analytics-alternatives.com](https://analytics-alternatives.com/tools/rybbit/)).

**OpenReplay CE** is the most mature replay-first tool. It includes devtools (network, console, JS errors, store state), funnels, journeys, Assist co-browsing, input and network masking, and a heatmaps claim that one competitor disputes ([OpenReplay GitHub](https://github.com/openreplay/openreplay); [temps.sh](https://temps.sh/blog/best-self-hosted-session-replay-tools-2026)). That debugging depth suits the voice-agent copilot, where you need to see what the network and console did, not just where people clicked. Its v2 API creates projects with an org key and returns a `projectKey` ([OpenReplay API](https://docs.openreplay.com/en/api/)). It costs more to run: a **2 vCPU / 8 GB baseline**, about 20 services, and an object store that recently moved from MinIO to RustFS. That move is an upgrade risk ([OpenReplay compose](https://raw.githubusercontent.com/openreplay/openreplay/main/scripts/docker-compose/docker-compose.yaml)). SAML SSO is Enterprise-only ([OpenReplay SSO](https://docs.openreplay.com/en/configuration/sso/)).

**OpenPanel** is the only lightweight open-source suite that lists **A/B testing**, along with funnels, cohorts, retention and opt-in replay that masks inputs by default. It says self-hosting has "no artificial limits" ([OpenPanel](https://openpanel.dev/for/developers); [self-host docs](https://openpanel.dev/docs/self-hosting/v2/get-started); [replay docs](https://openpanel.dev/docs/session-replay)). It has **no heatmaps**. It pins Postgres 14 and adds Redpanda capped at 2 GB ([OpenPanel compose](https://raw.githubusercontent.com/Openpanel-dev/openpanel/main/self-hosting/docker-compose.template.yml)). Its Manage API creates projects and clients but does not document member management. Its root client has organization-wide access ([OpenPanel Manage API](https://openpanel.dev/docs/api/manage)). Matomo has the most mature per-site permission API ([UsersManager API](https://raw.githubusercontent.com/matomo-org/matomo/5.x-dev/plugins/UsersManager/API.php)). It still loses here, because it needs MySQL/MariaDB ([Matomo FAQ](https://matomo.org/faq/how-to-install/faq_55/)) and a paid heatmap/recording plugin from about €219 a year ([Matomo pricing](https://matomo.org/pricingforai/)).

## Cloud options: PostHog wins on features, Clarity on price, neither on provisioning

**PostHog Cloud** is the only tool with published prices that covers the whole checklist. Its heatmaps docs list rage clicks (3 clicks within ~30 px in 1 s), dead clicks, scrollmaps and clickmaps, all built on autocapture. Heatmap data is free to ingest ([PostHog heatmaps docs](https://posthog.com/docs/toolbar/heatmaps.md)). The free tier includes 1M events, 5k web recordings, 1M flag requests and 1,500 survey responses a month, for **1 project**. With a card on file the base price stays $0 and you get **6 projects**. Past 1M, events cost $0.00005 each up to 2M, then $0.0000343 ([PostHog pricing](https://posthog.com/pricing.md)). By that pricing, **5M anonymous events cost about $153/mo** and 20M about $643. Identified events (with person profiles) raise those to about $560 and $1,928. 25k replays add about $85 ([PostHog pricing](https://posthog.com/pricing.md)). The catch is multi-tenancy. **Unlimited projects need Boost at $250/mo, and per-project access control (RBAC) needs Enterprise at $2,000/mo.** The organization invites API works on any plan ([PostHog invites API](https://posthog.com/docs/api/invites)). The cheap path is a few projects that you alone can see. It does not give each Octo user their own login.

**Statsig** has the cheapest event-plus-replay free tier: 2M events and **50k replays a month free**, and Pro at $150 for 5M events and 100k replays. Pro allows **one project per subscription**, and the pricing page does not list heatmaps ([Statsig pricing](https://www.statsig.com/pricing)). Mixpanel Growth costs $613/mo at 5M events, about 4x PostHog's anonymous rate ([Mixpanel pricing](https://mixpanel.com/pricing/)). The enterprise digital-experience tools are out of budget. Vendr's median FullStory deal is $28k a year ([Vendr](https://www.vendr.com/marketplace/fullstory)), and Quantum Metric averages about $280k a year by one estimate ([ITQlick](https://www.itqlick.com/quantum-metric/pricing)).

**Microsoft Clarity** is free with no traffic tiers. It gives unlimited projects and members, and records up to 100k sessions per project per day ([Clarity FAQ](https://learn.microsoft.com/en-us/clarity/faq)). Its metrics include scroll depth, dead, rage and quickback clicks, and it always masks inputs ([Clarity FAQ](https://learn.microsoft.com/en-us/clarity/faq); [Clarity Export API](https://learn.microsoft.com/en-us/clarity/setup-and-installation/clarity-data-export-api)). Three limits matter here. **It has no API to create projects or members**, and export is capped at 10 calls per project per day, so Octo cannot provision it ([Clarity Export API](https://learn.microsoft.com/en-us/clarity/setup-and-installation/clarity-data-export-api)). You cannot delete one user's data, only a whole project, and recordings last 30 days ([Clarity FAQ](https://learn.microsoft.com/en-us/clarity/faq)). Microsoft's terms let it use personal data to build profiles, including for advertising ([Clarity terms](https://clarity.microsoft.com/terms)). That makes it a poor fit for the legal search app and for any tenant app. It works best on your own public websites, as a free source of rage/dead-click data next to Umami.

## The ranked shortlist and how to combine the pieces

**1. Umami self-hosted: recommended core.** It is the only free tool here that combines heatmaps, replay, funnels, an MIT licence, Postgres-only storage and a full provisioning API for teams and users. Octo's provisioning code stays small: create a team, create websites, add users with a role. The trade-offs: frustration signals (rage/dead clicks) and click autocapture are unconfirmed, there are no surveys or A/B tests, and replay storage could swell Postgres. Add **GrowthBook** for A/B tests or **Formbricks** for surveys only when a specific app needs them. Note that Formbricks CE caps you at **3 projects** ([Formbricks licence](https://formbricks.com/docs/self-hosting/license)).

**2. Rybbit self-hosted, plus Clarity on public sites: the scale fallback.** Pick it if the load test shows Umami's Postgres can't keep up with ingest or replay writes. ClickHouse handles event volume better, and the org and per-site permission model fits Octo. You give up first-party heatmaps. Clarity fills that gap only where you can set up projects by hand and accept Microsoft's data terms.

**3. PostHog Cloud on pay-as-you-go: the buy-everything option.** It is the only single tool with every feature you listed, and it costs nothing to run yourself. With ≤6 projects at 2-5M mostly anonymous events, expect about **$50-150/mo**, plus replay overage above 5k ([PostHog pricing](https://posthog.com/pricing.md)). Choose it if your time matters more than per-user tenant logins. It stops being cheap at more than 6 apps ($250) or per-project permissions ($2,000).

**4. OpenReplay CE: for the voice copilot's debugging.** It is the best open-source replay with network and console capture. Run it alongside Umami only if replays without devtools prove too thin for debugging the copilot. Budget about 8 GB of RAM.

**5. OpenPanel: if experiments come first.** It has A/B tests and replay in one light stack, but no heatmaps, and its API doesn't manage members.

Two warnings apply to any hybrid. First, running two trackers on one page doubles the client-side weight. Second, two ClickHouse stacks on one box double the background merge load. ClickHouse defaults to using up to **90% of host RAM** ([ClickHouse docs](https://clickhouse.com/docs/reference/settings/server-settings/settings/max-server-memory-usage)). Rybbit ships a 0.8 ratio, which is still too high on a shared box ([Rybbit compose](https://raw.githubusercontent.com/rybbit-io/rybbit/master/docker-compose.yml)). Set an absolute cap of a few GB. Every candidate ships Docker Compose with its own Caddy proxy. Remove that proxy when you import the stack into Komodo behind your existing cloudflared tunnel.

## Open questions that need a load test on the real server

No source gives measured RAM, CPU or disk per million events for any of these tools at 1-5M events a month. Every footprint figure above is a vendor minimum or an idle reading. Run the test on the 6c/12t, 22 GB-free box before you commit. **First**, replay real traffic shapes into Umami at 2x your expected peak (events per second and replays per hour). Measure Postgres CPU, insert latency, table and WAL growth, and replica lag. Confirm where replay chunks are stored. Repeat with Umami's ClickHouse backend if Postgres struggles. **Second**, measure the actual compressed bytes per replay for your apps. The map agent and voice copilot will produce very different DOM churn. Multiply that by 30 days of retention against the 380 GB disk. Published figures range from ~200-400 KB to a 5 MB fair-use ceiling ([rrweb Cloud](https://rrweb.com/product/cloud); [rrweb FUP](https://rrweb.com/fup); [Krama](https://github.com/NachikethaKG/Krama/pull/179)). **Third**, check features hands-on: whether Umami or Rybbit autocaptures every click, whether either detects rage or dead clicks, whether OpenReplay CE really has heatmaps, and whether Umami's funnels and journeys work as expected in v3. **Fourth**, run Rybbit side by side with a hard ClickHouse memory cap and compare its ingest headroom. Also test whether it runs against the existing Postgres 17 with the bundled database removed. **Fifth**, put a privacy review on the legal search app before any third-party script, Clarity included, touches it, and confirm input masking works on its search forms.

## Conclusion

The question "is there a better open-source PostHog?" has the wrong frame. No open-source project matches PostHog's breadth in 2026. PostHog's own free self-host edition is also not PostHog in practice: it has one project, is sized for a few hundred thousand events and comes with no support. What changed this year is that Umami gained replay and heatmaps on top of the most Octo-friendly provisioning API in the field. The cheap way to work as a solo UX owner is now one lightweight, API-provisioned core per server, with specialist tools added per app as real needs show up. A heavyweight suite is not required.

That also gives you a clean exit. If the load test fails, the Octo integration you build for Umami (team, website, user, role) maps almost one-to-one onto Rybbit's org, site and member model. Switching costs a provisioning adapter, not a redesign. PostHog Cloud stays available as a paid escape hatch for any single app that needs surveys or experiments next quarter.
